# 性能（2026-10-13）

- **每个 `motion.*` 元素都是 Motion 投影树上的一个节点**：只要应用里用过 layout / layoutId，Motion 就给所有 HTML 的 motion 元素建投影节点（不管它自己有没有 `layout`）。任何一个 layout 动画（选中高亮、导航指示块、命令面板的高亮）在动的每一帧都要把整棵树过好几遍，节点上的滚动位置也要重量（强制排版）。列表这种一屏几百个的地方，能不用 motion 元素就不用，用的话控制同时挂着的数量（笔记列表分批画）。
- memo 掉的 motion 元素不重渲染就不会量位置，layout 动画也就不播：它上面的东西变了（插进一张卡片、展开文件夹）时要让它也重渲染。笔记列表用一个「列表样子」的计数传给 `layoutDependency`，只换选中、只存正文时不变。
- context 的值每次渲染都是新对象的话，所有消费它的组件都跟着重渲染，`memo` 拦不住。要么拆成身份不变的那部分单独一个 context，要么 `useMemo`。
- CodeMirror 的 `new EditorView({ parent })` 会先把编辑器挂进页面、建好正文，最后才设 contentDOM 的 contenteditable / spellcheck 等属性 —— 挂在页面上时设这一下很贵（切一篇 4 倍降速约 50ms）。先不给 parent 建好，再 `appendChild(view.dom)`。
- 「写样式 → 量尺寸」放在循环里，每一轮都强制整页排版一次。要量一批东西就先全部写完、再全部量、最后全部写（`math.ts` 的 `fitToWidth`）。
- 量按键延迟别用 Event Timing：无头模式下按键之后没有新画面时，条目会一直算到下一次真正绘制，长尾全是假的（同一段时间最长的一帧只有 75ms，它报 1 秒）。用页面里「keydown → rAF 里再 setTimeout 0」量。点击有画面变化，Event Timing 可信。
- 量之前、量之后的场景要真的一样：perf 脚本第一版先切换笔记再测打字，挑哪几篇笔记取决于列表画了多少行（分批渲染后变了），两边最后停在不同的笔记上，打字、滚动是在两篇不同的笔记里量的，结论正好反过来。
  改了「打的字落在哪」的时候同理：`typingMiddle` 的光标放在长文正中那一行，正好是一张表的表头，打的字落到表格下面紧贴的那一行；
  2026-11-16 修「字并进表格」以前量的是在整张变回源码的表格里打字，修了以后是普通的一段字，p50 从 41–53 掉到 28–44 ms（4 倍降速）—— 不是变快了，是量的东西变了（`表格.md` §13）。
  数变得不合常理时先看一眼场景里实际发生了什么（打完的正文、DOM 换了多少节点），再找原因
- **`:focus` 后面跟不带类名的后代（`:focus ::selection`、`:focus *`），焦点每变一次整棵子树重算样式**：Chrome 认不出这条规则只牵涉哪几个后代，只能把「焦点变了的那个元素」整棵子树的样式作废（后代带类名的 `:focus .x` 只作废那几个 `.x`）。
  正文 `.cm-content` 里一直有一条 `.odea-editor .cm-content :focus ::selection`（抄 CodeMirror drawSelection 的写法），正文每得一次、失一次焦点（开关命令面板、点侧栏、切窗口）画出来的整篇都重算：
  长文、4 倍降速一次 26–39ms，`UpdateLayoutTree` 重算 1491 个元素；删掉这条降到 1.6–2.8ms（2–4 个元素）。只写 `:focus::selection`（选区在得焦点的那个元素自己身上）。
  模态框修好焦点归还以后（焦点回正文），这笔早就有的浪费变成每次都要付，命令面板打开从 85ms 慢到 113ms，才被 `perf.mjs` 量出来；
  回归测试 `src/styles/focusInvalidation.test.ts` 查 `globals.css` 里没有这种写法（2026-11-14 全项目审查 §4.59）
- **这台开发机是大小核（i9-13980HX：8 大核 16 线程 + 16 小核），单线程的基准不绑核时每隔几次就有一整轮慢 40–50%**（被排到小核上）。一边连着撞上两次，看着就像「改慢了」（2026-11-15 量后端时差点误判，REVIEWS/2026-11-15-桌面端验证.md §2.4）。量 CPU 上的耗时先绑一个大核：`cmd /c start /b /wait /affinity 10 <exe> …`（第 4 个逻辑核），之后同一边几次之间差 2–5%
- **读整张表的大列只为在里面找一个词，别为每一行建一份带全文的结构、整篇转小写**：`search_text` 以前每篇都建一份带正文的 `DocRow`、`to_lowercase` 一份，
  3000 篇 13 MB 一次 100 ms，真正找只要 1 ms。`row.get_ref(..).as_str()` 借着读，命中了才建行；只有 ASCII 和没有大小写的字时在原文里按字节不分大小写地找（`vault/index.rs::Needle`）。
  同理，一批读进索引别一篇一个事务：每篇提交一次，同几页 B 树一遍遍写进 WAL，写库占了读一篇的一半多（`begin_batch` + 每篇一个保存点，−25–35%）（2026-11-15，`REVIEWS/2026-11-15-桌面端验证.md` §3.6、§3.7）
- **逐字比（LCS）光给每一处设上限不够，要给一次调用设总量**：两份分叉很久的长文，每一处都不到上限，加起来在主线程上算 800 ms（`collab/external.ts::fineEdits` 的 `MAX_TOTAL_CELLS`，同上 §3.8）
- **长操作别一直拿着仓库的锁，一大批变化别一个个通知前端**（2026-11-19，`仓库与启动器.md` §21）：导入以前在锁里拷完、读完（1 万篇 21 秒，这段时间点笔记、保存都排队，界面上什么都没有），
  再把几千个笔记 id 发给前端；`applyVaultChange` 每篇一个 `note_get` 来回、整个列表排一次序、重画一次，和「篇数 × 仓库篇数」成正比，1 万篇又是 4 分钟。
  拷文件不拿锁；读进索引照打开大文件夹那样每批 50ms 放开一次；一批超过 20 篇的变化前端整个重取两个列表
- **逻辑目录的树（`Tree`）上一篇篇 `find_note` / `place` 是 O(节点数)**：每篇线性找三四遍（找节点、找文件夹、列同层），往两万多个节点的树里放一万篇就是十几秒，还拿着锁。
  一批放进同一个文件夹用 `Tree::place_many`（文件夹、已有的节点只找一遍）
- **排序键一个个接在上一个后面，键越来越长**：`key_between(上一个, None)` 每五六次长一位，一个文件夹放三千篇键就有几百个字符，清单文件跟着变大。
  空文件夹一次放一大批用 `spread_keys`（在 (0, 1) 里均匀摊开、等长，一万篇三位）
