# 工程约定

## 结构与命名

- 新建目录、文件之前先看现有的结构和实现，目录结构必须反映真实的系统架构、功能领域及模块职责，禁止随意创建平行目录或重复模块。
- 优先按照功能和模块职责组织代码，将紧密相关的实现、类型、样式及测试合理集中；跨模块真的复用才提到共享的地方
- 避免目录过度嵌套、文件过度拆分及单个文件承担过多不相关的职责。
- 挪、改名、删文件时查引用、动态加载、构建配置、测试、文档
- 源码目录里不留临时文件、调试文件、废弃的实现、备份；版本交给 git，文件名里不带 new、old、final、temp、copy
- 同一个概念在界面、代码、接口、文档里用同一个词；时间、大小这类数值在名字或类型里带单位

## 代码

- 注释写为什么这么做，不要写没用的注释
- 避免重复实现、无意义的硬编码、魔法数字及本次变更产生的废弃代码。
- 修 Bug 先写一条能失败的测试
- 证据优先，禁止凭空猜测技术事实，同时要避免过度设计和无意义的抽象，一切技术决策必须有依据，包括现有代码、官方文档、源码、实验或实际测量数据。
- 代码质量、性能、可维护性是交付要求，而非可选的优化项。
- 不以牺牲长期代码质量换取短期开发速度

## 前端

- 界面高级、优雅、丝滑、符合项目主题。
- 要以人为本，尽可能达到极致用户体验，可以先查阅资料，同时要保障性能。
- 保证不同设备、屏幕尺寸下的布局和交互体验，保证字体清晰、图像清晰。
- 保证视觉层级、文字可读性、不同设备下的交互一致性。
- 界面上每个元素都要有信息或交互的价值：不加多余的小字、重复的说明、装饰性的标签
- 优化先量再做：有测量依据才加缓存、memo
- 监听器、定时器、订阅用完要清；异步的结果回来时先确认还是不是当前要的
- 优先使用已有设计系统及公共组件
- 追求极致的用户体验和性能要求

## 后端（Rust）与数据

- 追求极致的用户体验和性能

## 依赖

- 加依赖之前看：现有的代码和依赖能不能解决；多多少体积（前端分包、安装包）、多少传递依赖。重的依赖用到时再加载
- 锁住的版本不动：tauri-specta 的三个 crate（`技术方案.md` §7.1）、`tauri-plugin-global-shortcut`（`TODO.md` P15「全局快捷键速记」）、
  Mermaid 底下的 KaTeX（`1110审查与研究.md` §5.4.1）
- 升级依赖单独做、单独验

## 测试

- 层级和现状在 `技术方案.md` §15：Rust 单元测试、前端单元（`*.test.ts`）、前端 DOM（`*.dom.test.ts(x)`，
  文件头 `// @vitest-environment happy-dom`）、读 CSS 的守卫测试
- 单测走不到的路（输入法的组字、沙箱的隔离、逐帧的动效、窗口级的动画）用 `scripts/perf/` 里的脚本在真的内核里验（`VERIFICATION.md`）
