## 3. 发现（修了的）

### 3.1 【体验·键盘】启动器「拉取」：没登录时点 GitHub，等验证码的那几秒焦点掉在 body 上、Esc 退不出去；要码失败以后还在 body 上（第二段，第四个会话）

- **位置**：`src/launcher/ClonePanel.tsx`。托管方按钮 `disabled={!!working || busy}`：按下 GitHub 以后 `working` 是「正在向 GitHub 要验证码…」，按下的那个按钮变灰，
  浏览器把焦点挪到 body；Esc 挂在这一屏的 `div` 上，收不到。§4.55 加的「焦点没处去时放到『返回』上」只在 `step.kind` 变的时候查，要码这几秒 `step` 还是 `provider`、
  要码失败也回到 `provider`（没变），都查不到。审查验 §4.55 时的假接口是登录过的（直接进仓库列表），没走到这条路
- **怎么触发 / 证据**（桌面端，真按键）：启动器回车进「拉取」、Tab 到 GitHub、回车：之后每 150ms 读一次焦点，6 次都是 `BODY`，「正在向 GitHub 要验证码」显示着；这时按 Esc 什么都不发生；
  让要码 6 秒后报错（包 `fetch`），报错显示出来以后焦点还是 `BODY`，再按两次 Esc 也不动。国内不开代理时要码要等很久，用键盘的人这时候既退不出去、失败了也不知道焦点在哪
- **修**：那个 effect 的依赖加上 `working`（忙起来、忙完都查一次），焦点在一个变灰了的按钮上也算「没处去」（React 在离散事件里同步跑 effect，这时浏览器还没把焦点挪走）。Gitee 验令牌、列仓库这些 `run` 也走同一个 `working`
- **验**：同样的按键（Vite 热更新以后刷新启动器）：等码时 4 次读焦点都是「返回」；要码失败后焦点在「返回」；等码时 Esc 回首页、焦点在「拉取」。
  回归测试 `src/launcher/Launcher.dom.test.tsx` 加 1 条（等码时焦点在「返回」、失败后还在、等码时 Esc 回「拉取」），把修复撤掉这条挂（`expected null to be '返回'`）

### 3.2 【缺陷·数据】组字时防抖存盘照样到点：拼音落盘；回音以后外面一改文件，编辑器整篇替换，组着的词跑到文档开头、拼音留成正文（第三段，第五个会话）

- **位置**：`src/editor/MarkdownEditor.tsx` 的 updateListener 每次 `docChanged` 都 `saver.schedule(正文)`，组字时的正文是拼音；`src/editor/debouncedSave.ts` 400ms 到点就写。
  回音确认以后 `syncedMarkdownRef` 是带拼音的那一版，`current === synced`，外部改动走「没有没存的改动 → 整篇替换」（同一个文件的 `[initialMarkdown, externalRevision]` effect）
- **怎么触发 / 证据**（桌面端 WebView2，CDP 组字）：组 s → sh 停 800ms、shu … shuru 停 700ms 再上屏：包 `fetch` 记到三次 `note_save`，前两次是 `…sh`、`…shuru`。
  组 wai 停 800ms，外面往文件里加一行：编辑器换成外面那一版、光标到 0，接着组的字出现在开头，上屏后 `外面# 输入法三 … 这一篇。wai`，磁盘上一样。真输入法挑候选停半秒以上是常事；
  外部改动可以是同步拉下来的、别的编辑器改的
- **修**：`createDebouncedSaver` 加一个 `hold`：到点时 `hold()` 为真就再等一轮（最多 30 秒，组字状态万一卡住也会存）；显式的 flush（失焦、换篇、关窗、Ctrl+S）不等。
  编辑器传 `() => !!live.view?.compositionStarted`。组字时正文和「已存」不一样，外部改动就走「两边都改了」（编辑器留着，外面那一版另存冲突副本），整篇替换不会落在组字中间
- **验**：桌面端重走（§2.3「修了以后重走」）：组字时一次没存、上屏后存一次；外面改文件时组字不断、词落在原处，外面那一版成了冲突副本。
  回归测试：`debouncedSave.test.ts` 加 2 条（等 hold、上屏后存最新的；显式 flush 不等、30 秒后不再等），`src/editor/imeSave.dom.test.tsx` 2 条（真的 `MarkdownEditor`：组字时不存、上屏后存一次；组字中外部改动算冲突、正文不动）。
  把编辑器传的 `hold` 换成 `() => false`，`imeSave` 两条都挂（`expected [ '甲ni\n', '甲nihao\n' ] to deeply equal []`）

### 3.3 【缺陷·输入法】组字时按 Ctrl+Tab（Ctrl+W、Alt+数字、Alt+←、Ctrl+K、Ctrl+Shift+F、Ctrl+;）照样换篇、开面板：组着的拼音成了正文里的字、存进文件（第三段，第五个会话）

### 3.4 【体验·输入法】命令面板组字时列表跟着拼音一个字母一个字母地跳，每个字母还搜一次正文（第三段，第五个会话）

### 3.5 【性能·改慢了】开关过日程以后，每次启动多 15 ms：`forget_kept_ids` 把日记留着的几百行挨个 stat（第四段，第七个会话）

### 3.6 【性能·浪费】搜正文每篇都建一份带全文的 `DocRow`、整篇转一份小写：3000 篇一次 100 ms，命令面板每打一个字一次（第四段，第八个会话；原来是 §4.3 的候选）

- **位置**：`src-tauri/src/vault/index.rs::scan_text`（命令面板、归档搜索框的 `search_text`）
- **证据**（§2.4「§4.3 搜正文拆开量」）：一次 100–137 ms 里，`SELECT` 21 列 + 每篇建 `DocRow`（全文拷成 `String`）48 ms、每篇 `to_lowercase` 69 ms，真正找 ≤ 1.2 ms
- **修**：① 正文用 `get_ref` 借着读，选列时 `'' AS content_md, content_md AS body`，命中了才 `row()` 建 `DocRow`（不带正文）；
  ② `Needle`：要找的字只有 ASCII 和没有大小写的字（中文、数字、标点、表情）时直接在原文里找，ASCII 字母不分大小写 —— 先用 `str::find`（memchr / Two-Way）找要找的字里最长一段不带字母的（≥ 3 字节），

  剩下的：SQLite 把 13 MB 读一遍（mmap 后约 12 ms）+ 命中的篇建 `DocRow`（3000 篇命中时约 10 ms）。核心基准（走 `vault.db()` 主连接、①② 的第一版）里 `search_common` 也是 106 → 47，同一个方向。
  检查：`cargo test --no-default-features --lib` 388 条全过（多了三条）、clippy 两遍（默认、`--profile test`）都过；命令和类型没动，`bindings.ts` 不用重新导出；前端没动

### 3.7 【性能·浪费】读文件进索引一篇一个事务：后台读、整扫、只重读几篇都是每篇提交一次（第四段，第八个会话；原来是 §4.4 的候选）

- **位置**：`src-tauri/src/vault/index.rs::put` / `remove` 各自 `unchecked_transaction`；`Vault::index_backlog`（后台每批 50 ms）、`rescan`、`rescan_paths_and_announce` 一篇调一次
- **为什么一篇一个**：看了代码（`index_backlog`、`vault_ops.rs` 的后台线程、`put` 的注释），没有「随时能被打断、前台插进来、崩了不丢进度」的设计：后台那一批本来就在仓库的锁里一口气做完 50 ms（前台要等的就是这一批），
  一篇一个只是 `put` 自己要原子（文档和插件的表同一个事务）。WAL + `synchronous=NORMAL` 下提交不刷盘，但每次提交都把这一篇碰过的 B 树页再写一遍 WAL，同一批里几十篇碰的是同几页
- **修**：`index::Atomic`：`put` / `remove` / `drop_kept` 的写改成 `SAVEPOINT doc_write` … `RELEASE`（外面开着事务时是其中一个保存点、一篇失败只退它；没开着时它自己就是一个事务，保存、改名这些单篇的写照旧），
  `?` 中途出去时 `Drop` 里 `ROLLBACK TO` + `RELEASE`，不把事务留着开着。`Vault::batched`：`index_backlog` 的一批、`rescan` 整个、`rescan_paths_and_announce` 读的那一段包一个 `BEGIN` … `COMMIT`；
  中途出错（`rescan` 的 `?`）时已经写好的照样提交（和以前一样）；提交失败整批退回、记一笔，这一批的文件索引里还是旧的或者没有，下次扫描按修改时间和大小再读（和一篇读不了时一样）。
  不变的：每批的时间预算（50 ms）、前台等的最多一批、`on_indexed` 在最后一批提交以后才调、通知前端在提交以后（`rescan_paths_and_announce` 改成提交完再 `announce`）
- **验**：回归测试 `vault::index::tests::a_batch_commits_once_and_a_failed_write_only_undoes_itself`（一批里一篇撞了 `doc_key` 唯一索引：只退它、事务还开着、别的连接提交前看不见、提交后都在；
  没开批时每篇自己提交、失败了不留开着的事务；已经在事务里时 `begin_batch` 不另开也不替别人提交）；kept_ids 的五条（`foreign_notes_keep_their_ids_*`、`ids_survive_two_rebuilds_in_a_row`、
  `kept_ids_wait_for_files_that_could_not_be_read`、`a_kept_id_is_not_handed_to_another_note_later`、`kept_ids_of_plugin_docs_stay_until_their_files_are_gone`）和整套 `vault::tests` 照过。
  量（§2.4 的表）：第一次读完 1368 → 1026 ms（−25%）、重建 1481 → 1036（−30%，比基线还少）、日程关 / 开 −27% / −33%、外面改 100 个 −35%；再次打开、存盘不变

### 3.8 【性能·卡顿】挂上会话时逐字比没有总量上限：两份分叉很久的长文（很多段整段改写）在主线程上算近一秒（第五段，6.7 复审）

- 位置：`src/collab/external.ts::fineEdits` / `charEdits`。6.7 的逐字比只有「一处」的上限（100 万个格子），`textEdits` 按没动的行（Markdown 段和段之间的空行）切成很多处，
  每一处都不到上限、加起来没有上限。`binding.ts::align` 在绑定的构造函数里同步算（`origin → 会话`、没有 origin 时 `编辑器 → 会话`），团队里没有 base、本机和主持人分叉了的那种最容易碰到
- 证据：把 `lineDiff.ts` + `external.ts` 拷出来用 Node 24 直接跑（会话临时目录 `fe/bench.mts`）：两份各 200 段 × 900 字、每段都改写 → `fineEdits` **798 ms**（`textEdits` 2 ms）；
  100 段 432 ms、20 段 79 ms。逐字比本身 900 × 900 一段 3.7 ms（换成整数数组也只快 1.4 倍，不是根因）
- 修：一次 `fineEdits` 加一个总量上限（400 万个格子，约 15 ms），用完了剩下的几处不细分（和 `textEdits` 一样整处替换：不丢字，只是同一段里两边都改了时对方的字挪到替换的边上）。
  复量：200 段 798 → **23 ms**、100 段 432 → 35 ms、20 段 79 → 20 ms；随机 2 万组（含 `\r\n`、emoji、组合字符、零宽字符、家庭 emoji、空串）打回去全对、不落在代理对中间
- 回归测试：`external.dom.test.ts`「很多段整段改写的长文：逐字比有总量上限……」（60 段 × 800 字、每段隔 40 个字改一个：前面细分、最后一处和 `textEdits` 一样）；把上限改成 `Infinity` 这条挂

### 3.9 【缺陷·协作】磁盘上是 `\r\n` 换行的笔记进协作：会话里留着 `\r`，访客的编辑器每行多出一个空行（第五段，6.7 复审）

- 位置：建会话（`session.ts` 的 `initialText`）、`markOrigin`、外部改动（`external.ts::mergeExternal`）都把磁盘上的正文原样放进 Loro；CodeMirror 的文档读进来时 `\r\n` 就成了一个换行，两边下标对不上。
  6.7 以前：访客的编辑器整篇换成会话的、CodeMirror 又把 `\r` 吃掉，编辑器比正文短，之后的字写进会话的位置每行错一个（数据错位）；6.7 以后：「以会话为准」改成细到字，
  插进来的每个 `\r` 在 CodeMirror 里成了一个换行 —— 访客看到每行后面多一个空行，在那里打字会写进 `\r` 和 `\n` 中间。团队加入时本机（`\r\n`）和主持人（`\n`）比，正文一样也被当成没合进去、之后另存一份冲突副本
- 证据（`binding.dom.test.ts` 里先写的探针）：主持人用 `a\r\nb\r\nc` 建会话，访客挂上 → 访客的编辑器 `"a\n\nb\n\nc"`；主持人的编辑器挂上以后才被它自己的对齐抹平（主持人没开着这一篇就一直这样）
- 修（根因：会话的正文一律 `\n`，和 CodeMirror 一样；存回去的是 `\n`，和不协作时编辑器存盘一样）：`session.ts::toLF`，建会话、`markOrigin`、`mergeExternal` 的磁盘正文、团队 `join` 三方合之前的本机和 base 都过一遍
- 回归测试：`binding.dom.test.ts`「磁盘上是 \r\n 换行：会话里是 \n……」（访客、主持人的编辑器都是 `a\nb\nc`；外面存成 `\r\n` 的同样正文不算外部改动；访客打的字落在原位）；`toLF` 改回原样这条挂

### 3.10 【缺陷·体验】标签、键名打全了一个现成的名字，回车加上的是以它开头的另一条（第五段，6.2 复审，第十一个会话）

- 位置：`src/properties/PropertiesPanel.tsx::useSuggestions`。提示把「和打的字一模一样」的那条筛掉（`item !== query`），默认选中第一条的输入框（标签、列表、键名）里，
  排在第一的就成了以它开头的更长的那条。打「项目」（仓库里有「项目」和用得更多的「项目二期」）回车，加上的是「项目二期」；加属性打 `tag`（有 `tag`、`tags`）回车加的是 `tags`。
  6.2 要的正是「存的是打的字」，这条在快照以前就有，6.2 的测试只试了打一截的情况。另外标签照着显示的样子打了 `#`（`#项`），提示整个没了（拿带 `#` 的字去筛）
- 证据：新写的测试先跑一遍挂在「第一条是 `#项目二期`」（`expected '#项目二期' to be '#项目'`）
- 修：默认选中第一条的，和打的字一样的那条（不分大小写）不筛、排第一；不默认选中的（文字值）照旧不列它。标签的提示按去掉开头 `#` 的字筛（加的时候本来就去掉）
- 回归测试：`PropertiesPanel.dom.test.tsx`「typing a whole existing name and Enter keeps that name……」（带 `#` 打有提示；打全「项目」第一条是它、回车加的是它；加属性打 `tag` 回车加的是 `tag`）

### 3.11 【缺陷·丢字】属性的「源码」框里改了一半，别处一改这一篇（另一个窗口、外部程序、协作的对方），打的字整个被冲掉（第五段，6.8 复审，第十一个会话）

- 位置：`PropertiesPanel.tsx::SourceEditor` 的 `useEffect(() => setDraft(text), [text])`：面板收到仓库变动去取一遍，`text` 一变草稿就换成新的，不管用户改没改过。
  文字值（`TextValue`）是「没在打字时才跟上」，源码框没照这个来。快照以前就这样
- 证据：回归测试在旧写法下挂（打了两行以后外面一改，框里成了外面的那一版）
- 修：记着上一次显示的 `text`，草稿没动过才跟上；动过的留着，存好时以打的为准（和文字值一样）
- 回归测试：`PropertiesPanel.dom.test.tsx`「the YAML being edited is not wiped by a change from elsewhere……」（没动过跟上外面的；改了一半外面再改，框里还是打的，Ctrl+Enter 存的是打的）

## 4. 风险（读代码推出来、没复现的）

### 4.1 焦点在菜单按钮上时点它，菜单偶尔开了又自己收（第二段，第四个会话）

- **看到的**：列表头「排序」按钮（`ActionMenu`）有焦点时真点它（CDP 的 `mousePressed` / `mouseReleased`），两次里菜单 15ms 时开了（焦点进 `DIV[role=menu]`），约 110–300ms 后又收了、焦点回到按钮；
  紧接着同样的点法连点 9 次、循环 8 次都正常，没再出来。两次都在应用刚起来的头两分钟里（后台还在建索引、首扫）
- **猜**：Radix 收起是 `onOpenChange(false)`（焦点回到了按钮，说明不是整块重挂）；可能是首扫时列表栏重画让 `DismissableLayer` 记成了「碰了外面」，也可能是 OS 层面窗口焦点被别的程序拿走又还回来（用户的机器上别的窗口在动）。
- **怎样能复现**：刚起应用（或者造一批外面的改动让列表一直在刷新），焦点在「排序」上，每 500ms 点一次、记 `focusin` 的调用栈；收起那一次看栈是不是从列表的重画来的

### 4.2 上一份审查 §5.10（紧贴表格的那一行打字、粘贴进了表格）：桌面端复现了，几种修法和为什么没修（第三段，第五个会话）—— 做了，见 `表格.md` §13

- **复现**（§2.3）：格子里回车走出来、真点表格下面紧贴的空行，两种都落在那一行；在那里组字、粘贴，内容都成了表格的行，下面那段「后」也被带进表格。组字的第一个字母进来的那一刻表格就变回源码（光标进了表格）
- **不碰组字的办法有没有**：
  1. 第一次输入时补换行（`transactionFilter` 认 `input.type` / `input.paste` / `input.drop`，插在表格下紧贴的空行上就在前面加一个 `\n`）：普通打字、粘贴、拖进来都能在同一个事务里干净地做完，不碰组字。
     但组字的第一笔是 `input.type.compose`，同一个事务里在它前面加换行，组字的文本节点就换了行，CodeMirror 保不住组字节点、要重画，输入法会断（CodeMirror.md 第 10 行那条坑）
  2. `compositionstart` 里先派发一个插换行的事务、把光标挪到新行，浏览器再在新的选区上放组字串：用 CDP 的 `imeSetComposition` 多半能过（Blink 发完 `compositionstart` 再读选区），
     但真的微软拼音走 TSF，组字开始时输入法记着的位置和文本在 Chrome 的 TSF 桥里，开头这一下改了文本它跟不跟得上，只有真输入法能验（§6）
  3. 上屏以后再补换行（组字结束、CodeMirror 读完最后一次改动以后派发）：内容最后是对的，但组字的那一两秒表格一直是源码（整张表闪成源码再变回来），
     派发的时机要照协作绑定那一套等「最后那次组字改动读进来」（`协同编辑.md` §4.3），复杂、容易丢字
  4. 「点下去的那一刻 / 回车走出来的那一刻就隔开」：走出来时补一个换行（像文末那样）—— 回车本来就是换行，这一条最干净，但它改了 §4.43 定的「只是走出来时不为留空行改正文」；
     点下去就补换行是「路过就改正文」（点了不打字也多一行、会存盘、会进协作），不该做
- **为什么没修**：不碰组字又不闪的只有 4 里「回车走出来时补换行」，那是改产品行为（§4.43 当时特意不这么做）；点下去那条路只有 2 能做，要真输入法验。照交接的话「没把握不硬做」。
  **建议**：先做 1（普通打字、粘贴、拖放，不碰组字）+ 4 的「回车走出来补换行」；组字那一条等能用真的微软拼音验时再试 2。这几条都改「打的字落在哪」，由用户定（同上一份审查 §5.10）

### 4.3 【性能·候选】搜正文一次扫全部正文、每篇都整篇转小写：3000 篇（12.7 MB）的仓库一次 100 ms，命令面板每打一个字搜一次（第四段，第七个会话）

- **量的**：核心基准（release、绑大核）`search_text` 一次：`vault-500`（2.25 MB）18 ms，`vault-3000`（12.7 MB）**100–105 ms**，有没有命中都一样（两边一样，不是这次改慢的）。
  命令面板（`CommandPalette.tsx` 的 `useTextSearch`）每个字发一次，后来的顶掉还在扫的（`TEXT_SEARCH_GEN`），停下来那一下要等满一整次，正文命中比标题命中晚 0.1 秒出来
- **读代码看到的**：`index::scan_text` → `each_text_doc` 把每一行 `SELECT {COLUMNS}`（整行 21 列连同 `content_md`）建成 `DocRow`，`line_with` 里 `content.to_lowercase()` 把每篇整篇转一份小写再 `find`。
  没采样，不知道是 SQLite 取行、建 `DocRow`、还是转小写占大头
- **可能的做法**（要先拆开量）：只取要用的几列；没有大小写之分的词（中文、数字）直接在原文里找、不转小写；ASCII 的词按字节不分大小写地找，命中了才转那一行
- **没做的原因**：不是这次改慢的；这一段上下文用到了约 80 次工具调用，留给下一个会话先拆开量再定
- **第八个会话**：拆开量了（§2.4），是浪费，修了，见 §3.6。全文索引不用加：剩下的大头是 SQLite 把 13 MB 正文读一遍（13–16 ms），`技术方案.md` §6 去掉 `doc_fts` 的理由照旧成立

### 4.4 【性能·候选】后台读进索引，一篇一个事务：写库占了读一篇的一半多（第四段，第七个会话）

- **量的**（`vault-3000` 第一次扫描，3365 个文件，核心基准的 `breakdown` 阶段打点）：stat + 读 + 解码 429 ms（每篇 127 µs）；拆属性块、摘要、字数、指纹这些纯算 212 ms（63 µs）；
  `index_text` 整个 948 ms（282 µs，其中又算一遍那 63 µs，剩下**约 220 µs 是写库**：`put` 每篇开一个事务，`SELECT` 旧行、删、插、插件的表、提交）。后台读完 1.3 秒里一半多在 SQLite
- **可能的做法**：后台那一批（50 ms 的预算）包进一个事务、`put` 用调用方的事务；常用的几条语句 `prepare_cached`。要动 `index::put` 的事务归属（一篇失败时整批回滚还是只跳过它），
  和「一篇读不了跳过、别的照常」的规矩要对上，先量收益再定。不是这次改慢的
- **第八个会话**：做了（一篇是一批里的一个保存点，失败只退它），后台读完 −25%，见 §3.7

### 4.5 【性能·记下】kept_ids 让重建、开关日程读完多 10–14%：`put` 每篇删一行（第四段，第七个会话）

- **量的**：`vault-3000` 重建读完 基线 1298–1358 / 现在 1434–1549 ms（+10–14%），日程关 / 开 +10–13%，重建打开（窗口等的）21 → 29 ms（`keep_note_ids` 抄 3000 行）。
  实验（`%TEMP%\odea-perf7\exp`，只把 `put` 里删 `kept_ids` 那一行拿掉，同条件 5 轮 `results-vault-3000-exp.jsonl`）：重建读完 +4.9%、日程关 / 开 +3% —— **多出来的约三分之二是每篇删那一行**
  （B 树上真删一行、每个事务多脏几页），`prepare_cached` 省不掉；剩下的是没写 id 的笔记查 `kept_id`、抄表
- **为什么没修**：能省的办法是「不在 `put` 里一篇篇删，`on_indexed` 时一条语句删掉索引里已经是笔记的那些路径」，改了技术方案 §5.3.1 用户定的「用掉的那一行删掉」的时机
  （重建读到一半时那几行还在）。重建只在升级、开关日程 / 归档时有，在后台，3000 篇多 0.15 秒；收益低、要改定好的方案，记在这里
- **第八个会话（结论：不改 kept_ids）**：更正一句 —— 「用掉的那一行删掉」是主会话调研时定的实现细节，不是用户定的。但 §3.7 一批一个事务以后，每篇删那一行只是同一个事务里多脏几页：
  `vault-3000` 重建读完 1036 ms 对第一次读完 1026（+1%，改前是 +8%），比基线的重建还少 24%；日程关 / 开同样。多出来的那 10–14% 已经没了，
  再把删除挪到 `on_indexed` 省不下什么，反倒要处理「读完以后才删」那一段时间里同一个路径上新建的笔记会捡到旧 id（`a_kept_id_is_not_handed_to_another_note_later` 守的那条），
  以及 `rescan` 不走 `on_indexed` 时用过的行留到下次启动。不值得动这块数据相关的代码，`技术方案.md` §5.3.1 不用改。剩下的是重建打开时 `keep_note_ids` 抄 3000 行（窗口多等 9 ms，升级时一次）

### 4.6 【性能·候选】启动、整扫比对用的 `file_states` 要顺着正文的溢出页读过去：3000 篇 11 ms，占再次打开的四成（第四段，第八个会话）

- **量的**（`perf8`，3000 篇的真索引，绑大核）：`SELECT rel_path, mtime, size FROM doc` 11.1 ms；只取排在 `content_md` 前面的几列 5.2 ms；在一份拷贝上建 `(rel_path, mtime, size)` 的覆盖索引（建一次 14.7 ms）以后 **0.6 ms**。
  核心基准的「再次打开」是 25 ms、「没变时整扫」24 ms，这一条占四成多
- **读代码看到的**：表里 `mtime`、`size` 排在 `content_md` 后面，长文的正文溢出到别的页，SQLite 要顺着溢出页链一页页读过去才拿得到后面的列
- **为什么没做**：两种改法都动索引的表结构 —— 加覆盖索引（`prepare` 里 `CREATE INDEX IF NOT EXISTS`，不升版本）每次写多维护一棵 B 树，第一次扫描、重建会慢一点，没量；
  把这两列挪到正文前面要升版本，每个用户升级时整个重建一次。收益是每次启动、每次整扫省 10 ms（3000 篇），不急。记进 `TODO.md`，先量写的代价再定
