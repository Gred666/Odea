## 1. 结论

| 层 | 定了什么 | 为什么 |
|---|---|---|
| 协同模型 | **会话式**：主持人分享一篇，别人加入；主持人那台的 .md 仍是唯一真相 | 技术方案 §2.2 早就否掉了「CRDT 存储」；不要账号，也不替别人存数据 |
| 合并算法 | **Yjs 13**（CRDT） | 实测每次按键收发的 p99 都在 0.1ms 以内，更新包 20 字节，前端只多 29KB（gzip） |
| 编辑器绑定 | **自己写**，不用 y-codemirror.next | 现成的两个绑定都不管输入法组字；要留住 CodeMirror 自己的撤销 |
| 传输 | **iroh 1.x**（QUIC，按公钥拨号），放在 Rust 侧 | 能直连就直连；端到端加密；1.x 之间线协议不变 |
| 服务器 | **默认一台都不连**；用户可以自己配中继 | 我们零运维；有条件的团队架一台小机器，全组受益 |
| 协议 | 只定一层薄的 **`odea/collab/1`**（ALPN），同步语义照搬 y-protocols | 合并算法和传输都有验证过的实现，自己发明只会更慢、更不稳 |
| 加入 | 邀请链接 + 主持人确认；局域网「附近」；回连链接 | 都不需要会合服务器 |
| 拓扑 | **星形**：更新经主持人转发 | 权限和落盘都在主持人那里；两个人时就是直连 |

难点不在带宽（一个人打字每秒几百字节），在两处：编辑器的边角（输入法、撤销、外部改动、光标，§4.3），和没有服务器时能不能连上（§5.3）。

## 2. 范围与约束

### 2.1 要什么

- 两个到几个人同时编辑同一篇笔记，看得到彼此的光标和选区
- **性能、实时性第一**：本地打字一点不受影响；别人的字在网络单程延迟之后马上出现
- 用户在全球各地，网络方案不按国家区分
- **我们不提供服务器**：默认点对点，用户可以自己配中继（§6）

### 2.2 和现有约束怎么对上

左边的节号是技术方案的，右边的是本文的。

| 现有约束 | 协同怎么守住 |
|---|---|
| 文件是真相（技术方案 §2.2、§5.1） | 只有主持人那台写盘，走原来的 `note_upsert`；会话的 CRDT 状态放在应用数据目录，不进仓库 |
| 本地优先，没网也 100% 可用（技术方案 §1.2） | 协同只在会话里存在；断网照常编辑，重连后合并 |
| IME 输入不能卡顿吞字（技术方案 §1.2） | 组字期间不收发会碰到它的改动（§4.3） |
| 单人可维护，不引入要专职维护的基础设施（技术方案 §1.2） | 默认零服务器；中继是用户自己的，无状态 |
| 一切皆文档，不写新视图组件（技术方案 §1.1） | 访客那篇在 `data/adapter.ts` 里多映射一种 `DocumentModel` |
| 动效规矩（CLAUDE.md、技术方案 §10） | 远端光标位置直接落位，名字标签只淡 opacity（§4.3） |
| 安装包 < 20MB、常驻内存 < 150MB（技术方案 §13.1） | Yjs 前端只多 29KB；一篇文档加 3000 次按键的 CRDT 约 2MB；中继不进主程序 |

### 2.3 v1 不做

- **持久共享**：访客那边长期留一份、隔几天各自改了再合并。会话期间的落盘（崩溃、断线后接得上）要做，会话结束后不留（§3）
- 共享整个文件夹、一次共享多篇；某一天、目标（v1 只做笔记）
- 只读之外的细粒度权限
- 短码加入（要一台会合服务器，§8.7）
- 移动端、浏览器版、语音视频

## 3. 协同模型：会话式

```
主持人：在一篇笔记上点「邀请协作」
   ├─ 起 iroh 端点（只在会话期间开着），建 Y.Doc（内容 = 编辑器里的文本）
   ├─ 生成邀请链接 → 用户自己发给别人（任何聊天工具）
   └─ 有人连进来 → 主持人确认 → 发快照 → 之后实时互发更新
访客：点链接 → Odea 打开 → 连主持人 → 等确认 → 收快照 → 打开一篇「协作中」的文档
结束：主持人点「停止协作」，或者所有人都走了；访客可以「存一份到我的笔记」
```

- **真相只有一份：主持人那台的 .md。** 远端的改动在主持人那边和自己打的字一样，走 400ms 防抖保存（技术方案 §8.6）；索引、git 同步、冲突副本都不用改
- **CRDT 里放的就是编辑器里的那份文本。** 换行统一是 `\n`（技术方案 §5.2），落盘时的处理照旧
- **访客手里是副本**：不落进访客的仓库。`DocumentSaveTarget` 多一种 `shared`（保存是空操作），横幅「正在和 张三 一起编辑」。「存一份到我的笔记」新建一篇，用到的图片从缓存拷进访客自己的「附件/」
- **会话状态落盘**：双方每隔几秒把 Y.Doc 的状态（`Y.encodeStateAsUpdate`，197KB 的文档导出约 4ms）写进应用数据目录的 `collab/<会话 id>`，会话正常结束就删掉。主持人崩溃、重启后在这篇上出「继续上次的协作」，访客自动重连；双方的 CRDT 历史都在，合并不用退回文本 diff
- **Y.Doc 不放在编辑器组件里**，放在会话模块（会话期间常驻）：切到别的笔记时照收更新、主持人照存；切回来时用 Y.Doc 的文本建编辑器
- **标题**（= 文件名，技术方案 §5.2）：v1 只有主持人能改，访客那边只读显示

**为什么不做持久共享。** 每人长期留一份、随时各自改、随时合并，CRDT 就成了数据的一部分，要和 .md、别的编辑器、git 同步三方对账 —— 正是技术方案 §2.2 当初否掉「CRDT 存储」的原因。会话式只在会话期间有 CRDT，会话之外一切照旧。

## 4. 合并：Yjs 和编辑器绑定

### 4.1 选型

| 方案 | 结论 |
|---|---|
| **Yjs 13.6** | ✔ 采用。打字收发的 p99 都在 0.1ms 以内；更新包最小（20 字节）、并发合并最快、前端体积最小（gzip 29KB）；事件同步派发，绑定里没有微任务竞态。用了十年左右，CodeMirror、ProseMirror、Monaco 都有官方绑定。v14 还在 beta（14.0.0-16），先用 13 |
| Loro 1.16 | 打字速度和 Yjs 打平；不带历史的浅快照加入最快，自带历史版本和可移动树，Rust 和 wasm 是同一个核心。但更新包大 4–5 倍、并发合并慢 4–6 倍、wasm gzip 后 1.1MB（解压后 3.4MB）；CodeMirror 绑定 loro-codemirror 0.3.3 一年没发版。做持久共享、共享文件夹时再考虑 |
| Automerge 3.5 | ✘ 访客每收一次按键 16–37ms，文档越长越慢（测的是标准 JS 接口 `applyChanges`）；同一位置两人各打 200 字，合并要 3–8 秒 |
| `@codemirror/collab` | 最轻的备选：主持人当中心权威，类 OT，几 KB，不要 CRDT 库，CodeMirror 的撤销天然配合。只做会话式也够，但断线久了 rebase 慢，以后做离线合并、共享文件夹得推倒，不选 |
| diamond-types（Eg-walker） | ✘ 算法最新（EuroSys 2025），但 JS 包 2023 年以后没再发版，没有编辑器绑定、没有光标 |

### 4.2 实测（2026-10-17）

初始内容是 `docs/技术方案.md`（197KB，10.6 万个 UTF-16 单元），模拟 3000 次按键：每次随机落到文中一处、连写 1–40 下再换地方，其中 60% 汉字、27% 英文字母、3% 回车、10% 退格。主持人每按一下，更新包立刻交给访客。条件和 `docs/语法全览.md`（68KB）的结果见附录 A.1，同量级或更小。

| | Yjs 13.6.33 | Loro 1.16.4 | Automerge 3.5.0 |
|---|---|---|---|
| 本地改 + 出包（中位 / p99） | 0.030 / 0.090ms | 0.030 / 0.183ms | 0.47 / 2.3ms |
| 对方收包 + 应用（中位 / p99） | 0.014 / 0.061ms | 0.027 / 0.154ms | **37 / 48ms** |
| 每次按键的更新包 | 20B | 90–99B | 112–116B |
| 加入：完整快照 | 210KB（brotli 后 89KB），载入 14ms | 277KB（brotli 后 169KB），载入 6.8ms | 109KB，载入 86ms |
| 加入：更小的格式 | V2 编码 207KB（brotli 后 86KB） | 不带历史的浅快照 139KB（brotli 后 122KB），载入 1.5ms | — |
| 同一位置两人各打 200 字 | 合并 4.3ms，收敛，不交错 | 17.8ms，收敛，不交错 | 7.7 秒，收敛，不交错 |
| 断线后各写 1000 下再重连 | 补齐包 10.9KB，合并 3.7ms | 3.3KB，1.4ms | 109KB，38 秒 |
| 内存（文档 + 3000 次按键） | ≈ 1.8MB | ≈ 2.2MB | 没量 |
| 前端体积（gzip） | 29KB（含 y-codemirror.next） | wasm 1.1MB | 没量 |

打字时双方的 CRDT 开销都不到一帧（16.7ms）的 1%。真正花时间的是网络，以及 CodeMirror 画这一次改动 —— 和本地按一次键同价（技术方案 §13.2：一次按键 2.4–3.9ms）。

### 4.3 编辑器绑定（自己写，约 200 行）

现成的 y-codemirror.next 0.3.6 和 loro-codemirror 0.3.3 做的事很简单：CodeMirror 的改动逐段写进 Y.Text，Y.Text 的变化变成一次 CodeMirror 事务。有两件它们都不管（源码里连 `composing` 都没出现）：输入法组字，以及 CodeMirror 自己的撤销。所以自己写。

**出站：本地改动 → Y.Text**

- 在 `ViewPlugin.update` 里，`docChanged` 且不是远端事务的，`iterChanges` 逐段写进 Y.Text；整个事务包在一次 `ydoc.transact(fn, LOCAL)` 里，Yjs 一次 transaction 出一个更新包
- 不攒批：每个更新包立刻交给 Rust 发出去；同一个任务里出了好几个（一次粘贴拆成几段之类），先 `Y.mergeUpdates` 合成一包
- **组字期间只写不发**：组字时 CodeMirror 文档里是拼音字母，直接发的话对方看到「nihao」闪一下变成「你好」。改动照常写进 Y.Text（本地的 Y.Text 和 CodeMirror 文档必须时刻一致），更新包先攒着，组字结束合成一包发 —— 对方只看到上屏的字

**入站：远端更新 → CodeMirror**

- Rust 送来的字节 `Y.applyUpdate(ydoc, bytes, REMOTE)`；Y.Text 的 observer 把 delta 变成一次 CodeMirror 事务：`changes` 加上 `Transaction.remote.of(true)`、`Transaction.addToHistory.of(false)`，再加一个自己的 `collabSync` 注解（和 `externalSync` 一样，用来认出这不是用户输入）
- 不带 `userEvent`：模板触发（`/模板`）、`【【` 双链补全这些只认用户输入的逻辑，不会被别人的字触发 —— 实现时逐个核对一遍
- 到了就应用。同一帧里来了好几个（重连补齐、三个人同时打字），这一帧已经派发过一次的话，剩下的合到下一帧一起派发，免得一帧里重排好几次
- **组字期间先排队，连 Y.Doc 都不碰**：收到的字节攒着，组字结束后一次应用、一次派发。放行的时机要等 CodeMirror 把最后一次组字改动读进来：组字结束后第一次 `docChanged` 的更新，或者 `compositionend` 之后 50ms 都没有新改动。**不能一听到 `compositionend` 就派发**：最后那次组字改动常常晚于 `compositionend` 才读进来（CodeMirror 在微任务里补读），而派发事务时 `EditorView.update` 会先 `observer.clear()`，把还没读进来的 DOM 改动整个丢掉 —— 那就是吞字
  - 为什么连 Y.Doc 都不碰：远端改动先进了 Y.Text、却还没进 CodeMirror 的话，组字期间本地的改动按 CodeMirror 的位置写进 Y.Text 就错位了，得像 OT 那样 rebase
  - 代价：组字的人在那一两秒里看不到别人的改动，上屏后一起出现。换来的是输入法永远不会被打断（CodeMirror 只在改动不碰组字范围时保得住组字，碰到了会中断，有的浏览器上还会重复上屏）。真有人嫌这一两秒，再做「不碰组字那一行的改动立刻进来」，那要在绑定里做 rebase

**撤销**

- 留着 CodeMirror 自己的 `history()`（`MarkdownEditor.tsx` 里那一个）：远端事务标了 `addToHistory: false`，history 会把已有的撤销记录映射过远端改动，于是 Ctrl+Z 只撤自己的。`@codemirror/collab` 靠的就是这套机制。表格格子编辑、模板这些「和正文一样撤销」的行为都不用动
- 不用 `Y.UndoManager`（y-codemirror.next 的做法）：它要换掉 CodeMirror 的 history；而 y-codemirror.next 派发的远端事务没标 `addToHistory`，两者混用时 Ctrl+Z 会撤掉别人的字
- 撤销出来的是一次普通的本地改动，照常写进 Y.Text 发出去
- 主持人的撤销历史保留（都是自己的改动）；访客从空的历史开始

**远端光标**

- 位置用 `Y.RelativePosition`（贴着字走，不会被别人的插入挤偏），经 QUIC 数据报发（§7.2）：选区变了就发，同一帧只发最后一次；停下 200ms 后补发一次最终位置（数据报可能丢）；静止时 5 秒一次心跳，15 秒没消息就淡出
- 像 `selectionLayer.ts` 一样画在 CodeMirror 的 layer 里；位置变了**直接落位**，不做位移过渡（CLAUDE.md 动效规矩第 1 条）
- 名字标签：只淡 opacity，`will-change: opacity`，每次淡入前 `snapToDevicePixels`；用这个人自己颜色的实色底，不用毛玻璃（规矩第 3、4 条）。`scripts/perf/fade-frames.mjs` 加一个场景验
- **不参与藏标记**：reveal（光标进入语法范围就露出源码）只认本地光标。别人的光标一动、你这边排版就跳，是最糟的体验
- 每个人一个颜色，从一组固定的色板里按公钥算；亮、暗两套主题都要看得清

**和编辑器现有机制的交界**

| 现有机制 | 协同时怎么办 |
|---|---|
| 外部改动回填是整篇替换（`externalSync`，技术方案 §11.6） | 共享中的文档不走这条（§4.4）。整篇替换 = 在 CRDT 里删光再插一遍：所有人的光标塌到一处，那一刻别人正在打的字落到莫名其妙的位置 |
| 平滑光标（`smoothCaret.ts`：小于 120px 的位移走过渡） | 远端事务引起的位移直接落位。字是瞬间挪过去的，光标却在后面追着滑，看着像光标自己在动 |
| 编辑器状态缓存（12 篇 LRU，技术方案 §11.6） | 共享中的文档不进缓存、不从缓存里取：切走期间远端还在改 |
| 保存（400ms 防抖，技术方案 §8.6） | 主持人照旧，远端的改动也存；访客是空操作 |
| 块级装饰的打字快速路径（`mapBlockState`，技术方案 §11.2） | 不用改：远端改动和本地打字一样走它 |
| 标题收起（`headingFolds`，技术方案 §11.4.5） | 位置映射本来就支持别处的改动；「改动碰到收起的内容就展开」只认本地改动 —— 别人改了你收起的那一节，不该替你展开 |
| 表格格子编辑（`tableWidget.ts`） | 格子里正在编辑时远端改了同一张表：格子跟着重画，但不丢焦点、不丢光标。专门测 |
| 双链 `knownWikiTitles`、图片 `imageBaseDir` | 访客那边：双链按「不存在」画（指向的是主持人的笔记）；相对路径的图片从主持人那里按需拉（§7.2），缓存在临时目录 |

### 4.4 外部改动进 CRDT

会话中，主持人那台的文件被别的程序改了（另一个编辑器、git 同步拉下来的、网盘）。

- 不能拿磁盘上的新版和 Y.Text 直接 diff：主持人那边可能有还没存下去的会话改动（防抖期间），直接 diff 会把它们当成「外部删掉了」
- 做法：**把外部程序当成一个从「上次保存」处分叉出去的协作者。** 每次保存成功时留一份当时的 Y.Doc 状态（导出一次约 4ms，和保存一起做）；外部改动到了，用这份状态建一个临时的 Y.Doc（新的 clientID），把「上次保存的正文 → 磁盘上的新正文」的差异作为编辑打在它上面（先逐行，`lib/lineDiff.ts`；改了的行里再逐字），再把它的更新合进会话的 Y.Doc。外部改动和会话里的改动按 CRDT 规则合并，大家都看到；不出冲突副本
- git 同步（技术方案 §5.9）合并下来的改动也走这条
- 主持人自己保存回去的那一次：内容指纹对得上，不会被当成外部改动（技术方案 §5.3 本来就这样）

## 5. 传输：iroh，默认不连任何服务器

### 5.1 选型

| 方案 | 结论 |
|---|---|
| **iroh 1.x**（n0，Rust；2026-06 发 1.0，现在 1.3） | ✔ 采用。按公钥拨号，连接本身就是双向认证 + TLS 1.3；一条 QUIC 连接里多条路径（局域网、IPv6、IPv4、中继）同时试，自动换到最快的那条；可靠的流 + 不可靠的数据报；路由器端口映射、局域网 mDNS 都现成；1.x 之间线协议不变 |
| WebRTC（WebView 里） | ✘ 信令、STUN / TURN 一样要服务器；Linux 的 WebKitGTK 默认构建不带 WebRTC（WebKit bug 274711 还开着）；网络跑在 WebView 主线程上 |
| 中心服务器（y-sweet、Hocuspocus 这类 WebSocket） | ✘ 每次按键多绕一跳；要账号、要运维、要替别人存数据，和本地优先、单人可维护都冲突 |
| libp2p | ✘ 能做，但打洞同样要中继协调，组件多、体积大，对这个场景太重 |
| Hyperswarm / HyperDHT | ✘ 去中心化的打洞做得最好（Keet 在用），但跑在 JS / Bare 运行时上，没有能用的 Rust 实现 |

### 5.2 默认配置

```rust
// 示意，接口以 iroh 1.3 为准
let endpoint = iroh::endpoint::Builder::empty()     // 不连 n0 的中继，不用 n0 的 DNS
    .secret_key(device_key)                          // 设备身份，放系统钥匙串（§8.6）
    .alpns(vec![b"odea/collab/1".to_vec()])
    .portmapper_config(PortmapperConfig::Enabled)    // UPnP / NAT-PMP / PCP：问自家路由器要一个公网端口
    .relay_mode(relay_mode)                          // 默认 Disabled；配了中继是 Custom（§6）
    .bind()
    .await?;
let mdns = MdnsAddressLookup::builder().build(endpoint.id())?;  // iroh-mdns-address-lookup：局域网发现
endpoint.address_lookup()?.add(mdns.clone());
```

- **端点只在会话期间开着**：开始协作时起，结束时关。平时不占端口、不广播、不弹防火墙
- 上面的 `portmapper_config` 是示意：iroh 1.3 没配中继时根本不去要端口映射，实际是自己驱动 `portmapper`（§17.2）
- 代码里不出现 n0 的中继和 DNS 地址。加一个测试守着：默认配置下端点的中继表是空的，地址查找只有 mDNS
- IPv4、IPv6 都绑（iroh 默认就是双栈，IPv6 绑不上不算错）
- BitTorrent 的公共 DHT（`iroh-mainline-address-lookup`）按公钥找人：没有采用。它不属于任何公司，但要依赖别人运营的引导节点，查一次比 DNS 慢；好处（主持人换了网络、旧链接照样找得到人）以后需要再加

### 5.3 不靠服务器能连上哪些情况

先说清一条绕不过去的限制：互联网上两台电脑如果都在 NAT 后面、都不允许外部连进来，没有第三台机器帮忙，**任何协议都建不起连接**。打洞之前两边要先知道对方的公网地址，这一步本身就要一个双方都连得上的第三方；打洞失败时，也只能靠第三台机器转发。

| 情况 | 怎么连 | 能不能保证 |
|---|---|---|
| 同一个网络（同一 Wi-Fi、办公室、手机热点） | mDNS 自动发现，「附近」列表里点一下 | 能。例外：开了「客户端隔离」的公共 Wi-Fi（酒店、咖啡馆、访客网络），设备之间互相看不见 |
| 主持人能被外部连进来：有公网 IPv6 且路由器放行，或者路由器给了端口映射 | 邀请链接里带着这个地址，访客直接拨 | 能连，看主持人的网络 |
| 主持人连不进来，访客能 | 反过来：访客一键生成「回连链接」发给主持人（§8.4） | 能连，多一步 |
| 两边都连不进来（手机网络、运营商级 NAT、公司防火墙最常见） | — | **连不上**，只能换到同一个网络（比如一方开手机热点给另一方），或者有一方配了中继（§6） |

后两种情况有多常见，没有可靠的总数，能找到的参考：
- 全球 IPv6：Internet Society 汇总几家来源平均约 43%，Google 2026-03-28 单日到过 50.1%；但很多家用路由器默认挡掉外来的 IPv6 连接
- 运营商级 NAT：移动网络绝大多数在用（2016 年的研究，APNIC 转述约 94%）；固定宽带 2017 年欧美抽样里约一成运营商在用，而且在涨
- 端口映射指望不上：2012 年一项覆盖 12 万户的研究里，多数家庭根本拿不到 UPnP 数据
- iroh 官方说的「约九成网络环境能直连」，前提是有中继帮忙交换地址；关掉中继以后会明显低一些，没有现成数据

所以「保证」拆成两半：**连上之后的体验能保证（§9.1）；能不能连上，同一网络能保证，互联网上尽量连，连不上就第一时间说清楚（§8.5）。**

### 5.4 拓扑：星形

- 所有更新经主持人：主持人收到谁的更新就转给其他人。Yjs 的更新可以原样转发，重复收到也没关系
- 某个访客那边慢（积压），主持人把要发给他的更新先 `Y.mergeUpdates` 合成一包再发，不排长队（实际做法：积压了就丢掉排着的、换成一次补齐，§18.1）
- 主持人负责鉴权：只读成员的更新直接丢；踢人就断开
- 两个人时就是直连；三人以上，访客之间多一跳
- 网状更快，但 Yjs 更新里的作者（clientID）是自报的、没签名，权限守不住。要做的话得先给更新签名，v1 不做

### 5.5 WebView 和 Rust 之间

- **CRDT 放在 WebView 里**，和 CodeMirror 在同一个线程：本地改动和远端改动在同一个线程上排队，CodeMirror 文档和 Y.Text 永远一致，不需要任何 rebase。Rust 只搬字节，不懂文档
- 前端 → Rust：`invoke` 带原始字节（不走一字节一个数字的 JSON 数组）
- Rust → 前端：Tauri 2 的 `Channel`。2.11.5 的实现（`ipc/channel.rs`）里，小于 1KB 的二进制、小于 8KB 的 JSON 直接 `eval` 送达，更大的走 fetch；每次按键的包都走 `eval`。往返延迟还没量，P10.1 量
- 握手、成员、权限这些控制消息由 Rust 解析，经 tauri-specta 生成的事件交给前端；文档更新、光标是不透明的字节，Rust 不解析
- v1 的 Rust 侧没有 Y.Doc（会话状态落盘也是前端交字节、Rust 写文件）。做持久共享时再在 Rust 侧放 yrs（和 Yjs 格式兼容）

## 6. 中继：我们不提供，用户可以自己配

### 6.1 中继起什么作用、谁配了算数

中继有两个作用：
- **打洞的介绍人**：告诉每个客户端自己的公网地址（QUIC 地址发现），帮双方交换地址。有它的时候，iroh 的说法是约九成网络环境能直连
- **打不通时转发**：剩下那部分走它转发。它只转发端到端加密的密文

| 谁配了中继 | 结果 |
|---|---|
| 主持人 | 邀请链接里带上中继地址和令牌，访客加入时自动用上：把它加进这次会话的端点（`Endpoint::insert_relay`，带上 `RelayConfig::with_auth_token`），会话结束就移除，不写进访客自己的配置 |
| 只有访客 | 访客的回连链接（§8.4）里带上自己的中继，主持人同样把它临时加进会话的端点，经它连过来 |
| 都没配 | 和默认一样：局域网、能直连的互联网、回连链接 |

所以一个团队里**有一个人架好，全组都能用**：把一串「中继码」发给大家，每人粘贴一次。

### 6.2 用户怎么架

用官方的 iroh-relay 就行，不用我们写服务端，也不发自己的服务端程序。

- **机器**：一台有公网 IP 的机器，云主机、NAS、家里常开的电脑都行。1 核 1G 就够（§6.3）
- **端口**：TCP 443（中继本身）、TCP 80（强制门户检测）、UDP 7842（QUIC 地址发现；不通的话转发照样能用，但打洞辅助没了）
- **证书**：有域名就用内置的 Let's Encrypt 自动签。没有域名用自签名证书，中继码里带上证书指纹，Odea 这边用 iroh 1.x 的自定义证书校验（`CaTlsConfig::custom_server_cert_verifier`）认它
- **访问控制**（官方程序自带）：`access.shared_token`（令牌，可以同时配好几个，能平滑轮换）、`access.allowlist` / `access.denylist`（按公钥，固定团队用白名单最省心）、`access.http`（每个连接问一次外部接口）
- **限速**：`limits.client.rx`，防止有人拿它传大文件

样例配置（我们的「自建中继」文档里给这一份，默认就开好访问控制和限速）：

```toml
# relay.toml —— 官方 iroh-relay 1.x，改好域名、邮箱和令牌
# 安装：cargo install iroh-relay --features server
# 运行：iroh-relay --config-path relay.toml
enable_relay = true
enable_quic_addr_discovery = true        # 默认是关的；打洞要靠它告诉客户端自己的公网地址
access.shared_token = ["换成一长串随机字符"]

[tls]
cert_mode = "LetsEncrypt"
hostname = "relay.example.com"
contact = "you@example.com"

[limits.client.rx]
bytes_per_second = 262144                # 每个客户端 256KB/s：打字绰绰有余
max_burst_bytes = 1048576
```

- 中继无状态，什么都不存：挂了重启就行，客户端自动重连；换机器不用迁移数据；9090 端口有指标（连接数、流量），这个端口别对公网开
- 用别人托管的中继（比如 n0 卖的托管中继）也行，对 Odea 来说都只是一个地址

### 6.3 多大的机器够（实测）

本机实测（2026-10-17）：iroh-relay 1.3 走 TLS；中继进程限定在 2 个逻辑核、2 个工作线程上，模拟 2 核机器；客户端两两配对，互发 100 字节的小包。方法和前提见附录 A.2。

| 中继每秒转发 | 在线连接 | 中继 CPU（满载 200%） | 转发延迟 中位 / p99 | 丢包 |
|---|---|---|---|---|
| 100 包 | 100 | 1.8% | 0.37 / 0.89ms | 0 |
| 1,800 包 | 200 | 19% | 0.87 / 2.3ms | 0 |
| 2,000 包 | 1,000 | 30% | 3.6 / 12.7ms | 0 |
| 5,000 包 | 1,000 | 70% | 8 / 37ms | 0 |
| 10,000 包 | 1,000 | 138%（已满） | 75 / 179ms | 0 |
| 30,000 包 | 1,000 | 已满 | 积压到 8 秒 | 86% |

内存：空载 35MB，每多一个在线客户端约 30KB。1 万人在线约 330MB，2G 内存挂几万个连接没问题。

换算成人：
- 一个人正在打字：每秒十来次按键，每次大约一个 QUIC 包（文档更新和光标可以装进同一个包），对方每两个包回一个确认，经中继每秒约 15 个包；中文输入法只在上屏时发，少得多。打一阵停一阵，平均每人每秒 2–5 个包
- 只有「两边都连不进来」的那部分人一直走中继；其余的人只在刚连上的头一两秒经过中继，之后每十几秒一次保活
- 所以 2 核在延迟还很低的区间（每秒 2000 包左右）就能同时给 400–1000 个只能走中继的活跃用户转发。按九成能直连算，相当于同一时刻几千人在协同

先吃紧的不是 CPU 和内存，是：
1. **带宽**：每个只能走中继的活跃用户平均约 0.5–1KB/s（进出各一份），1000 个约 4–8Mbps。加入时的快照（100–300KB）如果在打洞完成前发出，也会经过中继。很多 2C2G 的便宜套餐只给 1–5Mbps 固定带宽，这才是先满的那个 —— 选按流量计费、或者带宽 ≥ 10Mbps 的。附件不走中继：等直连了再传，或者单独限速
2. **位置**：中继夹在两个人中间，离双方越近越快。用户分布在全球的团队，美、欧、亚太各放一台 1–2 核的小机器，比一台大机器体验好得多；iroh 客户端会自动挑延迟最低的那台当 home relay

### 6.4 Odea 这边要做的

1. **配置入口**：命令面板「协作中继…」（不做设置页是定过的，技术方案 §16）；连不上时的排障面板里也给一个入口。地址记在应用数据目录的 `config.json`（每台机器一份，不进笔记仓库）；令牌放系统钥匙串，和同步令牌一样走 `keyring-core`
2. **中继码**：地址、令牌、可选的证书指纹和名字打包成一串 `odea://relay/…`。点开时问一句「添加中继 relay.example.com？」，必须用户确认 —— 它决定了以后你的连接元数据经过谁的机器
3. **「测试」按钮**：连一下，报告延迟、令牌对不对（iroh 的 `home_relay_status` 能直接拿到连接状态和「认证被拒」）、证书有没有问题、UDP 7842 通不通
4. **分享前的自检**多一行：「经由 relay.example.com · 延迟 35ms ✓」或者「中继连不上：…」
5. 可以配好几个，iroh 自己挑延迟最低的当 home relay；邀请链接里带的是主持人当时的 home relay

### 6.5 安全边界

- **中继看不到、也改不了内容**：端到端加密，密钥只在两端。它看得到的是：双方的 IP、哪两把公钥在通信、流量大小和时间；能做的坏事是丢包、拖慢
- **访客要知情**：加入时提示「这次经由 relay.example.com 转发（主持人配置的）」，访客的 IP 会被那台机器看到；给访客一个「只直连，不经中继」的选项
- **令牌会随邀请链接发出去**：被邀请的人之后也能用这台中继，靠限速兜着，需要时换令牌。以后要更严，做「主持人签发、带过期时间的一次性令牌」：中继端用 iroh-relay 的 `AccessControl` 接口写一段访问控制（能看到令牌和对方公钥），也就是要编一个自己的中继，v1 不做

### 6.6 版本

- iroh 承诺 1.x 之间线协议不变，用户的中继跟着 1.x 走就行
- Odea 哪天升到 iroh 2，用户自己的中继也得跟着升。应用要能认出「中继版本不对」并直接说出来，不能一直连不上又不说为什么

## 7. 协议：odea/collab/1

### 7.1 为什么不另起炉灶

- 合并算法是个还在出论文的方向（比如 EuroSys 2025 的 Eg-walker），Yjs 是十年打磨出来的；QUIC 是 IETF 标准。这两层自己发明只会更慢、更不稳
- y-protocols 的同步语义（sync step 1 / step 2 / update）本来就和传输无关，直接照搬
- 要自己定的只有很薄的一层：握手、鉴权、成员与权限、通道划分、消息类型、版本规矩
- 参考过 Teamtype（原名 Ethersync，Automerge + iroh + magic-wormhole，FOSDEM 2026 上在推一个跨编辑器的协同编辑协议）：编辑器和守护进程之间走 JSON-RPC、按 Unicode 字符计位置、靠修订号丢弃过期的改动。那是为了让 Neovim、VS Code 能互通；Odea 是一个应用内部，二进制 + UTF-16（和 CodeMirror、Yjs 一致）就够了

### 7.2 通道与消息

一条 iroh 连接（ALPN `odea/collab/1`）上：

| 通道 | 消息 |
|---|---|
| 控制流（双向流，访客先开） | `Hello{协议版本, 特性, 会话 id, proof, 昵称, 颜色}` → `Welcome{成员, 你的权限, 文档标题}` 或 `Reject{原因}`；之后 `Members` / `Permission` / `Kick` / `Bye` |
| 文档流（双向流） | 双方各发一次 `Sync1{状态向量}`，回 `Sync2{对方缺的更新}`，之后一条条推 `Update{字节}`。重连时照这样再来一遍，断线期间各自的改动就补齐了 |
| 光标（QUIC 数据报） | `{成员号, 序号, anchor, head}`，位置是编码过的 `Y.RelativePosition`；只认序号更大的，丢了不重传 |
| 附件（每个文件一条单向流） | `Get{相对路径}` → 字节；访客粘贴图片是 `Put{文件名, 字节}`，主持人走原来的 `vault_attach` 存进「附件/」，回一个相对路径，访客那边再插 `![](…)` |

附件的规矩：**只给这篇正文里引用了的、规范化之后落在仓库「附件/」里的文件**，否则写个 `../../` 就能读到主持人硬盘上的任意文件。正文里的本机绝对路径（`C:\…\a.png`）不给，访客那边显示占位；网络图片访客自己加载。单个文件上限和粘贴附件一样（50MB），只读成员不能 `Put`。

QUIC 的流互不阻塞：附件、快照各走各的流，按键的更新永远不会排在一张大图后面；光标走数据报，连重传都不等。

### 7.3 握手与鉴权

1. 访客按邀请链接里的公钥拨主持人。TLS 层已经双向认证了公钥：访客连到的一定是主持人本人，主持人也知道来的是哪把公钥
2. 访客在控制流上发 `Hello`。`proof = HMAC-SHA256(邀请密钥, export_keying_material("odea-collab-hello", 会话 id, 32))`：证明自己拿着邀请链接，而且这个证明绑在这一条 TLS 会话上，截获了也没法在别的连接上重放
3. 主持人核对 proof → 弹确认（§8.2）→ `Welcome` 或 `Reject`
4. 文档流上 `Sync1` / `Sync2`，然后进入实时阶段
5. 权限只有 `edit` / `read`，主持人随时能改（`Permission`）、踢人（`Kick` + 断开，这次会话里拉黑这把公钥）
6. 「重置邀请链接」换掉邀请密钥：旧链接作废，已经在里面的人不受影响

断线检测：QUIC 每 5 秒保活一次，10 秒左右认出断了，界面显示「重新连接中…」，本地照常编辑；按上次的地址、mDNS、中继（有的话）退避重连。

### 7.4 编码与版本

- 每条流上是长度前缀的帧：`varint 长度 + 1 字节类型 + 内容`。内容是 Yjs 的二进制，或者很小的结构（Rust 侧用 postcard 编码），不用 JSON
- 位置一律 UTF-16，和 CodeMirror、Yjs 一致
- 不兼容的改动换 ALPN（`odea/collab/2`），新版本同时接受新旧两个；兼容的改动在 `Hello` 的特性列表里声明；认不出的消息类型直接忽略
- Yjs 的大版本写进特性列表：双方不一致时直说「对方的 Odea 版本太旧 / 太新」，不硬连

## 8. 加入流程

### 8.1 邀请链接

`odea://join/<票据>`，用户自己发给要邀请的人（任何聊天工具）。

- 票据里有：主持人的公钥（就是地址）、直连候选地址（局域网地址、公网 IPv6、端口映射拿到的公网 IPv4:端口）、中继地址和令牌（主持人配了的话）、会话 id、邀请密钥、默认权限
- base32 编码，没配中继时一百多个字符，带上中继地址和令牌时两三百个。地址部分可以直接用 iroh-tickets 的 `EndpointTicket`，外面包一层会话信息
- 深链接：加 `tauri-plugin-deep-link` 注册 `odea://`；项目里已经有 `tauri-plugin-single-instance`，正在运行的那个实例接住链接
- 链接里有主持人的 IP 地址，只发给要邀请的人。会话结束、或者主持人「重置邀请链接」时作废
- 没装 Odea 的人点不开（没有网页兜底，那要服务器）。分享框复制出去的文字里附一句「用 Odea 打开」和下载地址（GitHub Releases）
- 主持人换了网络（IP 变了）：没配中继时，旧链接里的地址就失效了，分享框里提示重新复制；配了中继时照样能用

### 8.2 主持人确认

- 每个人进来之前，主持人看到「李四 想加入」→ 允许编辑 / 只读 / 拒绝。链接被转发了也不怕
- 可以「记住这个人」（按公钥记在应用数据目录），下次免确认
- 成员列表在分享框里，可以改权限、踢人

### 8.3 局域网「附近」

- 只在主持人开着分享时用 mDNS 广播，广播里只有主持人的昵称和公钥，**不带文档标题** —— 办公室 Wi-Fi 上谁都收得到；标题在主持人允许之后才给
- 访客那边：命令面板「附近的协作…」列出同一网络里正在分享的人，点一下发加入请求，主持人照样要确认
- 没有网也能用（只要在同一个局域网里）

### 8.4 回连链接

主持人连不进来、访客能（有公网 IPv6、端口映射成功，或者访客配了中继）时：访客一键生成回连链接发回给主持人，主持人点开后由主持人往访客那边拨。连上以后角色不变，主持人还是主持人。

### 8.5 分享前自检、连不上时

- **分享之前先查**：主持人点「邀请协作」时就查端口映射成没成、有没有公网 IPv6、中继（配了的话）通不通，一行字说清楚谁能加入：「同一网络和互联网上的人都能加入」或者「现在只有同一网络里的人能加入」，后面跟办法（连同一个 Wi-Fi / 开手机热点 / 配中继）。不让对方点开链接以后干等
- **访客连不上时 3 秒内给结论**：哪几条路试过、卡在哪（「对方的路由器不允许外部连入」「你们不在同一个网络」「这个 Wi-Fi 不允许设备互连」「中继认证被拒」「看得到对方但连不上：多半是对方的防火墙」），下一步怎么做（换同一个 Wi-Fi、开热点、发回连链接、配中继）
- 永远不出现无限转圈

### 8.6 身份

- 每台设备一把 iroh 密钥（ed25519），第一次协作时生成，放系统钥匙串（项目里已经有 `keyring-core`）
- 昵称、颜色在本地设；没有账号

### 8.7 不做短码

「7-紫色-大象」这类短码要一台会合服务器帮两边交换地址（magic-wormhole 的 mailbox），和「不提供服务器」冲突。局域网里也用不着：「附近」列表直接点。

## 9. 体验承诺与延迟预算

### 9.1 连上之后

| 承诺 | 靠什么 |
|---|---|
| 本地打字和不协同时一模一样 | 改动先进本地 CRDT（0.03ms），网络完全不在本地输入的路径上；对方卡了、断了，你这边照样流畅 |
| 别人的字几乎同时出现 | 直连没有中转：同一网络约 1ms，同城 5–20ms，加上本地处理 1–4ms。每个更新立刻发，不攒批 |
| 光标跟手 | 光标走 QUIC 数据报：丢了不重传、只认最新的，不会排在一次大粘贴后面 |
| 点链接后很快看到全文 | 一次握手 + 一次传输。像 `技术方案.md` 这么大的文档，快照压缩后 89KB，同一网络里几十毫秒 |
| 断网不丢字 | 照常编辑，重连后自动合并（双方各写 1000 下，合并 3.7ms）；换网络时 QUIC 在同一条连接里换路 |
| 主持人崩溃、重启后接得上 | 会话状态落盘（§3），重启后「继续上次的协作」，访客自动重连、合并 |
| 主持人走了也不丢 | 访客手里有完整副本，可以接着写；主持人回来自动合并，或者「存一份到我的笔记」 |
| 输入法、撤销、光标都对 | 组字期间攒着再收发；撤销只撤自己的；远端光标按动效规矩画（§4.3） |

### 9.2 别人按一下键，多久出现在你屏幕上

| 环节 | 量级 | 依据 |
|---|---|---|
| 对方按键 → 出更新包 | 0.03ms（p99 0.09ms） | §4.2 |
| 对方 WebView → Rust | 一次 `invoke` | 没量，P10.1 量 |
| 网络单程 | 同一局域网约 1ms（Wi-Fi 会抖到几毫秒）；同城 5–20ms；跨洲 40–100ms 以上。经中继的话再加中继的处理（轻负载下不到 1ms，§6.3）和绕的路 | 物理距离决定，协议省不掉 |
| Rust → 你的 WebView | `Channel`，小于 1KB 走 `eval` | §5.5；没量 |
| 你这边应用更新 | 0.014ms（p99 0.06ms） | §4.2 |
| 你这边 CodeMirror 画这次改动 | 和本地按一次键同价，2.4–3.9ms | 技术方案 §13.2 |
| 你正在组字时 | 先排队，上屏后一起出现 | §4.3 |

真正决定「实时」的只有网络单程延迟。设计上就四条：能直连就直连；不攒批；光标走数据报、大块传输各走各的流；中继尽量离用户近。

## 10. 系统层面的坑

1. **Windows 防火墙**：应用第一次在网络上接受连接时，Windows 会弹窗问是否允许。Odea 是按用户安装的（`installMode: currentUser`），安装包没有管理员权限，没法预先加规则。所以：
   - 端点只在第一次点「开始协作」时才开，弹窗出现在上下文里；弹之前先用一句话说明接下来会问什么
   - 弹窗里「专用 / 公用网络」两个勾决定在哪种网络上放行。当前网络被 Windows 标成「公用」、而用户只放行了「专用」，或者干脆点了拒绝，局域网里的人照样连不进来。检测不到的话，至少在访客那边「看得到但连不上」时，把这条原因列在第一位，并告诉主持人去哪里改
   - 只往外拨的一方（访客）基本不受影响
2. **macOS 15 起的「本地网络」权限**：要在 Info.plist 里声明 `NSLocalNetworkUsageDescription`，少了会悄无声息地连不上（不少应用踩过）。另外现在是 ad-hoc 签名（`signingIdentity: "-"`），这类隐私权限跟签名绑定，每次更新后可能都要重新允许 —— 要做局域网协同，macOS 最好换成正式签名。开着系统防火墙的 Mac 还会问「是否接受传入网络连接」
3. **公共 Wi-Fi 的客户端隔离**：明明在同一个网络却互相看不见。提示「这个网络不允许设备互连，换个网络或者开手机热点」

## 13. 测试与验证

- **收敛模糊测试**（P10.0）：3–5 个副本随机打字、删除、粘贴、撤销；网络模拟器随机延迟 0–300ms、乱序、重复投递、断线重连；每一轮结束，所有副本的 Y.Text 和 CodeMirror 文档逐字相等
- **编辑器边角**（happy-dom，和 `MarkdownEditor.dom.test.ts` 同一类）：组字期间远端改动排队、上屏后一次进来、组字期间不往外发；组字刚结束就来了远端改动，最后那次组字的字一个不丢；撤销只撤自己的；远端事务不触发模板、补全；标题收起跟着映射、别人的改动不替你展开；表格格子编辑时远端改同一张表；平滑光标遇到远端位移直接落位；外部改动和防抖期间没存的改动一起保住
- **性能**（`scripts/perf/perf.mjs` 加场景）：模拟远端每秒 20 次按键 + 光标移动，量本地打字、滚动的帧

### 15.1 和设计不一样、或者设计里没写的

- **回 Sync2 之前先把收件箱里排着的应用掉**（`session.ts` 的 `answerSync`）。同一帧里第二个到的更新包要等下一帧才进 Y.Doc，可网络层收到时已经把它转给了当时连着的人；正好断着的那位这时重连，主持人按 Y.Doc 回的 Sync2 里没有这个包，他就永远缺这几个字。一万轮模糊测试的第 622 轮抓到的。P10.1 里转发在 Rust、回同步在前端，一样会碰上
- **组字放行的判断不只靠 DOM 事件**：会话问编辑器「现在能不能动 Y.Doc」，编辑器答 `view.compositionStarted || 刚收到 compositionend、最后那次改动还没读进来`。CodeMirror 自己的组字状态是准的；DOM 的 compositionend 只用来开始那 50ms 的等
- **远端光标的位置在编辑器里映射**：收到光标消息时用 `Y.RelativePosition` 换算一次，之后正文每改一次在 StateField 里 `mapPos(…, 1)`（贴着后面的字，和 RelativePosition 的默认一致），不用每个按键再派发一次。对方在自己光标处打字，光标消息还没到时光标就已经在新字后面了。光标消息指着还没到的字（数据报比更新包先到）时先留在原处，字到了再落过去
- **名字标签**：对方的光标或选区变了亮 2.5 秒；心跳（同一个位置）不算，不会每 5 秒闪一下。新出现的光标、15 秒没消息的光标整个淡入淡出（400ms）。8 种颜色按 id 算（`peerColor`），不用主色那种蓝，免得和自己的光标混；暗色下光标和选区换浅一档，标签底色不变（白字够深）
- **表格格子写回源码只换变了的那几个字**（`lib/lineDiff.ts` 的 `commonEnds`）：以前整格替换，在 CRDT 里等于删光重插，对方同时在这一格里打的字会被覆盖。格子编辑中源码被别处改了：只有这一格的源码真变了才换字，光标按改动挪（以前是一律跳到末尾），正在组字的那一格不动

## 16. P10.1 实现记录

2026-10-18。网络接上了：Rust `src-tauri/src/collab/`（§11），前端 `collab/net.ts`、`link.ts`、`store.ts`、`mockNet.ts` 和 `components/CollabDialog.tsx`。入口在命令面板：「邀请协作…」（当前笔记）、「加入协作…」，或者直接点 `odea://join/…` 链接。**两台实机还没测**（这一轮没有第二台机器），桌面端也只编译过、没在这一轮里实际启动界面；网络这一半靠同一进程里的真端点测（§16.3）。

### 16.1 两边怎么接

```
前端（WebView）                         Rust                                   网络
CollabSession ─ link.ts ─ net.ts ──collab_send（原始请求体）──▶ Host / Guest ──iroh（QUIC，odea/collab/1）──▶ 对方
               ◀── 二进制 Channel（collab_pipe）─────────────  控制消息 ──▶ collab-event（tauri-specta）
```

- **数据不走 JSON**：前端 → Rust 是原始请求体，Rust → 前端是二进制 Channel；帧 = 1 字节类型 + 2 字节成员号（小端）+ 内容。`collab_send`、`collab_pipe` 不经 tauri-specta（它不认原始请求体），lib.rs 里和 specta 的命令合在一个 handler 里
- **同步由 Rust 提醒、前端算**：Rust 没有 Y.Doc。刚连上某人时 Rust 发「把你的状态向量发给他」（`SyncStart`），某人发来状态向量时 Rust 转给前端「回他缺的」（`SyncRequest`），前端用 `session.stateVector()` / `answerSync()` 回。重连时两边再来一遍，断线期间的改动就补齐了
- **连接上的两条流**：控制流（访客先开，Hello → Welcome / Reject，之后 Members / Permission / Kick / Bye）和文档流（Welcome 之后访客开）。QUIC 的流要先有数据对方才 accept 得到，所以访客开文档流时先发一个空的 `OPEN` 帧（类型 0），主持人忽略
- **星形转发在 Rust**：主持人收到访客的 Update / Sync2 交给前端，同时原样转给其他访客；只读成员的更新直接丢（光标照转）。光标数据报主持人转发时前面加上成员号

### 16.2 和设计不一样、或者设计里没写的

- **邀请链接自己定格式**，没用 iroh-tickets 的 `EndpointTicket`：1 字节版本 + postcard（主持人公钥、直连地址、会话 id、邀请密钥、默认权限），base32 小写，两百来个字。不直接序列化 iroh 的类型：iroh 哪天改了序列化，发出去的链接不能跟着作废；P10.2 带中继换了版本 2（§17.2）。认链接时空白、尖括号、大小写、只粘了票据那一截都认
- **握手证明可选**：从局域网「附近」点进来的没有邀请密钥（加入请求上标「在同一个网络里」，主持人照样要确认）。带了证明却对不上（链接被重置过、不是这次的）直接拒，不打扰主持人
- **允许过的人断线重连不再问**，还是原来的成员号和权限；被移出的这次会话里按公钥拉黑
- **拒绝原因不打内部标签**（`#[serde(tag)]`）：postcard 不自描述，不支持；给前端的 JSON 是 `"declined"` 或 `{ version: { theirs } }`
- **设备密钥**在钥匙串里（`collab-device-key`，第一次协作时生成）；钥匙串用不了就用一把临时的（这次能协作，下次别人认不出是同一台）。名字在 `config.json` 的 `collab_name`，没设过用系统用户名
- **主持人那边的保存**：会话正文一变 400ms 后存（`store.ts` 的 `watchHosted`）。编辑器挂着时它自己的保存也照常，两边写的是同一份，data store 判重只落一次盘；切到别的笔记时别人还在改，靠前一条照存。存的那一刻同时留 `snapshot`，外部改动（`externalRevisions` 变了）按它合进会话（§4.4）。笔记改了名告诉 Rust，之后进来的人看到新标题
- **做客的那一篇**不进 `DocumentSaveTarget`（搜索结果、历史版本也用那个类型），只在文档模型的编辑器目标上多一种 `{ kind: "shared" }`：不保存、不接附件和双链、标题不能改；协作结束以后只读，要接着写就「存一份到我的笔记」
- **yjs 不进主包**：adapter 在主包里要读协作的状态，状态模块里建会话、合并外部改动用到时才动态加载，颜色算法单独一个不依赖 yjs 的 `colors.ts`
- **协作标签不放标题栏**（那里只有窗口按钮，浏览器预览里还不渲染），放在标题上方那一行（路径 / 日期 / 「林夕 的笔记」）的右端；右上角是目录树的标题，第一版放那儿叠在了一起。静态出现，不做动画
- **加入请求**：对话框开着时在对话框里，关着时是底部的提示卡（只淡 opacity），按钮是「允许编辑 / 只读 / 拒绝」
- **浏览器预览**里没有 Rust：`mockNet.ts` 说同一套帧，主持时一会儿以后「Alex 想加入」、允许了真的用一个 Yjs 会话同步并打一句话；加入时模拟连接中 → 等确认 → 进来。界面在浏览器里能走通，也拿它写前端测试
- **macOS** 加了 `Info.plist`（`NSLocalNetworkUsageDescription`、`NSBonjourServices: _odea-collab._udp`）；**Windows** 防火墙只在开始协作、端点起来的那几秒里说一句「勾上专用网络」，检测没做

## 17. P10.2 实现记录

2026-10-18。Rust `collab/` 多了 `reach.rs`（能不能被连进来、端口映射）、`diagnose.rs`（连不上的结论）、`relays.rs`（中继、中继码、测试中继），`ticket.rs` 多了回连链接；前端 `collab/reach.ts`（把事实拼成人话）、`relayStore.ts`、`components/RelayDialog.tsx`，`CollabDialog.tsx` 里多了分享前自检、连不上的面板、回连。入口：命令面板「协作中继…」；点 `odea://back/…`、`odea://relay/…` 链接。用户怎么架中继另写在 [自建中继.md](./自建中继.md)。**真实的互联网环境一格都没测**（连通性矩阵、云主机压测都要别的网络和机器，§17.3 末尾）；Rust 这一半用进程里起的真中继测。

### 17.1 怎么接

- **分享前自检**：主持人一开始协作，Rust 起一个盯梢的任务（`reach::watch_reach`）：端点地址、中继状态、网络报告、端口映射任一变了，就算一份 `Reach` 发给前端（`Control::Reach`，带着这时的邀请链接）。前端 `reach.ts` 拼成「谁能加入」一行 + 几行明细（局域网、公网 IPv6、端口映射、每台中继）。没结果之前行就占好（对话框展开时只量第一帧）。复制过的链接之后变了（端口映射晚到、换了网络），分享框提示再复制一次
- **连不上**：访客 3 秒还没连上就算一份 `Diagnosis` 发出来（`Status::Unreachable`）。不算结束：后台接着拨（拨 10 秒、等 8 秒），结论变了才再报；换了网络会自己连上
- **回连**：访客的端点一直在 accept，只认链接里主持人的公钥。生成回连链接 = 开端口映射、等映射和中继有个结果（最多 5 秒），把自己的地址和一台连上了的中继打包，顺带告诉访客「主持人能不能拨到你」。主持人 `dial_back` 拨过去，拿到的连接照常 `serve`：访客开控制流、发 Hello，主持人照样确认。主持人拨的连接**必须带邀请证明**：回连链接谁都能伪造，不能凭它让陌生人出现在加入请求里。拨通后断了主持人接着往回拨（1→8 秒退避，连续拨不通 10 分钟就停）
- **中继**：地址、名字、指纹记在 `config.json` 的 `collab_relays`，令牌在钥匙串（`collab-relay:<地址>`）。令牌不出 Rust：前端只看得到「带没带令牌」，中继码也在 Rust 里拆、存。主持人的端点用自己配的所有中继，邀请链接里带 iroh 选中的那台（还没选出来就带第一台）；访客的端点用自己配的 + 链接里的（没选「只直连」的话）

### 17.2 和设计不一样、或者设计里没写的

- **端口映射自己驱动**：iroh 1.3 只在配了中继时才去要端口映射（`socket.rs` 里中继表为空就整段跳过，`procure_mapping` 在那之后），而默认配置恰恰没有中继，§5.2 那段示意里的 `portmapper_config` 不管用。所以不开 iroh 的 `portmapper` feature，自己用同一版的 `portmapper` crate 要，拿到的地址 `add_external_addr` 进端点。映射到的「公网」地址是 100.64.x.x 或私有地址时（路由器自己在运营商的 NAT 后面）不加进链接，自检里直说。停止时把映射还给路由器（`deactivate` 之后等 300ms：client 一丢，还映射的那个任务也跟着停了）
- **访客平时不要端口映射**，生成回连链接时才要：不无故去碰路由器
- **邀请链接只发 v2**（v1 后面接一个可选的中继，带地址、令牌、指纹），v1 照样认。P10.1 没发过版，不用两种都发
- **中继码、回连链接**和邀请链接一个路数（1 字节版本 + postcard + base32）。三种链接粘错了地方（回连链接粘进加入框、中继码当邀请链接）直接说是哪一种，不硬解
- **自签名证书**：证书校验换成自己的（`relays.rs` 的 `PinnedVerifier`）：带指纹的主机只认那一张（不看 CA、有效期、主机名，指纹就是全部的信任），其余照常按内置的 CA 根证书，和 iroh 默认一样。指纹表做成能往里加的：主持人按回连链接临时加进来的访客的中继也要认
- **网络报告**用了 iroh 的 `unstable-net-report`：到中继的延迟、UDP 7842 通不通（有 QAD 探测的结果就是通）。它不受语义化版本保护，`Cargo.toml` 里把 iroh 锁在 `~1.3`，升 iroh 时先看 `Endpoint::net_report` 变没变
- **访客的结论怎么猜**（`diagnose::conclude`，纯函数）：没网 → 中继（令牌被拒 / 连不上中继 / 中继连上了却找不到主持人）→ 同一个网络（主持人的局域网地址在我的网段里，或者 mDNS 看到了他）却连不进去 → 主持人只有公网 IPv6、我没有 → 主持人有公网地址却连不进去 → 不在同一个网络。中继还在连的时候先按直连的情况说。网段用 netwatch 读网卡（带前缀长度）
- **看得到却连不上**：P10.1 的遗留在这里落下：mDNS 看到了主持人还连不进去，结论是防火墙（Windows 把网络标成了「公用」），第一步是在「允许应用通过防火墙」里给 Odea 勾上「公用」。主持人那边的检测还是没做
- **结束原因**：`EndReason::Unreachable` 没了（连不上不再是结束），换成 `Dropped`（还没进去，主持人那边就断开了）
- **直连还是中继**：访客盯着连接选中的那条路（`paths_stream`），变了发 `Control::Route`；一直经中继的话状态行写「经由中继转发」
- **测试中继**单独起一个只连那一台的端点（Windows 上建端点也要两三秒），最多等 8 秒；「名字」可以不填，显示主机名
- **中继版本不对**（§6.6）没有专门认：现在 Odea 和中继都在 iroh 1.x 上，线协议不变；真碰上了，iroh 给的错误原文放在「连不上中继」后面

## 18. P10.1、P10.2 遗留补全

2026-10-18。§16、§17 里「没做」的那几样补上了：「附近」列表、会话状态落盘、附件按需传（含访客那边双链按「不存在」画）、慢的访客合包、主持人那边的 Windows 防火墙检测、界面上看得到设备公钥、中继压测程序进了仓库。Rust 新增 `collab/nearby.rs`、`record.rs`、`queue.rs`、`firewall.rs`，附件流在 `host.rs` / `guest.rs`，读写仓库在 `commands.rs`；前端新增 `collab/attachments.ts`，`store.ts`、`CollabDialog.tsx`、`RelayDialog.tsx`、`DocumentView.tsx` 跟着改。**两台实机、真实网络（连通性矩阵）、云主机上的中继压测还是没做**：这台机器上没有别的机器和网络。

### 18.1 怎么接

- **附近**（§8.3）：加入对话框开着时，Rust 起一个只听不广播的端点订阅 mDNS（`Nearby`），只认带昵称的（只有主持人广播昵称），列表变了整张报给前端（`Control::Nearby`）。点一个：用他的公钥和 mDNS 给的地址拼一个不带会话 id 和邀请密钥的 `Invite`，访客 `nearby = true`：Hello 里会话 id 全 0、不带证明。主持人认出这种 Hello（全 0、没证明、不是回连拨过去的），照样问，请求上标「在同一个网络里」
- **落盘**（§3，`record.rs`）：应用数据目录的 `collab/` 下 `host.json` / `guest.json` + `host.ydoc` / `guest.ydoc`。主持人的记录 Host 自己写（会话 id、邀请密钥、默认权限、标题、是哪篇笔记、允许过谁、拉黑了谁、端口），一有变化就整份重写；访客的在命令层写（邀请链接或「附近」拼的那个、只直连没有、标题、主持人叫什么）。Y.Doc 的状态前端交（`collab_send` 的 `PIPE_SAVE`，原始字节），停下两秒后交一次，主持人每次存盘时连同那一刻的状态再交一次。正常结束（停止协作、离开、被拒、被移出、主持人停了、关窗口）就删掉
- **继续上次的协作**：重启后 `collab_resume_info` 有东西，底部出一张卡。主持人「继续协作」：读回状态建会话（`initialState`），磁盘上的正文和它不一样（崩溃前最后几百毫秒存下去的、别的程序改的）就按外部改动合进来（§4.4，基准就是这份状态 —— 它和最后一次存盘是同一刻取的），再用记录起端点：同一个会话 id、邀请密钥、端口。访客那边一直在退避重连，旧链接里的地址又通了，允许过的不再问，接上、补齐。访客「重新加入」：用落盘的状态建会话再加入，断线期间自己写的同步时给主持人
- **附件**（§7.2）：一个请求一条双向流（访客开），帧类型 `ATTACH_GET` / `ATTACH_PUT` → `ATTACH_DATA` / `ATTACH_LINK` / `ATTACH_ERR`，附件流的单帧上限 50MB（控制流、文档流还是 32MB）。主持人的 Host 只把请求变成事件（`Event::AttachGet` / `AttachPut`），命令层查、读、存，再 `answer_attachment`。查的是两道：路径在这篇正文引用的表里（前端正文一变就算一份：正文里相对路径的图片 → 按这篇所在的文件夹算出的仓库路径），规范化之后落在仓库的「附件/」里（canonicalize 之后再比一次，符号链接绕不出去）。访客粘贴的：主持人走 `Vault::attach` 存进「附件」，回从那篇引用它的路径；只读的人传不了，主持人那边连事件都没有
- **访客那边的图片**：编辑器的图片基准（`imageBaseDir`）除了文件夹还能是一个解析器（`ImageResolver`）。做客的那一篇用 `GuestImages`：正文一变扫一遍相对路径的图片，没有的向主持人要，缓存在 `collab/cache/`（文件名按路径算、扩展名留着：asset 协议按扩展名放行），要到了换一个新的解析器，编辑器按引用比较、只重画那几张。还没要到的、主持人电脑上的绝对路径显示占位；网络图片照常。双链：`linksMissing` 让做客那一篇的 `[[双链]]` 一律按「不存在」画
- **慢的访客**（§5.4，`queue.rs`）：主持人发给每位访客的文档流自己排队。排着的超过 256 帧或者 Update 超过 1MB，就把排着的 Update / Sync2 整个丢掉，换成一个 `RESYNC` 帧；访客收到就重发一次 Sync1，主持人的前端照它回一份 Sync2，正好是他缺的全部。等他 Sync1 的这段时间新来的更新也不排了（反正那份 Sync2 里都有）。设计里说的是 `Y.mergeUpdates` 合包，Rust 侧没有 Y.Doc 合不了，这样做效果一样：不排长队，一包补齐
- **Windows 防火墙**（§10，`firewall.rs`）：开始协作后头一分钟每 5 秒、之后每分钟读一次：当前生效的是哪种网络（`INetFwPolicy2::CurrentProfileTypes`）、这种网络上防火墙开没开、给这个 exe 的入站 UDP 规则（有「阻止」就是挡着、只有「允许」就是放行、都没有就是还没问过）。结果进 `Reach.firewall`：自检里多一行「防火墙」，挡着时那一句变成「现在谁都连不进来：Windows 防火墙在这个「公用」网络上挡着 Odea」并给改法。访客生成回连链接时也查一次（主持人拨过来是入站）
- **设备公钥**：「协作中继…」底下显示、能复制（中继的 `access.allowlist` 要填它，十六进制，iroh-relay 认）

### 18.2 和设计不一样、或者设计里没写的

- **协议的特性列表多了 `resync`、`attach`**（§7.4）：缺了的直接按版本不对拒。P10.x 都没发过版，不用兼容
- **主持人继续协作时绑回原来的端口**：不然访客手里链接里的地址作废，只有同一个网络里 mDNS 还找得到。IPv6 的那个绑不上不算错；端口被占了就换随机的（这时只能靠 mDNS、中继，或者重新发链接）
- **关窗口也算正常结束**（`win_force_close` 里先收掉协作）：告诉别人、删掉记录，重启后不问「继续上次的协作」。只有崩溃、强退才会留下
- **落盘只在停下两秒后**，不是设计里说的「每隔几秒」：打字时一直推后，停下才写（197KB 的文档导出约 4ms）。崩了最多丢这两秒，对方那里有的同步时还会补回来
- **访客要不到图片会再试**：主持人那边的引用表比正文晚一点点（200ms 防抖），刚插进来的图片第一次可能被拒；1.5 秒后再试，最多三次，断了又连上从头算
- **附近的列表空着时先说「正在找…」**：起端点两三秒、mDNS 再要一会儿，前 5 秒空着算还在找

## 19. 第二轮：补上没做的、两个实例实测

2026-10-18。§15–§18 写了「没做」的几样补上了，并在同一台电脑上开两个实例真的连起来测了一遍（两台实机、真实网络、云主机还是没有）。

### 19.1 补上的

- **「存一份到我的笔记」带上图片**（§3）：访客要来的图片缓存成 `collab/cache/<路径的哈希>/<正文里写的文件名>`（`record::cached_name`：解开 %xx、按附件的规矩清洗），存一份时按路径交给 `vault_attach_path` 存进自己的「附件」，正文里的路径换成它回的（`attachments.ts` 的 `copyImages`、`rewriteImageRefs`：只换图片语法里地址那一段，alt、标题里一样的字不动）。还没要到的留着原来的路径，提示一句有几张没拿到。浏览器预览里要来的是 data: 地址，按名字和内容存。前端没法直接 fetch 缓存的图片：CSP 的 `connect-src` 不放行 asset 地址，所以走路径
- **记住这个人**（§8.2）：成员表里每位访客旁边一个「记住」，记在 `config.json` 的 `collab_trusted`（公钥、名字、给不给改）。记住的人拿着这次的链接、或者从「附近」进来不问，权限照记住的；链接、证明照样要对（记住的是人，不是让旧链接一直有效）。改权限跟着改，移出就忘掉。不在场的列在成员表下面，能「忘掉」。忘掉连同这次会话里的「允许过、重连不问」一起清掉：不然主持人刚点了忘掉，对方离开再回来又没问就进来了
- **版本对不上说清是谁的旧**（§7.4）：主持人回的 `Reject { Version { theirs } }` 是他的协议版本，访客比一下：比自己低是主持人旧，一样高还被拒是自己缺了特性、自己旧（`EndReason::Outdated { hostOlder }`）。主持人那边也知道一声（`Control::JoinOutdated`），对话框里一行「X 想加入，可是 X 的 Odea 比你的旧」，不然对方说连不上、他这边什么都没看到
- **中继的版本不对**（§6.6）：iroh-relay 不认 Odea 说的协议版本时回 400、正文里说它支持哪几版；或者回一个认不出的版本头。认这两种错误（`relays::upgrade_refused`），自检那一行、访客的结论、「测试」都直说。「测试」时再发一次升级请求读回 400 的原话（`probe_upgrade`，不带令牌），分清是版本（带上它认的版本）还是前面的反向代理没转发 WebSocket（原话照给）
- **格子编辑中表的上面插了 / 删了一行（列）**（§15.1 的已知边角）：`fill` 按位置复用 `<tr>` / `<td>`，先比一下前后两张表只差哪一行（列）（`shiftedAt`），DOM 里在同一个位置插 / 删，正在编辑的格子跟着自己那一行（列）走。插 / 删的落在一串一模一样的行里时哪一处都对，挑一处不挪正在编辑的那个；同时还改了别处的不认，照旧按位置
- **断线时协作标签不再说「2 人在编辑」**：访客重连中显示「重新连接中…」
- **设了 `ODEA_DATA_DIR` 时设备密钥放在那个目录**（`collab/device-key`），不进系统钥匙串：钥匙串里只有一把，同一台电脑上开两个实例就成了同一个 iroh 身份，自己连不上自己；也守住「换了数据目录不碰真实数据」（boot.rs）

### 19.3 踩到的坑

- **钥匙串里的设备密钥只有一把**：两个实例用同一把就是同一个 iroh 身份。换了数据目录时改放在数据目录（19.1）
- **iroh 给的中继错误要带起因**：`last_error()` 的 `to_string()` 只有一句「Failed to connect to relay server」，`{:#}` 才把原因连成一行（`relays::error_text`）。版本不对的实测原文是 WebSocket 库先报的「expected HTTP 101 Switching Protocols, got status code 400」，不是照 iroh 源码猜的「Unexpected status during upgrade: 400」—— 两种都认
- **测「以后的中继」的假服务器 `/ping` 要回 200**：网络报告靠它挑 home relay，`/ping` 也回 400 的话 iroh 根本不去连它，状态里什么错误都没有
- **会话中途「忘掉」**：一开始只删了记住的表，这次会话里「允许过」的那张表还在，对方离开再回来照样不问（两个实例上点出来的）
- **CodeMirror 6.43 把 view 挂在 `.cm-content` 的 `cmTile` 上**（以前是 `cmView`）：脚本读整篇正文用它
- **受控的 input 用 JS 设值不算数**：React 不认，脚本得聚焦以后用 DevTools 的 `Input.insertText` 真的打进去
- Windows PowerShell 5.1 读不带 BOM 的脚本按 ANSI 解，里面的中文乱码、引号配不上：给它的脚本只写 ASCII
- `tauri build` 把前端打进 exe（17.1MB）；§16.3、§17.3 的体积是 `cargo build --release`、没打前端（13.5MB），两种数别混着比

**测出来的问题（都修了）**：
- **一句话后面一直按 k，前一行被两端对齐拉开**：和协作无关，单人打字一样（`排版规范.md` §2、`editor/longRuns.ts`）
- **协作中改名字别人看不到**：另一台在主持时改了名，自己的成员表、主力那边还是系统用户名。协议补了一个 `NAME` 控制帧（访客 → 主持人，旧版本认不出直接忽略），主持人改名直接换掉成员表里的、广播，「附近」广播的昵称也换（`Host::set_name`、`Guest::set_name`）
- 「附近」空着时的说明加上「只看得到同一个网段里的人：学校、公司的大网络常分成好多段」

### 19.5 配了中继再测（2026-10-19，用户手动测）

用户照 [自建中继.md](./自建中继.md) 在一台公网服务器上架了官方 iroh-relay（在 Odea 里叫「GRED」），两台都添加了。主力主持时自检：「同一网络和互联网上的人都能加入（经由 GRED）」，中继一行「GRED · 12ms」，防火墙放行。第 4 轮那种「另一台在别的网络、两边都在 NAT 后面」的情况连上了，打字「延迟几乎感觉不到」。这是 §5.3 表里最后一行（两边都连不进来）靠自配中继解决的实例。

**测出来的问题（修了）**：自检的「公网 IPv4」一行列出了 `125.84.158.172` —— 这是中继看到的 NAT 出口地址（QAD），不在网卡上，外面连不进来。它被当成「网卡上直接就是公网 IPv4」：现在中继连着，结论按中继说，看不出错；中继一断，结论就会变成「这台电脑有公网地址、互联网上的人都能加入」。iroh 1.3 内部分得清地址来源（`DirectAddrType::Local / Qad / Portmapped`），但端点上没有公开取它的接口，所以自检自己读网卡（`diagnose::my_networks`，后台读、地址变了再读），只有在网卡上的公网 IPv4 才算；网卡没读出来之前算「还在查」（开头多两秒「在查」）。访客生成回连链接时用加入时已经读好的网卡地址。

**还是没验的**：中继压测（`load.exe` 从主力打到这台服务器，或者照附录 A.3 放在同一个机房）；两台真机在同一个局域网；macOS、Linux；在别的程序里点 `odea://` 冷启动。

## 20. P10.3 设计：换 Loro、共享仓库、访客转发、组字

> 共享仓库（§20.3–§20.8、§21.5、§21.6）2026-10-22 起退役，改成团队仓库：git 管持久、会话管实时（§22）。这几节留着当记录。

2026-10-21 定稿。P10.0–P10.2 是会话式：一篇笔记临时请人进来，CRDT 只在会话期间存在（§3）。§2.3 当初「v1 不做」的持久共享、共享文件夹、历史版本，加上 §12 里 P10.3 那一行的另外两件（访客之间转发、组字时不碰那一行的改动立刻进来），这一节一起定。

条件变了的地方：
- **逻辑目录**（[仓库与启动器.md](./仓库与启动器.md) §7）：树在清单里，和文件放在哪、叫什么无关。两台设备上同一篇的文件名可以不一样，挪文件夹不碰文件 —— 共享「文件夹」最难的那一半（文件路径怎么对上）没了
- **一个窗口一个仓库**（同上 §4）：共享的单位可以直接是一个仓库，不用在私人仓库里划出一块
- **外部改动进 CRDT**（§4.4）已经验证过：把别的程序当成从上次写盘处分叉出去的协作者。持久共享时 .md 和 CRDT 之间的对账就是这一条
- **自配中继**（§6、§19.5）实测能用：成员换了网络也找得到

### 20.1 结论

| 问题 | 定了什么 | 为什么 |
|---|---|---|
| CRDT | **换成 Loro**（前端 `loro-crdt`，Rust `loro`，同一个版本锁死），会话式也换 | 见 §20.2。P10 还没发过版，现在换只花开发时间，不用兼容旧格式 |
| 持久共享的单位 | **共享仓库**：整个仓库共享，必须是逻辑目录。「共享文件夹」就是它；只共享一篇 = 一个只放一篇的共享仓库 | 逻辑目录的树和文件位置无关；私人仓库里划一块共享出去，双链、附件、搜索都要分「这篇别人看得见吗」 |
| 真相 | 每台设备上的 .md 仍是**这台设备**的真相：别的编辑器、资源管理器照常用。设备之间靠 CRDT 合并 | 「文件是真相」不变；CRDT 是合并的手段，不是存储（技术方案 §2.2 否掉的是「CRDT 当存储」） |
| CRDT 存在哪 | **Rust**：仓库里的 `.odea/share/`，每篇一个 Loro 文档，外加一个仓库文档（树、每篇的元数据、附件清单） | 文档不用开着也能在后台合并、写盘；跟着仓库走（搬家、备份带着） |
| 前端 | 正在编辑的那一篇，WebView 里有一份副本，和 Rust 那份像两个对等端一样互发更新 | 编辑器绑定要和 CRDT 在同一个线程（§5.5），这一条不变 |
| 写盘 | 共享仓库里的文档**只由 Rust 写**，编辑器的自动保存不写 | 一个写入方：两条路写同一个文件，后到的旧内容会盖掉新的 |
| 拓扑 | **网状**：任意两位成员连上就互相补齐，收下的改动转给自己连着的其他成员 | 没有谁必须一直在线；会话式的星形是因为主持人那台是唯一真相 |
| 权限 | 管理员 / 可编辑 / 只读。成员表由管理员签名，谁都能转交；改动只收「连接对面是可编辑成员」发来的 | 连接本身按公钥认证（§7.3），只读的人发来的改动在第一跳就丢掉；可编辑的人转发别人的改动，等于他自己能写的 |
| 找到对方 | 每位成员上次的地址和中继记在本机；局域网 mDNS；成员之间互相告诉对方自己现在在哪 | 不要会合服务器。真的跨网络、都在 NAT 后面，还是要中继（§5.3 那一条不变），界面上照样说清楚 |
| 和 git 同步 | 共享仓库**不开** git 同步；自己的几台设备都当成员加进来 | 两条同步路线会把同一次改动合两遍：git 先送到的那份被当成外部改动、按本机重新打一遍，CRDT 后送到原来那份，正文重复 |
| 附件 | 不进 CRDT：仓库文档里一张清单（路径 → 哈希、大小、谁什么时候改的，后改的赢），按哈希向连着的成员要 | 二进制合并没有意义；上限照旧 50MB |
| 历史版本 | Loro 自带：每次改动带设备和时间。按「同一台设备、停顿 5 分钟以内」并成一版；看当时的全文、和现在比、恢复（恢复是一次新的改动，别人那里也恢复） | 不用关 GC、不用自己存快照 |
| 会话式 | 照旧，换成 Loro；协议升 `odea/collab/2` | 临时请人进来改一篇的场景还在 |
| 访客之间转发 | 已经在会话里的访客可以替连不上主持人的人转发：「转发链接」、局域网「附近」。主持人照样确认、照样管权限 | Keet 的思路；不靠服务器能多连上一部分 |
| 组字 | 不碰组字那一行的远端改动立刻进来；碰到的照旧排队 | 现在组字的人要等上屏才看到别人的字（§4.3「代价」） |

### 20.2 Loro 还是 yrs（2026-10-21 重新查、实测）

P10.0 选 Yjs 是因为会话式：CRDT 只在会话期间存在，Yjs 的包最小、合并最快（§4.1）。持久共享之后要的东西不一样了：

| | Yjs 前端 + yrs 后端 | Loro 前后端 |
|---|---|---|
| 两边是不是一份代码 | 不是：yrs 是 Yjs 的 Rust 移植，靠二进制格式兼容。2026-07 的 yrs 0.27.3 还在修「位置 0 插入时右边邻居」「粘性位置的方向」这类和 Yjs 不一致的地方 | 是：`loro-crdt` 就是 Rust 核心编成的 wasm。会话式里两边不一致只影响这一次会话；持久共享里分叉了就永远分叉 |
| 版本 | yrs 0.28.0（2026-09-17），Yjs 13.6.33，v14 还在 beta | loro 1.16.2 / loro-crdt 1.16.4（2026-09），1.x 以来格式稳定 |
| 历史版本 | 要关掉 GC（所有副本都得关），自己存快照、自己做 diff | 自带：改动带设备、时间戳、说明；`forkAt` 回到任一版，`diff` 两版之间的差别，`revertTo` 恢复（实测都对，见下） |
| 老历史太大 | 关了 GC 就一直长 | 浅快照：只留某一版之后的历史。一篇改了三万次（5.5 万字），完整快照 363KB、浅快照 132KB，载入完整快照 0.7ms |
| 树 | 自己用 Map 记节点，成环、重复靠我们的理顺规则（tree.rs 已有） | 自带可移动树，两边互相挪进对方实测不成环。共享仓库还是用 Map 记节点（和 `.odea/tree` 一行对一行，§20.4），这一条是加分 |
| 事件 | 同步派发 | 1.8 起同步派发：commit、import 之后当场收到（实测） |
| 每次按键的包 | 20 字节 | 90 字节（实测）：QUIC 一个包的开销比它大，无所谓 |
| 同一处两人各打 200 字 | 合并 4.3ms | 17.8ms（§4.2）：一帧以内，罕见 |
| 前端体积 | 29KB（gzip） | wasm 3.4MB（gzip 1.1MB）：只在用到协作、打开共享仓库时才加载 |
| Rust 体积 | 最小程序 95KB → 349KB（+0.26MB） | 95KB → 1.77MB（+1.7MB）。0.2.0 的 Windows 安装包 6.2MB，加上这两样估计 9–10MB，离 20MB 的线还远 |
| 光标 | RelativePosition | Cursor，编码 12 字节，贴着字走（实测） |
| 位置单位 | UTF-16 | JS 里是 UTF-16（实测 `a😀b` 在 3 插入落在 emoji 后面），Rust 里有 `*_utf16` |

loro.js（Loro 官方的纯 TypeScript 实现，0.3.0，2026-09-30）能省掉 wasm，但 README 自己写着还是实验性质、字节不规范，不用。

实测脚本当时放在临时目录，和 §4.2 那一份一样没进仓库；方法：两个文档互发增量、各打 200 字后按版本向量补齐、带时间戳的提交列表、`forkAt` / `diff` / `revertTo`、光标在前面插字后的位置、树上互相挪、三万次随机改动后的快照大小。

### 20.3 共享仓库的样子

```
仓库/
├─ 欢迎使用 Odea.md, 交易学习.md …   每台设备上的文件名可以不一样（同名时各自加「 2」）
├─ 附件/
└─ .odea/
   ├─ vault.json   kind: "logical"，share: { id }（这个仓库是哪个共享的）
   ├─ tree         清单：本机这一份，从仓库文档里写出来（§20.4）
   └─ share/
      ├─ share.json    共享 id、我是哪台设备、成员表（带签名）、每位成员上次在哪
      ├─ vault.loro    仓库文档：树、每篇的元数据、附件清单、peer → 设备
      └─ docs/<id>.loro 每篇一个：正文
```

- **每篇的 id**：笔记是属性块里的 id（共享之前，没写 id 的笔记写上 —— 共享时改一次文件，确认框里说清楚）；某一天是 `day-2026-10-21`，目标是 `goal-week-2026-10-19`（周期决定，每台设备都一样）
- **正文**：Loro 文档里一个 Text 叫 `body`，内容和编辑器里一样（不含应用自己管的属性块）。Rust 写盘时把属性块（id、和文件名不一样时的标题）拼回去
- **元数据**（仓库文档的 `docs` 表，每篇一项，整项后改的赢）：种类、标题、置顶、归档（和类别）、建的时间、删了没有。改标题 = 本机给文件改名（和现在改标题一样走 `rewrite_note_meta`）
- **删了**：元数据里标「删了」，各设备挪进自己的回收站；撤销 = 标回来。正文的 Loro 文档留着（撤销、历史要用）
- **落盘**：Loro 文档停手 2 秒导出一次快照（197KB 的文档 4ms），不写每一包

### 20.4 树

逻辑目录的清单（`.odea/tree`）一行一个节点，同步时本来就是按节点合并（[仓库与启动器.md](./仓库与启动器.md) §7.4）。共享仓库里照搬：仓库文档里一张 `tree` 表，节点 id → 那一行的内容（父节点、排序键、内容），**整行后改的赢**；读出来照旧过一遍理顺（成环的挪到根上、同一篇两处留一处、重名加序号）——理顺只看表里的内容，每台设备算出来的一样。

- 本机改树（建文件夹、挪、排序）：改清单的同时写进表
- 收到别人改的：从表重新写出本机的清单，前端刷新
- 共享仓库里一律按 id 引用笔记（共享时写上了 id），没有按路径引用的那种
- 没用 Loro 自带的可移动树：要给每个节点另起 id、排序键另一套，和清单对不上；我们的理顺规则在 P11.3 里已经测过并发挪动

### 20.5 .md、Rust 那份、前端那份怎么对上

```
别的程序 ──改文件──▶ .md ──(文件监听)──▶ Rust：和「上次写盘的正文」比，差异打成本机的改动 ──▶ 发给成员
成员 ──改动──▶ Rust：import ──▶ 停手 400ms 写 .md（只写有变化的那几篇）
             │
             └──▶ 这一篇正开着：转给前端那份 ──▶ 编辑器（和会话式一样的绑定）
编辑器 ──改动──▶ 前端那份 ──▶ Rust（import）──▶ 发给成员、停手 400ms 写 .md
```

- **外部改动**：Rust 记着每篇上次写盘的正文和那一刻的版本（frontiers）。文件监听报来一篇变了：内容和上次写的一样就是自己写的（现在就靠指纹认，§5.3）；不一样就从那一版 `forkAt` 出一份、换一个 peer，把「上次写的 → 磁盘上的」差异打上去（先逐行、改了的段里再逐字，和 `external.ts` 同一套），导出增量 import 回来。磁盘上的改动和这期间别人的改动按 CRDT 合并
- **前端那份**：打开一篇共享的笔记时，前端向 Rust 要这一篇的快照，建 Loro 文档，挂上绑定；之后两边互发增量。关掉就扔。组字期间的排队、放行和会话式完全一样（就是同一个会话类，网络换成 Rust 那份）
- **peer id**：Loro 要求同一个 peer id 不能同时在两个地方用。Rust 那份用一个固定的（存在 `share.json`），前端每次打开随机一个；正文文档里记一张 peer → 设备公钥的表，历史版本按它认人

### 20.6 成员和权限

- **成员表**：`{ 版本号, 成员[设备公钥, 名字, 角色], 签名者, 签名 }`。只认比手里新、而且签名者在手里那份表里是管理员的。两位管理员同时改，版本号一样的按签名字节大小挑一个（罕见，后改的那位再改一次就是了）
- **角色**：管理员（改成员表、邀请）、可编辑、只读。建共享的那台是管理员；自己的别的设备一般也给管理员
- **改动的权限**：连接建立时双方都查对面在不在成员表里、什么角色。正文、仓库文档的改动只收可编辑以上的成员发来的；只读成员发来的直接丢（他那边界面本来也是只读）。可编辑的成员转发别人的改动不再查 —— 他自己本来就能写任何东西
- **移出**：新的成员表传开以后，大家不再接他的连接。他手里已有的副本收不回来，之前写的也留着（CRDT 不能撤回别人的历史），界面上说清楚
- **身份**：设备密钥照旧（§8.6）。成员表里是设备，名字是人起的；同一个人的几台设备名字一样，历史里显示名字

### 20.7 同步协议 `odea/share/1`

一条 iroh 连接，ALPN `odea/share/1`，帧格式和 `odea/collab/2` 一样（§7.4）。

1. **握手**：双方各发 `Hello{共享 id, 成员表版本}`。不是同一个共享、对面不在我的成员表里：断开。成员表版本不一样：新的一方发 `Members{整张表}`
2. **对账**：双方各发 `Summary{ 每篇：id、版本向量 }`（两千篇约 40KB）。收到以后，对方缺的每一篇导出增量发 `Update{id, 字节}`。对方没有的整篇发
3. **实时**：之后本机每有一篇变了（本机编辑、外部改动、别人转来的），发给所有连着的可编辑以上的成员 —— 收到的改动 import 进来版本有变化才转发，转过的不会转回来
4. **附件**：仓库文档里清单变了、本机没有那个哈希的文件：向连着的成员发 `Want{哈希}`，回 `Blob{哈希, 字节}`（一个请求一条流，和 §7.2 一样）。对上哈希才写盘
5. **光标**：两边都开着同一篇时，光标数据报前面加上文档 id，其余和会话式一样

连接靠的是：成员表里每位成员上次在哪（直连地址、中继）、局域网 mDNS（广播里只有共享 id 的哈希和设备公钥）。仓库窗口开着就在后台连，和 git 同步一样 —— 应用关了就不同步。没有谁一直开着的话，两个人不同时在线就合不上：界面上说清楚，建议放一台常开的设备当成员。

### 20.8 加入

- **邀请链接** `odea://share/<票据>`：共享 id、邀请人的公钥和地址（含中继）、邀请密钥、默认角色、仓库名。管理员在「共享…」对话框里复制
- **加入**：启动器「加入共享仓库」或者点链接 → 选放在哪（新建一个空文件夹）→ 拨邀请人 → `Hello` 带证明（和会话式一样绑在 TLS 会话上）→ 邀请人那边弹请求卡（允许编辑 / 只读 / 拒绝）→ 签一张新的成员表发过来 → 对账拉下全部 → 写出文件、清单 → 打开这个仓库窗口
- **共享一个已有的仓库**：仓库窗口命令面板「共享这个仓库…」。先查：是逻辑目录（不是就问要不要转）、没开 git 同步（开着就问要不要停）、不在网盘里。确认后给没写 id 的笔记写上 id，把每篇读进 Loro（算作这台设备写的），写 `share.json`

### 20.9 访客之间转发（会话式）

主持人连不上、而已经在里面的访客 B 连得上的人 C（比如 C 和 B 在同一个局域网，主持人只有 B 够得着的公网 IPv6）：

- B 是一个「小主持人」：接 C 的连接，C 的 `Hello` 原样转给主持人（`Forward`，带上 C 的公钥、名字、证明是 B 核过的），主持人照样弹确认、记成员号和权限
- 之后 B 在 C 和主持人之间原样转文档流的帧（Update、Sync1 / Sync2、Resync）和光标数据报。只读照样由主持人丢
- C 怎么知道 B：B 的协作对话框里「转发链接」（`odea://join/` 的 v3，指着 B，带着原来的会话 id 和邀请密钥）；局域网里 B 也在 mDNS 上广播，C 的「附近」里显示「经由 B 加入」
- B 走了：C 断线，照旧退避重连（先试主持人、再试别的转发）

### 20.10 组字时不碰那一行的改动立刻进来

§4.3 的做法：组字期间远端改动连 Loro 文档都不碰，整个排队。改成：

1. 组字期间远端改动到了：先让 CodeMirror 把还没读进来的 DOM 改动读完（`view.observer.flush()`，读进来的组字改动照常写进 CRDT，只是不发）
2. 再 import。得到的变化如果不碰组字所在的那一行：马上派发事务（CodeMirror 在改动不碰组字范围时保得住组字）
3. 碰到了：这次的变化先不派发，记成一串待派发的改动（`ChangeSet`）。之后本地的组字改动写进 CRDT 时，先映射过这串改动（OT 的那一步，CodeMirror 的 `ChangeSet.map`）；组字结束一起派发

真 Chrome 里验（`scripts/perf/collab-ime.mjs` 加一种：远端在别的行打字时，组字的人当场看得到）。

### 21.4 P10.3.2 访客转发

- 协议：`Forward{C 的公钥, 哪种流, C 的 Hello, B 核过的证明}` 帧开头的流；C 的数据报 B 前面加 `FF FF + 成员号` 再转（光标第一个字节是版本号，不会是 FF）
- 主持人：成员的路由是 `Route::Direct(连接)` 或 `Route::Via{转发他的那位, 连接}`，权限上限是转发人的（只读的访客不能替人拿到可编辑）；转发人走了，经他的人跟着断
- 访客 B：连着主持人时才接别人的连接；先核 C 的证明（拿着邀请链接），再替他开流、原样搬字节
- 界面：做客时协作对话框里「转发链接」（指着 B、带原来的会话 id 和邀请密钥），能不能被连进来的说法和回连链接一样；主持人那边加入请求写「经由 B 转发」，成员列表「· 经由 B」
- **没做**：§20.9 的「局域网里 B 也在 mDNS 上广播、C 的附近里显示经由 B」

### 21.5 P10.3.3 共享仓库

#### 和设计不一样、或者设计里没写的

- **每个共享仓库一个端点、一把自己的设备密钥**（应用数据目录 `share/<共享 id>.key`，不在仓库里：仓库会被拷走、放进网盘）。不和会话式协作共用一把：同一把密钥起两个端点，中继那边会互相顶掉。成员表里的「设备」就是「这台设备在这个共享里」
- **Rust 那份的 peer 每次打开随机一个**（设计写的是固定、存在 share.json）：崩溃前没落盘的改动已经发出去了的话，重启后再用同一个 peer 会和别人手里的改动撞号。前端打开一篇时也由 Rust 另给一个，都记进 peers 表
- **mDNS 广播里只有公钥**（服务名 `odea-share`），不带共享 id 的哈希：按公钥拨，局域网里自然找得到
- **邀请链接里带着邀请人的仓库摆法**（日程开没开、`folders`）：加入的人新建的仓库照这个摆。笔记放在哪要一样 —— 正文里图片的相对路径是从笔记所在的文件夹算的
- **清单**：仓库文档的 `tree` 表一个节点一行（`父节点 排序键 种类 内容`）。本机改了哪几行按「上次对齐时本机的样子」（tree_base）比，所以每台设备自己理顺出来的变化（成环挪到根上、去重）不会被当成本机改的发出去；放笔记的那一行没了、笔记在 CRDT 里还在（别人刚建的笔记还没写下来，理顺时当成找不到去掉了）也不发。写清单前先写篇，免得理顺时把还没写下来的笔记当成找不到
- **笔记不见了先等两秒**：别的程序改名是先删后建，等一会儿新的出来了就不算删
- **打开时等索引读全**（`indexed_all`）再对第一遍账：没读到的笔记会被当成删了。对账时以前写过盘、现在不见了的笔记算删了（应用关着的时候删的），没写过盘的是别人的、还没写下来
- **编辑器绑着副本的那一篇，正文只由 Rust 写**：前端的 Loro 副本开着这一篇时，编辑器存盘时交来的正文 Rust 不用（`note_update` 只改标题、正文读磁盘上的；`save_day` 只改标题；`save_goal` 不写）—— 那份正文可能落后于 Rust 已经合进来的别人的改动。副本没开着的照常写、再当成磁盘上的改动进 CRDT：共享服务刚起来、前端还不知道这是共享仓库的那几毫秒里打的字不会丢（一开始做成「共享了就一律不用」，桌面端实测前想到这个竞态改的）。前端这边加入好了以后自动保存一律不写正文（`setBodyOwner`）。改标题、置顶、归档、删、挪树还是原来那几条命令，写完进索引，再由对账交给 CRDT
- **某一天、目标是一打字才有的**：前端打开它时 Rust 先在仓库文档里记上元数据（种类、空标题），不然正文到了不知道是什么、一直等着不写盘
- 加入中、被拒、被移出：仓库窗口里本来什么都没有，共享对话框自己弹出来说清楚
- **某一天不延续前一天**（共享仓库里）：两台设备同时打开今天、各自把昨天的内容抄进来，合并后就是两份。某一天、目标的「建的时间」记 0（属性块里不写，按修改时间算每台设备不一样）
- **附件**：不只是「附件」文件夹，仓库里不以点开头、不是 .md、不超过 50MB 的文件都算。清单里删了的：本机的还是那一版就挪进 `.odea/trash/files/`，本机改过的留着（下次扫描当新的交出去）。谁都没有的附件 30 秒后再要
- **打开一篇先对一次账**（`share_doc_open` → `Share::open_doc`）：磁盘上刚改的（刚建的笔记、别的程序刚改的）先进 CRDT，快照才是最新的；还没对完第一遍账时打不开，前端过一秒再来，这期间编辑器是只读预览
- **移出**：管理员签了新表、发给大家以后等 2 秒再断开被移出的人（马上断的话他可能收不到新表，不知道自己被移出了）。被移出的人以后再拨：对面先给他看新的成员表（他说自己有成员表的话），再拒绝 —— 他就知道了
- **断了 3 秒后重拨**（另外每 20 秒试一次所有没连上的成员）
- 和 git 同步二选一两头都拦：开着同步不让共享，共享着不让开同步；网盘里的不让共享、也不让加入到网盘里
- 共享仓库里不给会话式的「邀请协作」：一篇不能同时绑两个 CRDT
- 光标只发给直接连着的成员（不经别人转）
- 名字：成员表里的名字由管理员签。我是管理员的话改名字时顺手重签；别人的名字是加入时的，之后改了要管理员那边改

#### 还没做的

- 浅快照（只留某一版之后的历史）、按需加载文档：现在打开共享仓库时每篇的 Loro 文档都读进内存
- 中继压测、真实网络、两台实机（同一台电脑上两个桌面端实例测过，§21.7）
- 「共享一个已有的仓库」时转成逻辑目录、停掉同步：现在是直接拦下来、说清楚要先做什么

### 21.6 P10.3.4 历史版本

- `Replica::history`：沿着这一篇的改动按时间排，同一台设备（peers 表认人）、停顿不超过 5 分钟的并成一版，每一版记着结束时的 frontiers；`text_at` 是那一版的全文（`forkAt`），`restore` 是 `revertTo`（一次新的改动，发给大家）
- 改动多久并成一个：Rust 那份和前端那份都是 60 秒（`set_change_merge_interval`，默认是 1000 秒，长时间编辑会全挤在一个改动里分不开版本）；都开着记时间
- 界面复用原来的历史版本对话框：共享仓库里换成 CRDT 的历史（谁改的写名字），「恢复这一版」直接在 CRDT 里退回去，不走撤销提示条（想回来再从历史里恢复）

  - 乙的仓库按 `prepare_join` 的样子摆好（仓库标记、空的清单、拿着链接的 share.json），打开：共享对话框自己弹出来「连上了邀请人，等他同意…」；甲那边出现加入请求，同意以后乙同步到两篇笔记、20KB 的附件（逐字节一样），乙是可编辑
  - 乙在编辑器里打字（WebView2 里的 wasm Loro → 乙的 Rust → 甲的 Rust）→ 两边的磁盘都有；甲开着的编辑器当场看到；甲打字回去，乙的编辑器当场看到；别的程序改甲的文件，乙开着的编辑器当场看到
  - 历史版本对话框（乙）：三版、新的在前、自己的写「这台电脑」、默认选中上一版给出差异；「恢复这一版」→ 乙的编辑器、甲的磁盘都退回那一版
  - 甲把乙移出：乙的对话框「你被移出了这个共享仓库」、编辑器不再绑副本；两边日志里没有报错
- **没测到**：加入时点链接、选文件夹的系统对话框（实测里按 `prepare_join` 的样子手摆的仓库）；Windows 防火墙弹窗；两台实机、真实网络、经中继；macOS；release 包

### 21.8 踩到的坑

- 加了 Loro 以后测试程序链接不上：`LNK1140: too many modules for program database`。`[profile.dev.package."*"] debug = false`（依赖不带调试信息）。改完要整个重编 —— 这一下把 D 盘写满了（target/debug 63G），删了 `incremental`、`deps` 两个缓存才够
- rustc 偶尔 `STATUS_STACK_BUFFER_OVERRUN` 崩（并行 6 以上），`-j 3` / `-j 4` 就好
- 两个 Rust 类型都叫 `RejectReason`（协作的、共享的），导出的绑定里撞名：共享的改叫 `Refusal`
- 泛型命令（`share_create<R>`、`share_join<R>`）在两份命令表里要写明运行时（`::<tauri::Wry>` / `::<tauri::test::MockRuntime>`）
- 移出成员时马上断开，新的成员表常常还没送到 —— 他不知道自己被移出了（测试才暴露），改成等 2 秒
- 内置浏览器窗格藏着时 requestAnimationFrame 不跑：对话框关掉以后退场动画停在半路，遮罩还在、挡着点击。验证时改用脚本往编辑器里输入（`execCommand("insertText")`）；Vite 开发服务器里模块地址带 `?t=…`，看 store 要按 `performance.getEntriesByType("resource")` 里实际的地址导入
- Bash 的 heredoc 里有引号时整段追加失败（还什么都没写进去）：大段代码先用 Write 写到临时文件再 `cat >>`
- 桌面端实测时直接调 `share_create` 命令，前端的共享状态没跟着刷新（界面上的按钮会直接更新）：命令建好以后也发一次 ShareChanged
- 同一台电脑上两个调试版要各编一次（`pnpm tauri build --debug --no-bundle --config '{"identifier":"…"}'`），编完马上把 `target/debug/odea.exe` 拷走：下一次编会覆盖它

## 22. P10.4 设计：团队仓库（git 管持久，会话管实时）

2026-10-22 定稿（和用户讨论定的）。§20 的共享仓库想用一套点对点的 CRDT 同时管两件事：不同时在线时也能同步、同时在线时一起改。后一件它做得好，前一件做不到 —— 没有一直在线的那一份，两台设备得同时开着才同步得上；和 git 同步只能二选一；成员按设备算、没有「人」这一层，日程跟着整个仓库共享（每一天全体成员共用一篇，日程开关也是大家一起的，共享仓库里干脆不延续前一天）。

重新分工：**持久交给 git，实时交给会话。** 两样都是现成的，各自用最合适的东西。

### 22.1 结论

| 问题 | 定了什么 | 为什么 |
|---|---|---|
| 不同时在线 | **git 同步**（GitHub / Gitee，技术方案 §5.9），不改 | 云端一直在线；历史版本、冲突副本、清单按节点合并都有了 |
| 同时在线 | **会话式**（§3），从一篇扩到「一条连接里好几篇」 | 主持人的文件是真相，这一条不变 |
| 团队是什么 | **团队仓库**：一个开了 git 同步、几个账号都有权限的仓库（GitHub 的协作者、组织）。仓库标记里写着 `team`，设备名单在仓库里（`.odea/devices`） | 谁能进交给托管方的权限，Odea 不再自己签成员表 |
| 成员之间 | **不用邀请**：同一个团队仓库开着的设备自动连上；两个人打开同一篇就在同一个会话里 | 名单随 git 走，是不是成员不用另外问 |
| 不是成员的人 | 照旧发邀请链接，范围可以是一篇、一个文件夹或整个仓库 | 临时请人来看、来改，不用给他仓库权限 |
| 日程 | **团队仓库的日程是团队的**（每天一篇团队的、团队的目标），**个人的日程在个人仓库**。窄栏上的日程属于这个窗口的仓库；「日程切换器」在几个仓库的日程之间跳 | 个人的计划不给别人；团队的站会、目标本来就该一起写 |
| 共享仓库 | **退役**（§22.7） | 它管的两件事被上面两层接走了 |

### 22.2 两层怎么配合

```
              不同时在线：git                              同时在线：会话
张三 ──push──▶ GitHub ◀──pull── 李四              张三 ◀──iroh（局域网 / 中继）──▶ 李四
                                                    同一篇：主持人写盘、提交
```

难的是两条路线碰在一起的时候：同一次改动要是既经会话、又经 git 到了对方，git 会把它当成两边各改了一次（§20.1「和 git 同步」那一条）。规矩：

1. **一篇在会话里时，只有主持人写盘、提交。** 访客的编辑器绑着会话，不存这一篇（和现在做客一样）；访客本机那份文件不动，git 下次同步把主持人存的那一版拉过来。同一次改动只经一条路线进 git
2. **加入之前先同步一轮 git**（联得上网的话）：两边从同一版开始。访客本机这一篇和主持人那份不一样（有没推上去的改动、或者两边 git 不在同一版），把本机的改动当成「从共同的那一版分叉出去的外部改动」合进会话（§4.4，`external.ts`）。共同的那一版：主持人建这一篇的会话时记下 git 里它的 blob id（`Welcome` 里带着），本机的 git 里有这个 blob 就用它，没有就用本机 HEAD 里的
3. 主持人每次存盘，把那一刻的版本（Loro 的 frontiers）和存下去的内容的 blob id 告诉访客（`Saved`）
4. **主持人走了**（关掉这一篇、关窗口、断线超过 10 秒），留下的人里接着当主持人的那位（§22.4 的规矩）**先同步一轮 git**，把旧主持人推上去的拉下来；磁盘上这一篇和「旧主持人最后一次 `Saved` 的那一版」不一样（旧主持人之后又改过、或者还没推上去），就按外部改动从那一版分叉合进会话，然后照常写盘。这样新主持人的提交接在旧主持人的后面，git 合并不出冲突
5. **只有局域网、联不上 git**：照样实时。git 晚一点合，合不上时照旧另存一份冲突副本（技术方案 §5.9.5），不丢东西
6. 两边各自经 git 送到的同一处改动（规矩 2 合进会话的、本机又提交过的），git 三方合并时两边改得一样，本来就不算冲突

### 22.3 团队仓库

**标记。** `.odea/vault.json` 里 `team: { id }`，id 是随机的 16 字节（十六进制），连接时用来认「是不是同一个团队仓库」。随 git 走，成员打开时都认得出。

- 「邀请成员…」第一次邀请时写上（仓库得开着 git 同步）
- 拉一份别人的仓库（仓库的主人不是我的账号）：里面没写的话写上，下一轮同步推上去
- 没写 `team` 的就是个人仓库：不起端点、不写设备名单，和现在完全一样

**设备名单** `.odea/devices`，随 git 走：

```
# 一行一台设备：设备公钥  账号  设备名  更新时间（毫秒）
5f2c…e1  github:Gred666   书房的电脑    1792600000000
a91b…07  github:xiaowang  小王的笔记本  1792600123000
```

- 每台设备打开团队仓库时，自己那一行没有、名字或账号变了就改自己那一行（随下一轮同步推上去）。只改自己那一行
- `.gitattributes` 里给它 `merge=union`：两台设备同时改相邻的行时两边都留下。同一把公钥出现两行时认更新时间新的那行，下次改自己那一行时顺手去掉旧的
- **谁是成员**：名单里有的公钥。只有能推这个仓库的人才加得进来；连接两头都查对方在不在自己手里这份名单里
- 账号是自报的：成员之间是信任的（都有仓库的写权限），冒名只影响界面上显示的名字。界面上的人按账号认：同一个账号的几台设备是一个人、一个颜色

**邀请成员。**

- 仓库菜单（「仓库名 ⌄」）/ 命令面板「邀请成员…」：填对方在 GitHub / Gitee 上的用户名 → Odea 调托管方的接口把他加成协作者（GitHub `PUT /repos/{owner}/{repo}/collaborators/{username}`，会给他发一封邀请）→ 给一个链接 `odea://vault/<托管方>/<owner>/<repo>` 让你发给他（附一句「用 Odea 打开」和下载地址，和邀请链接一样）
- 对方点链接，或者在启动器「从同步仓库拉一份」：登录 → 有待接受的邀请就在 Odea 里接受（GitHub `GET /user/repository_invitations`、`PATCH /user/repository_invitations/{id}`）→ 拉下来、打开
- 列仓库改成 `affiliation=owner,collaborator,organization_member`：别人的仓库标「团队 · 主人是 xxx」
- GitHub 的 OAuth scope `repo` 已经包括这几个接口；Gitee 的协作者接口（`PUT /v5/repos/{owner}/{repo}/collaborators/{username}`）用真实账号验过再开
- **成员…**：名单里的人（按账号合起来）、在不在线、托管方那边还有谁有权限（GitHub `GET /repos/{owner}/{repo}/collaborators`）。「移出」= 调接口去掉他的权限 + 删掉名单里他的几行、提交推上去。他手里已经拉下来的副本收不回来，界面上说清楚

**提交署名**改成「账号 (设备名)」（个人仓库也是）：团队仓库的历史版本里看得出是谁改的。`history.rs` 认新旧两种（「Odea (设备名)」「OnTheWay (设备名)」照旧认成设备名）。

**设备密钥**：团队用的一台设备一把（钥匙串 `team-device-key`），几个团队仓库共用；和会话式协作那把分开 —— 两个端点同时开着，同一把密钥在中继那边会互相顶掉（§21.5）。

### 22.4 成员之间自动连上

**端点。** 有团队仓库的窗口开着就起一个（ALPN `odea/team/1`；一个应用一个，几个团队仓库共用，`Hello` 里带着团队 id）。和会话式不一样，它一直开着：别人要能找到你。第一次打开团队仓库时 Windows 会问防火墙，在那时说一句（§10）。个人仓库不起。

**找到对方。**

- 局域网：mDNS（服务名 `odea-team`，广播里只有设备公钥）
- 互联网：中继。团队的中继记在仓库里（`.odea/relays`，一行一个中继码，随 git 走）：成员打开时问一句「这个团队仓库用中继 X，要用吗」，允许了才连；加上自己配的中继（§6）
- 连上的成员互相告诉对方别人现在在哪（地址表，和共享仓库的 `places.json` 一样记在本机）：A 连得上 B、B 连得上 C，A 下次能直接拨 C
- 两边都没有中继、又不在一个网络里：连不上，只靠 git。界面上「在线」那里说清楚
- 网状：名单里每一台都去拨，20 秒试一次没连上的；两边同时互拨出两条连接时留公钥小的那一方拨出去的（这几样从 `share/service.rs` 拆出来）

**在线、在看哪篇。** 连上以后互发 `Presence{名字, 账号, 开着的文档 [文档 id]}`，变了再发。

- 窄栏同步那一格的悬停里「小王 在线」；文档标题那一行右边「小王 也在看」（和协作标签同一个位置，§16.2）
- 文档 id：笔记是属性块的 id（没写 id 的用相对路径 —— git 同步的仓库里两边路径一样），某一天 `day-日期`，目标 `goal-周期-开始日期`

**进同一篇。** 我打开一篇，Presence 里有人开着它：向他要（`Open{文档 id}`），之后和现在做客一样（Sync1 / Sync2 / Update、光标、附件、组字，§7、§20.10）。成员之间不用确认，都是可编辑。

- **谁当主持人**（不看时钟）：这一篇已经有访客的那位接着当；都还没有访客时，公钥小的当。两台设备断着网各自开了同一篇、连上以后发现对方也开着：公钥大的那位先把自己的存下去，再按 §22.2 规矩 2 加入
- **主持人走了**：留下的人里公钥最小的接着当，按 §22.2 规矩 4 接手；其余的人改连他
- **每一篇是星形，连接是网状**：两两之间一条连接，一篇的访客都经各自的连接连那一篇的主持人。C 连不上主持人 A、只连得上 B：B 替 C 转（§20.9 的办法，按篇转）
- 主持人那边每一篇一个 Loro 文档，只在有访客时才有；没人开着了就收掉

**做客的那一篇在成员这边是仓库里的文档**（不是 §16.2 的「做客的那一篇」）：标题、双链、附件照常；只是自动保存不写它（主持人在写），git 拉来的这一篇的改动不当外部改动合（那就是主持人存的）。主持人走了、自己接手后照常保存。

### 22.5 文件夹会话：邀请不是成员的人

- 「邀请协作…」多一个范围：这一篇 / 这个文件夹 / 整个仓库（默认这一篇，和现在一样）
- **文件夹、整个仓库**：访客那边是访客窗口（仓库与启动器.md §13），左边是这个范围里的树（主持人发 `Tree{节点}`，变了再发），点开哪篇就向主持人要哪篇（`Open`）。主持人那边起这一篇的 Loro 文档，访客都关掉了就收掉
- 访客新建笔记：交给主持人建（`Create{文件夹, 标题}`），只读的不能。删除、改名、挪：这一版不给
- 附件：照 §7.2 的规矩按每一篇算 —— 只给范围里这一篇引用了的
- 范围之外的文档要不到：主持人按范围查
- 主持人那边：成员表里「X 在看《周报》」；主持人自己没开着的那一篇也照收照存（现在主持一篇时切到别的笔记就是这样）
- 落盘、继续上次的协作（§18）：按篇记

**一台设备上一篇只有一份 Loro 文档，它可以同时连着几条链路。** 团队仓库里我邀请了外人：外人打开的那一篇正好由别的成员主持（我在那一篇里是访客），我这份就同时连着两头 —— 上游是那位主持人，下游是外人；每条链路各自 Sync1 / Sync2，从一头收到的改动转给另一头（CRDT 的更新重复收到没关系）。写盘的还是团队里的那位主持人。外人只读的话，他发来的我这里就丢（我是他的主持人）。

**协议 `odea/collab/3`**（不兼容，换 ALPN；会话式和团队共用这一套帧，§7.4）：

- 文档流开头一帧 `Open{文档 id}`，之后 Sync1 / Sync2 / Update / Resync 都在这条流上；一篇一条流
- 光标数据报前面加 2 字节的文档号（这条连接上 `Open` 时分配）
- 控制流多出 `Presence`、`Tree`、`Create`、`Saved`、`Close{文档 id}`
- 会话式的 `Hello` 多一个范围（`Scope::Doc` / `Folder(路径)` / `Vault`）；团队的 `Hello{团队 id, 账号, 名字}`，按名单认，不用证明

### 22.6 日程

- **团队仓库的日程是团队的**：每天一篇（站会、团队今天要做的）、团队的目标、日历上是团队笔记里写了日期的待办。存在 `日记/`、`目标/`，和现在一样。开关是团队的事（在仓库标记里，随 git 走，别的设备开关了照旧在底部问一句，仓库与启动器.md §14.2）
- **个人的日程在个人仓库**：自己的今日TODO、目标、日历在没写 `team` 的仓库里，别人看不到
- **延续照常**（共享仓库里不延续的那条随共享仓库一起去掉）。团队仓库里两个人都在线、先后打开今天：第二位直接进第一位的会话，看到的是同一份（第一位那份延续来的、还没落盘也一样）；不同时在线时各自延续，谁先改谁先建文件，另一位 git 拉到时冲突另存一份（和现在自己的两台设备一样）
- **日程切换器**：今日TODO、目标、日历那一行日期（「今天 · 10月22日 · 周三」）的后面一个小下拉（这一行的右端已经有「日 / 周 / 月 / 年」的分段控件），列出这台电脑上开着日程的几个仓库（团队的带一个小人图标，当前的打勾）；只有一个时不显示。点另一个：那个仓库的窗口提到前面、停在同一页同一天，没开着就打开它（不播开场）。跳过去的窗口摆在当前窗口的位置和大小上，看着就像同一个窗口里换了内容。命令面板「切换日程…」、快捷键 Ctrl+Alt+J 在它们之间轮着切
- 为什么不在一个窗口里同时显示两个仓库的日程：一个窗口一个仓库（仓库与启动器.md §4），两个窗口编辑同一篇会互相覆盖

| `src/lib/merge3.ts` | 逐行三方合并：加入时本机没提交的改动打到主持人那份上，撞上的不打（留给 git） |

controller 的规矩（§22.4 的落地）：

- **一个人开着不建会话**，照常编辑、存盘
- **有人主持就加入**：先存下自己的，等主持人那份到了，本机没提交的改动（相对这一篇在本机 git 里最近一次提交）三方合进会话；访客不存这一篇
- **都是一个人开着**：公钥最小的主持，别人等他的 Presence 再加入；有人在一份会话里（主持人刚走、正在接手）时谁都不新开会话
- **主持人走了**：Presence 里已经不主持的（自己关掉的）、已经不在线的马上接手；还在线、还说在主持、流却断了的等 10 秒（§23.5 实测后改的）。同一份会话里留下的人里公钥最小的接手：先同步一轮 git，再开始主持、先存一次；别人照旧连他，状态向量一换就补齐
- **主持人切走、还有访客**：先存、推一轮 git，再不主持（新主持人接手时拉得到，规矩 4）；这期间切回来就接着主持
- **两个主持人**（断线的那位回来了，或者断网时各开各的）：公钥大的让。同一份会话的照旧连过去，不是同一份的先把自己的存下去再按「加入」合
- **主持人身边没人了**：5 秒后收掉会话
- 每篇同一时刻只做一个转换（加入、主持、接手、交接），做完再按 Presence 判断一次；失败、被拒的隔 2 秒再试

和设计不一样、或者设计里没写的：

- **Presence 里多了「在哪一份会话里」**（主持人建会话时起的 id）：两台断网时各自开了同一篇、各有一份会话，主持人走了以后，不是同一份的拿旧会话去连新主持人会把正文合成两遍。同一份才能直接连，不是的要重新加入
- **没有 `Saved` 帧**：交接改成旧主持人不主持之前先存、推一轮 git，新主持人接手前先拉一轮。旧主持人崩了、没推上去的，新主持人照样用会话里的写（会话里本来就有他最后那几下），git 合并时合不上另存冲突副本（§22.9 第二条）
- **两个主持人时只比公钥**，没比「谁有访客」：让的那位的访客收到 docClosed，跟着过去
- **加入时三方合并的 base 用本机 git 里最近一次提交**，不用主持人那边的 blob id：本机的正文就是从它改出来的
- **文档 id 用相对路径**：属性块里的 id 只有 Odea 建的笔记才有，Obsidian 的库、没写 id 的在两台上不一样
- 一个窗口一次只看一篇（编辑器里那篇），Presence 里是它（加上在交接的）
- 访客粘贴的图片存在自己的仓库里，随 git 到主持人那边（没走 §7.2 的附件流）
- 当时没做的（`.odea/relays`、经 B 转、一份文档两条链路、防火墙那一句）§23.5 补上了

验证：Rust 单测 289 条（`team::` 5 条）；前端 1135 条，新的 `merge3.test.ts` 4 条、`team/controller.test.ts` 6 条（两台：小的主持、另一台加入、只有主持人存盘；加入时本机没提交的改动合进去；三台：访客之间经主持人看到；主持人切走：先推一轮、访客接手接着存、会话还是那一份、身边没人了收掉；主持人断线：等一会儿接手，他回来了还在主持，公钥大的让、三边一样且正文只有一份；访客走了主持人收掉）、`team/store.dom.test.ts` 2 条（文档 id；真的数据层和 `useCurrentDocument`：别人主持时编辑器拿到的文档带着会话、`remote`、这边一次都不存）；lint、tsc 过。浏览器预览里塞了一份 Presence 看「小王、林夕 也在看」在标题那一行的右端。

### 23.5 补上没做的、没测的（2026-10-22）

**经 B 转**（C 连不上主持人 A、只连得上同样开着这一篇的 B）

- Rust（`team/mod.rs`）：在会话里的人都接下游（前端 `host` 了这一篇）。一台设备上一篇的上下游两头转：上游来的（Update、Sync2）转给下游，下游来的转给上游和别的下游；光标数据报同样两头转、保留是谁的（只认名单里的人的）。不接自己上游开来的流、不往自己的下游开流（`open` 直接报错），两台之间转不成环
- Presence 多两样：`upstream`（我连着谁看这一篇）、`root`（这一份会话的主持人是谁）。前端（`controller.ts`）看不到主持人、却看得到一位 `root` 有的成员：等 3 秒（也许马上能直连上），再经他加入；主持人走了、同一份会话里还有人连着主持人的，经他接上，不急着接手。顺着候选人的 `upstream` 往上找得到自己的不选（会成环）
- 没解决的：C 只连得上 B、B 又走了，C 看不到 A 还在不在 —— C 自己接手。A 那边还在写同一篇，两份各存各的，git 同步时合（合不上另存冲突副本，不丢东西）

**一份文档两条链路**（团队成员在一份团队会话里，又用「邀请协作…」请了外人）

- `collab/link.ts`：一份会话可以接好几条链路（`attachSession`）。本机打的发给每一条；从一条收到的更新转给别的几条（CRDT 的更新重复收到没关系）。光标不跨着转：外人看得到我、看不到团队里的别人，反过来也一样
- 团队那边多一个「借用」（`controller.hold` / `release`，`team/store.ts` 的 `holdTeamDoc`）：协作要主持团队仓库里的一篇时借团队那份会话 —— 有就给，别人在主持就先加入，谁都没有就自己当团队的主持人；借着的时候不收掉、不换成别的一份会话（换了外人那边就合重了；两个主持人各存各的，git 合）
- 协作那边（`collab/store.ts` 的 `hostDoc`）：借到了就不自己建会话，存盘、外部改动都归团队（团队里别人主持就是他存）；编辑器存不存盘也听团队的（`adapter.ts` 里团队那份优先）

**团队的中继**（`.odea/relays`）

- 仓库里一行一个中继码（`vault/team.rs` 的 `read_relays` / `write_relays`），`.gitattributes` 里 `merge=union`。中继码里带着令牌：团队仓库本来就只有成员能读

- 「协作中继…」里自己的每台中继多一个「给团队用 / 团队在用」：写进、拿出 `.odea/relays`，戳一下同步
- 自己新配了一台中继：团队端点也当场接上
- 团队端点没配中继时也用「自己的中继表」（空的），后来加的才接得上；默认一台都不连，和以前一样
- 拨号时带上对方上次在哪（直连地址、他连着的那台中继），再加上自己的每一台中继

- **窗口刚起来时的 Presence 丢了**：连接建得比前端开始听事件还快，那几次「谁在线」没听到，之后对面没变化就一直显示不在线。前端开始听以后主动要一次（`team_peers`）

- **上一次做客结束了，「加入协作…」不见了**：命令面板只在「没在协作」时给邀请、加入，做客结束了还停着的时候回车落到了「新建笔记「加入协作」」上。结束了的也给；从命令面板、链接要加入新的时先收掉那一次（点协作标签照旧是那次结束的样子，可以存一份）

**还是没测的**：两台实机、经真的中继（不在一个网络）；防火墙弹窗那两句；GitHub 发邀请、接受邀请（第二个账号）；Gitee；接手时 git 真的同步一轮（测试仓库没有远端）

**更新说明**：下一版的草稿写在 `src/content/changelog.md` 开头的注释里（版本号还没升，不能多一节），升版本时挪成正式的一节。里面写了「共享仓库去掉了」

### 23.6 主持人走了、该接手的人挂在别人下面（2026-10-22）

发 0.4.1 时 CI 上「主持人断线：不在线了就接手」偶发等不到李四接手（本机单跑、并行压测都没复现）。模拟网络里 0ms 的定时器随机推迟 0–20ms 以后 60 次里卡 15 次：主持人张三刚断，李四先收到「张三不在线」、王五的 Presence 还是旧的（连着张三、根是张三），于是按 orphan 的「同一份会话里还有人连着主持人，经他接上」连到了王五下面；王五随后也丢了张三，按规矩等这份会话里公钥最小的李四接手 —— 李四在他下面做客，看上游一切正常，什么都不做。两边一直等。真网络里消息本来就没有全局顺序，这不只是测试的问题。

改法：做客的也看一眼上游 —— 上游在同一份会话里、不主持、也没有根（他也丢了主持人），就说明他在等人接手。等 `dropGrace`（他也许在等旧主持人回来，接回去了根就回来了），还是这样、这份会话里我公钥最小，就断开上游、照常接手（先同步一轮 git……），上游看到我主持再连过来。接手的人还是按同一条规矩算（同一份会话里在线的都算，orphan 和做客的用同一个 `sessionMembers`），不然各说各的。单测：李四连不上张三、经王五做客，张三断线 → 李四接手、王五连他、李四存盘。随机推迟下 60 次全过。

随机推迟下还剩两处，和这次无关、改之前就有：「连不上主持人：经一位连着他的成员转」那条测试里，王五看到张三写的字以后马上比李四和张三，李四那份可能晚一拍（测试该等一下再比）；看不到主持人的人在别人的 Presence 跟上之前就开了这一篇，会自己主持一份（各写各的，git 同步时合）—— 本可以经连着主持人的成员接上

### A.1 CRDT（2026-10-17）

**环境**：Windows 11、Node 24.10.0、i9-13980HX（24 核 32 线程）；yjs 13.6.33、loro-crdt 1.16.4、@automerge/automerge 3.5.0。

**做法**：
- 初始内容：`docs/语法全览.md`（68.1KB，41,866 个 UTF-16 单元）、`docs/技术方案.md`（196.7KB，105,863 个 UTF-16 单元），CRLF 规整成 LF
- 按键轨迹：固定种子；每次随机落到文中一处（不落在代理对中间），连写 1–40 下再换地方；10% 退格、3% 回车、27% 英文字母、60% 汉字；共 3000 次。正式跑之前先用另一条 300 次的轨迹热身
- 每次按键：主持人那份改一下，拿到这一次的更新包（Yjs 的 `update` 事件 / Loro 的 `subscribeLocalUpdates` / Automerge 的 `getLastLocalChange`），立刻交给访客那份应用；两边分别计时。最后两份的文本都和按 UTF-16 下标算出来的结果逐字一致
- 加入：打完 3000 下之后导出完整快照，在新副本里载入
- 并发：两份从同一状态出发，在同一位置各打 200 个字（「甲」「乙」），互不通气，然后互相应用：看是否一致、两段是否各自连成一片
- 断线：两份各按自己的轨迹写 1000 下，再一次补齐（Yjs 用 `mergeUpdates` 合成一包，Loro 按对方的版本导出，Automerge 逐个应用）

### A.2 中继（2026-10-17）

**环境**：同上一台机器。iroh-relay 1.3.0（`server` 特性），自签名证书走 HTTPS（和线上一样有 TLS），只开中继，不开 QUIC 地址发现。

**做法**：
- 中继进程限定在逻辑核 0–1（i9-13980HX 一个性能核的两个超线程）、`TOKIO_WORKER_THREADS=2`，模拟 2 核机器
- 压测程序在同一台机器上：N 个中继客户端两两配对，按固定频率互发 100 字节的包（前 8 字节是发出的时间），量收到率和延迟；先空闲 8–12 秒量内存，再发 15–20 秒
- 中继进程的内存（私有字节、工作集）和 CPU 时间用 `Get-Process` 读

### A.3 复现

- CRDT：当时是一个 Node 脚本，三个库装在临时目录里（不进项目的 `package.json`），文档路径当参数传进去；没进仓库
- 中继：`scripts/perf/relay-load/`（2026-10-18 重写进了仓库，独立的 Cargo 工程，不进 Odea 的依赖树）。两个程序：
  - `relay`：本机起一台（官方 iroh-relay 的服务端、自签名证书，`--port`、`--token`、`--quic`），打印地址和证书指纹
  - `load`：`--url`、`--token`、`--insecure`（不校验证书，压自签名的那台用）、`--clients`、`--rate`（每个客户端每秒几个包）、`--size`、`--idle`（先空闲几秒，这时看服务器的内存）、`--secs`。客户端两两配对互发，包的前 8 字节是发出的时刻，最后打印收到率和延迟的中位 / p99 / 最大

```bash
cd scripts/perf/relay-load; cargo build --release
```

在真实云主机上复测：服务器照 [自建中继.md](./自建中继.md) 跑官方 iroh-relay（模拟 2 核：`taskset -c 0,1` + `TOKIO_WORKER_THREADS=2`；`ps -o rss,pcpu -p <pid>` 或者 9090 端口的指标读内存和 CPU），`load` 放在同一个机房的另一台机器上按上面那张表的几档跑（`--clients 100 --rate 1`、`--clients 200 --rate 10`、`--clients 1000 --rate 2 / 5 / 10`、`--clients 2000 --rate 2`）。本机自测（2026-10-18，同一台机器上 relay + load）：100 个客户端、每秒 500 包、丢 0、中位 1.4ms
