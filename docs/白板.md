## 1. 结论

| 问题 | 结论 |
|---|---|
| 做成什么 | 不做「另一个产品」，做**笔记的另一种摆法**：白板就是一篇 Markdown 笔记，文档视图里从上往下读，白板视图里摆开。切换不转换数据（§4） |
| 凭什么不用重做一遍 | 正文还是 Markdown，卡片就是正文里的一段。搜索、双链、反链、带日期的任务进日历、导出、历史版本、协同里的 `body`、插件的读写，都在文本上工作，白板不用另接一套（§4.5）。要新写的是：镜头、选择、连线、形状、墨迹这一层，布局数据的读写，以及同步时按对象的合并（§6.4） |
| 实验改了什么 | 四处。① 两边同时改一张白板，git 按行只合得上 11 种情形里的 5 种，要按对象合（和 `.odea/tree` 一个路数），11 种都过。② 缩放用 `transform: scale`、**不加** `will-change`：字每一步都清楚、停下来不跳；但描边在 DOM 里会发虚，改成画在 canvas 上。③ 系统的手写识别器读不了算式（机器写的工整字也只对 56%，中文识别器把 `+` 读成「十」），算式全交给自带的模型。④ 标记和内容之间空一行。详见 §9 |
| 新在哪 | 「笔记和白板同构」AFFiNE 做了，但它的数据是 Yjs 的二进制；Obsidian 的白板是文件，但是一份 JSON，不是笔记。**同构发生在一份纯文本文件上**，这三家都没有（§3、§4.4） |
| 用不用现成的白板库 | 不用。tldraw 4.0 起生产环境要许可证、免费档带水印、商用价格要问；Excalidraw（MIT）和 BlockSuite 各有自己的数据模型和文字编辑器，卡片里用不上 Odea 的编辑器，动效和像素对齐的规矩也管不到它们里面（§3.7） |
| 手写的白板怎么导出为笔记 | 想法是对的，「导出」这个说法让它显得做不到。手写不用变成字才能进笔记：**一块墨迹就是笔记里的一块**（矢量、还能接着写），认出来的字放在替代文字里供搜索；要变成字或公式，选中了再转（§5.1）。整页手写自动排成干净的文档，别家最好的（Nebo）也要求先写在格子里，不承诺 |
| 写个算式就出答案 | 分两步。先做**打字的**：一行以 `=` 结尾就出结果，认变量；不用模型，人人用得上，Apple 的 Math Notes 本来也支持打字。再做**手写的**：墨迹 → 识别成 LaTeX → 同一个求值器（§5.2） |
| 答案模仿这个人的字迹 | Apple 用的是端上的生成模型，没有公开接口，评测说「不太像，但够近」。Odea 可以走一条更省、反而更像的路：**字形库** —— 答案只用得到十几个符号（0–9、小数点、负号），直接拿这个人刚写过的那几个数字的笔画来拼（§5.3）。长文字的「按我的字迹粘贴」要生成模型，不做 |
| 渲染 | 三层：底下一层 canvas（网格、分区、连线、形状），中间 DOM（卡片的底和字），上面一层 canvas（卡片的描边、选择框、墨迹）。canvas 每一帧按物理像素重画（§6.1） |
| 性能的底 | 实测（开发机、WebView2 151）：两百张卡片的白板，换一张编辑约 12 ms，卡片里打字不比整篇编辑器慢；墨迹一帧重画近四千笔仍是 180Hz，一屏一万笔掉到 45 帧；一页两千笔带原始采样存成 SVG 约 0.7 MB（§9） |
| 本机的底子 | 实测：WebView2 里低延迟墨迹要的接口都在、调得通（`navigator.ink`、合并 / 预测的指针事件、`desynchronized` 画布）；系统自带简体中文和英文的手写识别器，认字可以用。没有网页版的手写识别接口（§6.2、§6.3） |
| 最大的风险 | 还是范围：按「强大、细节到位」的标准，这是几个月的量。其次：这台开发机没有笔，真正的延迟和手感在这里验不了，实验里的「手写」是机器画的字；公开的手写算式数据集都是非商用许可（§11） |

## 3. 别家怎么做的

| 产品 | 白板是什么 | 值得拿的 | 不拿的 |
|---|---|---|---|
| AFFiNE（BlockSuite） | 同一篇文档的另一种模式：页面模式和无边界模式同构，切换不转换数据 | 同构这个想法；阅读顺序；分区（frame）按区域带着里面的东西走 | 数据是 Yjs 的二进制，不是文件 |
| Obsidian Canvas | 一个 `.canvas` 文件（JSON Canvas 1.0）：文字卡片、文件卡片、链接、分组、连线 | 卡片可以就是一篇笔记；格式公开、简单；文字卡片能「转成文件」 | 白板本身不是笔记，搜索和反链要另接；没有墨迹、形状；没有实时协同 |
| Excalidraw 的 Obsidian 插件 | 一个 `.md`：上面是「笔记背面」的 Markdown，下面一节是画的数据（压缩过的 JSON），文字元素另列成明文 | 画和笔记放在同一个 Markdown 文件里；文字列成明文，搜得到、链得到 | 画的数据压成一团，没法看差异、没法合并；背面的字和画上的字是两份东西 |
| Heptabase | 卡片库加白板：卡片是笔记，摆到一张或几张白板上 | 键盘流：从一张卡片直接长出下一张；分区、脑图排法 | 数据在它自己的库里 |
| Apple 备忘录 / Freeform | 备忘录里手写和打字同在一页；Math Notes 写 `=` 出答案、认变量、能画图（26 起三维）；Smart Script 把字迹理顺、拼写改正后用你的字迹重写 | 手写是文档里的一等内容；答案用主题色标出「这是算出来的」；可以关掉自动算、改成先建议 | 生成字迹的模型（没有公开接口，§5.3） |
| Goodnotes | 手写的拼写检查、补全（2023 年 8 月），Math Assist，手写可以重排、对齐 | 涂掉即擦、圈起来即选 | — |
| Nebo（现在叫 MyScript Notes） | 文档里分块：文字块（手写会重排）、公式块（能算简单的、能复制成 LaTeX）、图表块，另有自由画板 | **墨迹分块**：一块手写是一个对象；双击才转成字，不自动转 | 识别引擎是商业授权（§6.3） |
| tldraw / Excalidraw | 通用的白板，也是别人拿来嵌的库 | 无限画布的那些惯例；Excalidraw+ 今年 9 月把元素和网格对齐到整物理像素、消掉非整数缩放时的糊 | 整个嵌进来（§3.7） |

### 3.1 AFFiNE：同构

BlockSuite 的文档是一棵块的树：根下面第一个孩子是「画面块」（放笔刷、形状、连线这些只在白板上有的东西），后面是若干「便签块」，段落在便签块里。

- 页面模式：便签块按顺序从上往下排
- 无边界模式：每个便签块有自己的位置，可以拖开；一篇文档可以在白板上拆成好几张便签
- 两种模式是同一份数据，切换时不做转换；阅读顺序两边一致，白板上每张便签标着序号
- 叠放顺序用分数索引（fractional indexing），便签和画面上的元素放在一起比
- 两种归组：分区按几何区域（拖分区，区域里的东西跟着走），组记成员的 id（可以嵌套）
- 画面上的分区、组可以反过来嵌进页面模式

这正是「无缝切换笔记和白板」。它没解决的是存储：数据在 Yjs 里，不是用户文件夹里的文件。

### 3.2 Obsidian Canvas 和 JSON Canvas

JSON Canvas 1.0（2024-03-11）：顶层两个数组 `nodes`、`edges`。节点四种 —— `text`（Markdown 文字）、`file`（仓库里的文件，可以带 `#小节`）、`link`（网址）、`group`（带标题的框）；都有 `id`、`x`、`y`、`width`、`height`（整数像素）、可选的颜色（六个预设或十六进制）。叠放顺序就是数组里的先后。连线记两头的节点、从哪条边出、端点是不是箭头、标签。

- 没有墨迹、没有形状；到现在没查到 1.1
- 规范没说不认识的字段、不认识的节点类型怎么办
- Obsidian 自己到 2026 年还没有原生的手写。社区插件各走各的：有的在 Canvas 上叠一层画、有的另起一种 `.blackboard` 文件、有的把墨迹存成文字节点里的内联 SVG（Canvas Kit，识别用 MyScript）

### 3.3 Excalidraw 的 Obsidian 插件：笔记背面

一张画是一个 Markdown 文件：属性块里 `excalidraw-plugin: parsed`，正文前半是普通的 Markdown（它叫「笔记背面」），后面一节 `# Excalidraw Data`：文字元素一行一条、带 `^id`，画的数据是压缩过的 JSON，包在 `%%` 注释里。

它证明了两件事：把画和笔记放进同一个 Markdown 文件，用户接受；把画上的字列成明文，搜索和链接就不用另做。它的短处也清楚：数据压成一团，git 里看不出改了什么、两边改了合不了。

### 3.4 Heptabase

卡片是笔记，白板是摆卡片的地方，一张卡片可以出现在好几张白板上。今年的动作在别处：AI 导师（3 月）、脑图的竖排、卡片上划线批注。它的键盘操作值得照着做（§7）。

### 3.5 Apple：Math Notes 和 Smart Script

- **Math Notes**（iPadOS 18）：打字或者手写一个式子，写下 `=` 就出答案；认变量；两个没定义的变量就能画成图，沿着曲线拖能看数值；26 起三个变量画三维。答案用应用的主题色，表示是算出来的；可以关掉自动算，或者改成「先建议、点了才写上」
- **Smart Script**：端上的模型，边写边把字理直、理顺；拼错的词点一下换成对的，用你的字迹写；能把剪贴板里的字「按手写粘贴」
- Apple 的人自己说的：理顺是一上来就有的；「按手写粘贴」要写上一两段才学得像，而且看上下文 —— 贴在哪一段旁边就照那一段的样子
- 评测（MacStories）：换上去的词「不总是像我的字，但够近」；贴进来的字「太工整，明显不是我写的」；整屏写字时 M4 的 iPad Pro 明显发热
- 没查到给第三方用的 Math Notes 接口。iOS 26 的 PaperKit 是标注用的画布，不算数；搜到 WWDC26 的一讲说 PencilKit 在 27 里有了手写识别（认字，没提算式），只看到摘要

### 3.6 Nebo：墨迹分块

和「手写怎么进笔记」最有关的一家。它的文档是一块一块的：手写的文字块会跟着版面重排，公式块能算简单的式子、能复制成 LaTeX，图表块把手画的形状理成规整的。转成打字是用户双击才发生的，不自动。它的用户评价里反复出现的两条：想按行转、不想整块转；想把整页手写的推导转成 LaTeX，做不到。

### 3.7 为什么不嵌现成的库

- **tldraw**：SDK 从 4.0（2025 年 9 月）起用它自己的许可证。开发不要钥匙，生产要：试用、商用（去水印，报价制）、爱好者（免费，水印不能去）。许可证里明写不许隐藏、改动水印
- **Excalidraw**（MIT）：能嵌，但它的文字是它自己的文本框，手绘风格是它的，数据模型是它的 JSON
- **BlockSuite**：整套编辑器加 Yjs，等于换掉 Odea 的编辑器
- 共同的问题：卡片里要用的是 Odea 自己的编辑器（所见即所得、组字、表格、公式都在那里量过）；出现消失只淡透明度、描边落在整物理像素上这些规矩，进了别人的画布就管不到

要自己写的那一层（镜头、命中、选择、连线、形状、墨迹）是做法很成熟的东西。小而专的库可以用：笔画轮廓（perfect-freehand，MIT）、空间索引（rbush，MIT）。

## 4. 新的思路：一份文件，两种摆法

### 4.1 文件长什么样

白板是仓库里的一篇笔记。正文是卡片按阅读顺序排下来；每个对象前面一行注释记它摆在哪，注释和内容之间空一行。
草案（实验 5 验过往返和合并，§9.5；字段的写法还可以再改）：

```markdown
---
id: 0199f3c2-…
board: 1
---

<!-- @frame f1 0,0 960x640 -->

## 问题

<!-- @card c1 40,80 320 -->

导出很慢，**两千篇**要 40 秒。

- [ ] 量一下卡在哪 @2026-11-20

<!-- @card c2 420,80 320 -->

![[性能基线]]

<!-- @ink k1 40,360 480x200 -->

![12 × 3.5 = 42](附件/手写-0199f3c8.svg)

<!-- @edge e1 c1>c2 label="对照" -->
```

当普通笔记读，它就是：一个标题、一段话、一条任务、一篇嵌进来的笔记、一张图。

- **卡片的内容就是正文里的一段**：从这条注释到下一条注释之间
- **引用别的笔记的卡片**是一行 `![[笔记]]` —— 2026-11-11 刚做的嵌入，文档视图里已经会画成卡片
- **布局紧挨着内容**：挪一张卡片只改它前面那一行；删掉一段，它的位置跟着没了
- **注释后面空一行**：紧挨着的话，一边挪卡片、一边改它的第一行字，git 当成同一处改动、判冲突（实测）
- **连线、形状**没有正文，只有注释行，收在文件末尾
- **改布局是原地换那一行**，不把整篇重排一遍：差异最小，光看不改文件
- **布局丢了不丢内容**：注释被别的工具删了、写坏了，那一段照样在，白板视图里给它自动排个位置。和「日记文件夹里认不出日期的文件当普通笔记」是一个规矩：什么都不会消失。实测：删掉一个标记，内容并进上一张；位置被删，对象还在、标成自动排；复制出来同一个 id 的两份，第二份换 id；代码块里长得像标记的一行不算标记
- **任何一篇笔记都能摆开**：没有布局的笔记打开白板视图，按一级小节自动拆成卡片排好；用户动了才写注释，光看不改文件

**别的编辑器里什么样**（Obsidian 1.15 实测，§9.5）：阅读视图里看不见标记；编辑视图（实时预览）里每个标记是一行灰色的注释文字，
属性块里的 `id`、`board` 显示成两条属性。在里面改正文、从属性面板加一条属性，存完除了改的那一处一个字节不差。
GitHub、别的渲染器按 CommonMark 也不显示 HTML 注释。Typora 没测成（§11）。

**Odea 自己**：编辑器现在把块级的 HTML 注释收成一个写着「注释」的小标记（`CommentWidget`），白板的标记要改成完全藏起来、防误删；
静态渲染器本来就丢掉注释（导出、嵌入卡片不用改）；摘要和字数本来就跳过注释行（`lib/plainText.ts`，Rust 那边同一套规则）。

### 4.2 白板上有什么

| 对象 | 是什么 | 文档视图里 |
|---|---|---|
| 卡片 | 一段 Markdown；或者一行 `![[笔记]]`（那一篇的内容，改的是那一篇）；或者一张图、一个链接 | 就是那一段 / 那张嵌入卡片 / 那张图 |
| 墨迹块 | 一块手写：一个矩形区域里的若干笔画，存成附件里的一个 SVG | 一张图，替代文字是认出来的字 |
| 分区 | 带标题的区域，拖它里面的东西跟着走 | 一个标题 |
| 连线 | 接在两个对象上，可以有标签 | 不出现（以后可以在正文后面列成「关系」） |
| 形状 | 矩形、椭圆、菱形，里面可以有一行字 | 不出现 |

行内的卡片和引用的卡片可以互转：「转成一篇笔记」（Obsidian 有）和「并进来」。

### 4.3 阅读顺序

文件里的先后就是阅读顺序。白板上新建的对象按位置插进去（先分区，分区里先上后下、再左后右）。右侧的目录树在白板视图里就是这份顺序：点一条飞过去，拖着改顺序。AFFiNE 是在便签上标序号。

### 4.4 为什么不直接用 `.canvas`

| | Markdown 原生（这一稿的建议） | `.canvas` 原生 |
|---|---|---|
| 白板是不是笔记 | 是 | 不是，文档视图是另外生成的 |
| 搜索、反链、任务、导出、历史、合并 | 照旧 | 每一样都要另接：索引要会拆 JSON，合并要懂节点 |
| 「Markdown 为唯一文本格式」（技术方案 §1.2） | 守住 | 破例 |
| Obsidian 里打开 | 一篇普通笔记，内容都在，不是白板 | 是白板 —— 前提是它保留不认识的节点（墨迹、形状），规范没说 |
| 墨迹、形状 | 自己定 | 规范里没有，要加私有扩展 |

`.canvas` 当成导入导出的格式：导入时文字节点变行内卡片、文件节点变 `![[…]]`、分组变分区、连线照搬；导出反过来，墨迹和形状导不出去。

### 4.5 哪些现成的直接能用

| 现成的 | 为什么不用改 |
|---|---|
| 搜索、双链、反向链接 | 索引读的是 `.md` 的正文，卡片就是正文 |
| 带日期的任务进日历 | 卡片里写 `- [ ] 事情 @2026-11-20`，就是正文里的一行 |
| 导出 PDF / HTML | 文档视图走静态渲染器；墨迹块是图片 |
| 历史版本、差异 | 都是文本上的 |
| git 同步 | 文件照常同步。**两边都改了同一张白板时不能只靠 git 按行合**，要加一段按对象的合并（§6.4）—— 这一条是要新写的 |
| 协同会话 | 正文还是那个 `body`；布局另加一张表（§6.4） |
| 外部改动合进协同 | 把别的程序当成分叉出去的协作者，文本上的，不变 |
| 插件的 `documents.read` / `edit` | 读到的就是这篇 Markdown |
| 以后的 MCP / AI | AI 读白板等于读一篇笔记；写一张白板等于写 Markdown 加几行位置 |
| 标签页、分屏、弹出窗口 | 白板在窗格里，守 `usePaneWindow` / `docOf` / `winOf` 的规矩 |
| 卡片里的编辑器 | 表格的格子已经是「一个子 CodeMirror 绑着正文里的一段」（`cellEditor.ts`），卡片照这个做；不在编辑的卡片用静态渲染器画（嵌入卡片现在就是）。实测两百张卡片时换一张编辑约 12 ms，打字不比整篇编辑器慢（§9.2） |

### 4.6 代价

- 文件里多了注释行。源码模式下、Obsidian 的编辑视图里看得见；文档视图要像属性块那样藏起来、防误删
- 标记占地方：实验用的那份样本（卡片都很短）789 字节里标记占 326 字节；卡片写得越长占比越小
- 别的工具要是会删 HTML 注释（少见），布局会丢 —— 内容不丢，回到自动排
- 白板上自由摆的东西硬要有一个先后，新对象插在哪要有规矩，偶尔要用户自己调
- 同步时要多一段按对象的合并：git 按行合，两边都在末尾加一张、一边调顺序一边改字，都判冲突（§6.4）
- 协同时布局不能当文本合（两个人同时挪一张卡片，字符级合并会把那一行合坏），要另起一张表（§6.4）
- 「新增内容类型不写新视图组件」（技术方案 §1.1）这一条：白板不是新的内容类型，但确实是一个新的视图组件

## 5. 两个想要的功能

### 5.1 无缝切换，导出为笔记，手写怎么办

- **切换**：同一份文件换一种摆法，没有转换，也就没有「导出」这一步。整块内容换成另一块，按动效规矩用溶解（`SwapFade`），不做卡片飞来飞去
- **「导出为笔记」剩下的意思**：把布局去掉、只留正文（一条命令「拍平」）；或者把选中的几张卡片另存成一篇
- **手写**：想法没问题。问题出在以为手写得先变成字才能进笔记。分三层：
  1. **不转**。一块墨迹就是笔记里的一块，矢量的，回到白板还能接着写；文档视图、导出的 PDF 里它是一张清楚的图。认出来的字写在替代文字里（`![认出来的字](…svg)`），现有的搜索直接搜得到，不用改索引。什么都不丢
  2. **选中了再转**。选一块墨迹 →「转成文字」「转成公式」；原来的墨迹留着，确认了才换。Nebo 也是双击才转
  3. **结构**。分区变标题，先后按阅读顺序
- **不承诺**：整页随手写的东西自动排成一篇干净的文档。自由摆放的手写没有可靠的办法排成线性的，Nebo 的做法是让你先写在分好的块里
- **顺带得到的**：墨迹块是附件加一行引用，所以**普通笔记里也能手写一块**（像 Apple 备忘录），不用先开白板

### 5.2 算式：打字和手写一条管线

```
打字的一行 / $…$ ─────────────┐
                               ├─▶ 式子（LaTeX / 文本）─▶ 求值 ─▶ 结果
手写的墨迹块 ─▶ 识别 ─▶ LaTeX ─┘                            │
                                              打字：行尾浅色的结果
                                              手写：`=` 后面用这个人的字迹写出来
```

**先做打字的。** 一行以 `=` 结尾：`1280 * 0.85 =` 后面浅色显示 `1088`；认变量（`房租 = 3200`，下面 `房租 * 12 =`）；公式里一样（`$\frac{3}{4} + \frac{1}{8} =$`）。不用模型，有键盘就能用，这台机器上就能验。Apple 的 Math Notes 本来就是「打字或者手写」。

要定的一件事：**结果写不写进文件。**

- 不写（只是装饰）：式子改了结果跟着变；别的编辑器里看不到结果；导出时静态渲染器要跟着算
- 写：到处看得到；上面的数改了，下面写死的结果就旧了
- 建议：默认不写、实时算；提供「固定下来」把结果写成普通的字。Apple 有三档（自动、先建议、关），可以照着给

**再做手写的。** 墨迹块里出现 `=` 且右边空着，就识别、求值、把答案写上去。识别用自带的模型：系统的识别器读不了算式（§9.4）。必须做的细节：

- 把读到的式子排版出来，小小地显示在墨迹旁边。读错了用户一眼看得出，点一下能改。绝不能悄悄算错
- 答案用主题色，表示是算出来的（Apple 的做法），可以一键擦掉
- 改了上面的数，下面的答案跟着重写

求值：LaTeX 进、数值出。现成的有 Cortex Compute Engine（LaTeX → MathJSON → 化简、求值，包多大没量）；只做算术、变量、常用函数的话自己写也不大。结果要用精确的分数和十进制，不能出 `0.30000000000000004`。

### 5.3 答案用自己的字迹：字形库

Apple 的做法是生成模型：学这个人的字迹，再生成没写过的字。没有公开接口；学术上有同类的工作（按笔画生成、学写字人风格的：DSD、SDT、DiffInk），都是论文和要自己训练的模型，不是拿来就用的库。

算式的答案是个特例：**只用得到十几个符号**，而且这个人刚刚在同一块里写过其中好几个。

- 识别的时候顺带知道哪几笔是哪个数字，把它们按人存下来：每个符号留最近的若干个样本（原始的点、压感、时间）
- 写答案 `37.5`：取 `3`、`7`、`.`、`5` 的样本，优先取同一块里的（大小、笔、斜度本来就一致），按这个人自己的字距和基线排开，每个加一点点随机的变形，用同一支笔、主题色，按笔顺画出来
- 缺的符号（这个人还没写过 `8`）：用内置的一套手写体，缩放、倾斜到和旁边一致；等他写过一次就换成他的
- 这样写出来的**就是**他的字，不是「像」。不用模型，体积几乎是零，全在本机
- 局限：同一个数字连着出现会像复制的（留多个样本、在两个样本之间插值来缓解）；只适合小字母表，长文字做不了
- 对识别器的要求：要知道「这几笔是这个符号」。按符号切分的识别器直接有；整式进、LaTeX 出的模型只有粗略的对应，要另想办法（§6.3）

这一节是设想，没有原型。

## 6. 架构

### 6.1 渲染：三层

| 层（从下到上） | 画什么 | 为什么 |
|---|---|---|
| canvas（底） | 网格、分区的底和标题、连线、形状 | 每一帧按当前缩放、对着物理像素重画 |
| DOM | 卡片的底色和字：正在编辑的那张是子编辑器，其余是静态渲染出来的 HTML。**不画描边** | 文字、组字、选区、无障碍都要 DOM |
| canvas（顶） | 卡片的描边、选中的框和手柄、墨迹 | 描边要落在整物理像素上；墨迹要能盖在卡片上面 |

**缩放用 `transform: scale`，不加 `will-change`**（实验 1，§9.1）。PITFALLS/动效.md 第 5 条担心的是「位图被拉伸会发虚，停下来那一帧重画、清楚一下」。量下来：

| DOM 那一层的做法 | 缩放途中的字 | 停下来 | 排版 | 1px 的描边（非整数缩放时） | 每帧主线程（WebView2，200 张卡片） |
|---|---|---|---|---|---|
| `transform: scale`，不加 `will-change` | 每一步都重新光栅化，清楚 | 不跳 | 一个像素都不动 | **虚的**：没有一列是实色 | 0.13 ms |
| 同上，加 `will-change: transform` | 拉伸的位图，糊 | 一直糊着，去掉 `will-change` 那一下才清楚（就是那个「闪」） | 不动 | 虚的 | 0.11 ms |
| CSS `zoom` | 和静止画面逐像素一样 | 不跳 | 折行没变过，但卡片高度会差 1–2 px、同一个字会挪 1–2 px | 实的 | 7.2 ms（180Hz 保不住） |

- 第一种：字是清楚的、停下来不跳、便宜，唯一的毛病是描边。所以**描边不交给 DOM**，由顶上那层 canvas 按整物理像素画 —— 这同时满足「描边落在整物理像素上」那一节
- `will-change: transform` 在白板的世界层上是禁用的。这和 PITFALLS/动效.md「会淡入淡出的小控件加 `will-change: opacity`」不矛盾：那是透明度，这是缩放
- CSS `zoom` 留着备用：要它的像素级确定性时（比如导出白板成图），或者以后发现 `transform` 下字距不匀
- 三层要在同一帧里一起变：canvas 的重画和 DOM 的 `transform` 放在同一个 `requestAnimationFrame` 里。主画布不用 `desynchronized`（那个只给正在写的那一笔，§6.2）
- **平移**：镜头的位移对齐到整物理像素，和 `snapToDevicePixels` 一个道理
- **看不见的不画**：空间索引查出视口里的对象，视口外的卡片不挂 DOM；缩得很小时卡片只画标题和色块
- **动效规矩照旧**：卡片出现消失只淡透明度；白板上的小控件（连线的抓手、尺寸手柄）在 canvas 上画，不要一个控件一个图层

没量的：合成线程实际每秒出了几帧（量的是主线程的帧间隔和截图）；Excalidraw+ 今年 9 月专门做了「非整数缩放时对齐到整物理像素」，说明别家也在描边这里栽过。

### 6.2 墨迹管线

```
指针事件（笔）──▶ 原始采样（x, y, 压感, 倾斜, 时间）──▶ 平滑 ──▶ 变宽的轮廓
      │                                                         │
      │  还没抬笔：画在「湿」的那一层（低延迟画布 + 系统的墨迹尾巴）   │
      └──────────────────────────────────────────────────────────┴─▶ 抬笔：并进「干」的那一层，存盘
```

本机实测，无头 Chrome 157、无头 Edge 151、桌面端调试版里的 WebView2 151（真窗口）结果一样：

| 接口 | 做什么 | 在不在 |
|---|---|---|
| `PointerEvent.getCoalescedEvents()` | 一帧里被合并掉的采样全拿回来（笔的采样率比屏幕刷新高） | 在 |
| `pointerrawupdate` | 不等到下一帧就收到采样 | 在 |
| `PointerEvent.getPredictedEvents()` | 浏览器预测的下几个点，先画上、下一帧再改正 | 在 |
| `navigator.ink.requestPresenter()` | 把笔尖到上一帧之间那一小段交给系统合成器画（Windows 11） | 在，返回了 `DelegatedInkTrailPresenter` |
| 2D 画布的 `desynchronized: true` | 画布绕过合成、直接上屏 | 在，属性读回来是 `true` |
| `altitudeAngle` / 压感 | 笔的倾斜、力度 | 在 |
| `OffscreenCanvas`、WebGPU | 挪到 Worker 里画、以后换 GPU 画 | 在 |
| `navigator.createHandwritingRecognizer` | 网页的手写识别接口 | **不在**（印象里只在 ChromeOS 上有，没查） |

用调试协议发「笔」的事件进去（§9.3）：页面收到的指针类型是 `pen`，压感、倾斜都传到了；240 个移动合并成 2–39 次 `pointermove`（无头的少、真窗口的多），采样一个没丢；
一次最多给 10 个预测点；把笔尖那一段交给 `navigator.ink` 的那一下调通了。

- 这是「接口在不在、调不调得通」，不是「延迟多少」。真实的延迟要一支笔加一台真机量；`navigator.ink` 是不是真走了系统合成器，要有笔才看得出来
- **正在写的一笔几乎不花时间**：一千个采样的长笔，每帧把整笔的轮廓重算重画一遍 0.1 ms（4 倍 CPU 降速 0.4 ms）。不用做「只画新来的一段」那种优化
- **写完的笔画每帧整层重画是可行的**：一笔一条缓存好的路径、剔掉视口外的。WebView2（2560×1392）里一帧画 2000 笔、3871 笔都是 5.6 ms 一帧（180Hz），
  一帧画 10000 笔（缩到很小、整页都在屏幕上）掉到 22 ms 一帧。所以缩得很小时要另想办法：把远处的笔画存成位图块，或者画简化过的
- 一个反直觉的：把所有笔画并成一条大路径一次填，比一笔填一次慢四五倍（2000 笔 22 ms 一帧）
- 原始采样全留着：重画、识别（按笔顺的识别要时间）、字形库都要它
- 存成 SVG：显示用的轮廓是普通的 `<path>`，任何看图的地方都能看；原始采样放在同一个文件里的自定义属性里，Odea 读回来还能接着写。一笔一行。
  **大小**（机器写的字，240 Hz，平均每笔 28 个采样）：化简过的轮廓加原始采样每笔约 350 字节，一页 2000 笔 682 KB（压缩后 252 KB）；
  只存原始采样每笔 118 字节、232 KB，但别的工具就看不了了。两千笔的轮廓算一遍 10 ms
- 没有笔的机器（这台就是）：鼠标画线加稳定器，能用，不是主要用法。桌面上白板的主力是卡片、连线、形状；手写的价值在带笔的设备上 —— Surface 这类二合一、接手写板的、以后的平板（P14.5）
- 笔和手分工：笔是画，手指是平移缩放，鼠标是选择。按 `pointerType` 分，不用切工具

### 6.3 识别：几条路

| 路 | 是什么 | 好处 | 问题 |
|---|---|---|---|
| 系统的识别器（Windows） | 这台机器实测装着：简体中文、英文（美国、加拿大）的手写识别器，外加一个手势识别器。后台能调，一次约 16 ms | 不占安装包；认字可以用 | **读不了算式**（§9.4）：机器写的工整算式，英文识别器完全读对 56%，常丢掉末尾的 `=`、把 `÷` 读成 `=`；限定成数字反而更差（34%）；中文识别器只对 10%，把 `+` 读成「十」、`=` 读成「二」或冒号。系统里有数学输入控件（`micaut.dll`），是带界面的面板，不是后台能调的接口 |
| 自带的小模型 | 例子：Professor Euler 的识别器（MIT 的代码），4.3M 参数，ONNX 8 位量化后 4.6 MB，在手机上跑 | 离线、跨平台；计算器那一类式子它自己的测试表（一个人写的 38 条）读对 89%，同一张表上 300M 参数的 TexTeller 是 82% | 通用的公式不行：MathWriting 测试集上完全读对只有 53%。**权重是非商用许可**（跟着 MathWriting 数据集的 CC BY-NC-SA）。写法不同的人（欧陆写法的 1、4、7）要专门补数据 |
| 大一些的开源模型 | Texo（2000 万参数，能在浏览器里跑）、PP-FormulaNet-S（5800 万）、UniMERNet | 通用公式更准 | 都是看图的，主要为印刷体；几十 MB，要按需下载；手写上的数只有论文里的 |
| 商业引擎 | MyScript iink：文字、公式、图形都认，端上跑 | 质量最好 | 按设备数授权、报价制，和免费的本地应用对不上 |
| 云端的大模型 | 把墨迹当图发过去 | 潦草的也读得出 | 要联网、内容离开本机；可以等以后做 MCP / AI 时当可选项，不当默认 |
| 平板的系统接口 | iOS 27 的 PencilKit 识别（只查到摘要）、Android 的 ML Kit 数字墨水 | 不占包 | 都只认字，不认算式 |

倾向：**文字用系统的，算式全交给自带的小模型，只做算术这一档**（数字、四则、括号、分数、指数、根号、百分号、常用函数）。这一档正好是「写个式子出答案」要的，也是小模型做得动的。

实验 4 带出来的一条：一块墨迹是字还是算式要先分清，再送给不同的识别器。中文识别器眼里 `+` 是「十」、`=` 是「二」。

没解决的：许可。公开的手写算式数据（MathWriting、CROHME）都是非商用的。Odea 不收费的时候可以用；要留后路的话，得用自己攒的字形合成训练数据（Professor Euler 就是拿单个符号拼出计算器式子来补数据的）。

### 6.4 协同和同步

- **不同时在线（git）**：两边都改过同一张白板时，**按对象三方合并**，不管 git 自己合没合上 —— 和逻辑目录的清单一个做法（`sync/repo.rs` 的 `merge_tree_file`）。
  实验 5（§9.5）：十一种两边同时改的情形，git 按行只合上 5 种，按对象合 11 种都对
  - 位置、大小按属性合：只有一边改了的取那一边；同一个属性两边改得不一样，取本机的（位置撞了不伤内容）
  - 内容按行合；同一张卡片的同一行两边改得不一样，留本机的，对方的另放一张卡片在旁边 —— 冲突落在一张卡片上，不是整篇另存一份冲突副本
  - 先后单独合：谁调过原有对象的顺序就用谁的，另一边新加的插到它原来的前一个后面
  - 一边删了、另一边没动：删；另一边动过：留着
- **同时在线（会话）**：主持人写盘这条规矩不变。会话文档里：
  - `body`：正文，和现在一样
  - 一张布局表（Loro 的 Map）：对象 id → 位置、大小、颜色这些属性，按属性后改的赢；叠放顺序用分数索引
  - 每个墨迹块一个只增的笔画列表：抬笔之后的一笔不再改，擦除是打个记号
  - 还没抬笔的那一笔、别人的光标、选中了什么、拖到一半的位置，走不留历史的那一路（Loro 的 EphemeralStore），抬笔 / 松手才提交一次
- 主持人把 `body` 和布局表写回同一个 `.md`，把笔画列表写回 SVG。CRDT 是合并的手段，不是存储，这一条不变
- 附件按哈希向连着的成员要，现成的；正在写的墨迹走会话，不等文件

### 6.5 落在代码哪里

- 一个内置插件（L2）：`src/plugins/board/`。Rust 那一半很薄 —— 索引不用认识白板，只多一个「这篇有没有布局」的标记，列表里好换图标
- 不是新的文档类型（`DocumentRef` 还是 `note`），是笔记的一个视图开关：窗格里「文档 / 白板」
- 单独一个分包，用到才加载：入口包已经 1.29 MB（审查 §5.3），白板不能再往里加。识别用的运行时和模型按需下载，像 Loro 的 wasm 那样
- 窗格里的东西不写死全局 `document` / `window`（标签页与分屏.md）；弹出窗口里画布要重建、重画

## 9. 实验记录

2026-11-12 做的。调研稿列了五个「做不成就要改方向」的实验，这里是每一个怎么做的、量到什么、设计因此改了哪里、没量到什么。
脚本和测试页在 `scripts/perf/board/`（不进产品的包，`pnpm lint`、`tsc` 管不到）。

环境：开发机（Windows 11，2560×1440、100% 缩放、180Hz）。无头 Chrome 157 用 `--force-device-scale-factor` 起真的倍率；
WebView2 151.0.4129.107 是桌面端调试版的真窗口（2560×1392、1 倍、真显卡）。「4 倍降速」是 DevTools 的 CPU 降速，只管得到主线程。

| # | 问的是什么 | 结论 | 设计改了什么 |
|---|---|---|---|
| 1 | 缩放时卡片里的字清不清楚、跳不跳 | `transform: scale` 不加 `will-change`：清楚、不跳、便宜，但描边发虚 | 描边画到 canvas 上；世界层禁用 `will-change: transform`（§6.1） |
| 2 | 只给正在编辑的卡片挂编辑器，开销多少 | 两百张时换一张 12 ms，打字不比整篇编辑器慢；一千张也成立 | 不用改，照 §4.5 做 |
| 3 | 墨迹画不画得动、存下来多大（延迟没量成） | 接口在 WebView2 里都调得通；近四千笔每帧重画保持 180Hz；一页两千笔约 0.7 MB | 每帧整层重画；缩得很小时要位图块或简化（§6.2） |
| 4 | 系统的识别器读不读得了一行算式 | 读不了 | 算式全交给自带的模型；字和算式分开送（§6.3） |
| 5 | 文件记法经不经得起往返和合并 | Obsidian 里往返没问题；git 按行合不够 | 标记后面空一行；同步加按对象的合并（§4.1、§6.4） |

### 9.1 实验 1：缩放

`zoom.html` 里 40 张卡片（1px 描边、8px 圆角、中英混排，位置故意不落在整数上），四种做法：整个世界 `transform: scale`；再加 `will-change: transform`；
整个世界 CSS `zoom`；每张卡片各自 `zoom`、位置由脚本对齐到整物理像素。后两种的数几乎一样，下面只列 `zoom`。平移都在外面一层、对齐到整物理像素。驱动脚本是 `zoom.mjs`。

**A 途中和停下来。** 从 1.0 到 1.6 分十步，每一步截图，和「一上来就在这个缩放值」的静止画面逐像素比（画面 1200×800 CSS 像素）。
「不一样」是三个通道加起来差 6 以上，「明显」是差 150 以上。

| 倍率 | 做法 | 十步里最多不一样的像素 | 其中明显的 | 停下 1.2 秒后 |
|---|---|---|---|---|
| 1 | `transform` | 6565 | 15 | 6042，不再变 |
| 1 | 加 `will-change` | 129784 | 45208 | 111277，不再变 |
| 1 | `zoom` | 0 | 0 | 0 |
| 1.25 | `transform` | 8894 | 305 | 7186 |
| 1.25 | 加 `will-change` | 181836 | 51926 | 156622 |
| 1.25 | `zoom` | 0 | 0 | 0 |
| 1.5 | `transform` | 10737 | 298 | 10737 |
| 1.5 | 加 `will-change` | 257620 | 74737 | 216195 |
| 1.5 | `zoom` | 0 | 0 | 0 |

- `transform` 那几千个不一样的像素是字的边缘抗锯齿的细微差别（明显的只有十几个到三百个），放大看两边的字一样清楚；它不随时间变，所以停下来没有「再清楚一下」的那一跳
- 加了 `will-change` 的是拉伸的位图，放大看是糊的，而且一直糊着

**A2 每一帧都在变的快速缩放。** 连着 60 帧从 1.0 到 1.6，停下来立刻、150 ms、500 ms、1.2 秒各截一张，数明显不一样的像素：
`transform` 全是 0（1 倍、1.5 倍、WebView2 里都是）；加 `will-change` 的一直是 3.5–5.2 万；`zoom` 全是 0。

**B 排版。** 从 0.50 到 2.00 每 0.01 一步共 151 步，把每张卡片的高度、正文折成几行、同一个字的位置除掉缩放后和 1.00 时比。
`transform`：都是 0。`zoom`：折行一次没变；卡片高度最多差 2.02 px（1 倍）/ 1.33 px（1.5 倍），同一个字最多挪 1.84 / 1.00 px。
样本只有七段不同的字，「折行不变」不能推到所有内容上。

**C 开销。** 连着缩放 60 帧，每帧「改样式 + 把排版逼出来」的毫秒（平均）：

| 环境 | 卡片数 | `transform` | `zoom` | `zoom` 时两帧间隔的中位数 |
|---|---|---|---|---|
| WebView2，不降速 | 30 | 0.06 | 1.53 | 5.6 ms |
| WebView2，不降速 | 200 | 0.13 | 7.24 | 8.4 ms |
| 无头 Chrome 1 倍屏，4 倍降速 | 30 | 0.37 | 7.10 | 9.9 ms |
| 无头 Chrome 1 倍屏，4 倍降速 | 200 | 0.58 | 32.65 | 40.0 ms |

`transform` 的两帧间隔一直是 5.5–5.7 ms（180Hz）。

**D 静止时的描边。** 停在 0.8、1.1、1.25、1.5 四个缩放值上，横穿三张卡片的左边各取 9 个物理像素，数「就是描边颜色」的列和「半透明」的列。
`transform`：0.8、1.1、1.25 上实色的没有或只有一列，半透明的 3–6 列。`zoom`：四个值上半透明的都是 0 列。三种倍率都是这样。

**结论。** 用 `transform: scale`、不加 `will-change`；描边不放在 DOM 里。调研稿里「可能没有一种做法同时过得了途中清楚和不跳」的担心没有成立。

**没量的。** 合成线程实际出了几帧（量的是主线程的帧间隔和截图）；`transform` 下 1 倍屏的字距匀不匀只是放大看过，没量；公式、表格、代码块这些内容的卡片没放进去。

### 9.2 实验 2：卡片里的编辑器

`cards.html` 在开发服务器里引应用自己的模块：每张卡片的内容用静态渲染器（`render/staticHtml.ts`）画；点哪张，那张换成应用里真的 `MarkdownEditor`，上一张换回静态的；
改动写回整篇正文（换掉那一段，后面卡片的范围跟着挪）。卡片里有标题、任务、引用、表格、代码块、双链。没有剔除：所有卡片都挂在页面上。
打字的延迟是「keydown → 下一帧画完」，和 `perf.mjs` 一个口径（16 个字、回车、6 个退格）。驱动脚本是 `cards.mjs`，无头 Chrome 1 倍屏。
**开发构建**，比生产构建慢 2.5–3.5 倍，看相互之间的比例。

| | 200 张 | 200 张，4 倍降速 | 1000 张 | 1000 张，4 倍降速 |
|---|---|---|---|---|
| 开白板：认卡片 + 静态渲染 + 挂上去画出来 | 0.1 + 16 + 34 ms | 0.3 + 76 + 109 ms | 0.3 + 43 + 118 ms | 3.1 + 260 + 624 ms |
| 换一张编辑（中位 / 九成） | 12 / 14.6 ms | 34.5 / 38.5 ms | 12.6 / 28.1 ms | 73.3 / 86.8 ms |
| 在卡片里打字，每键（中位 / 九成） | 5.6 / 6.7 ms | 14.2 / 17.5 ms | 5.8 / 8.2 ms | 20.6 / 28.2 ms |
| 对照：整篇正文放进一个编辑器，在中间打字 | 5.9 / 10 ms | 17.4 / 25.7 ms | 10.5 / 11.8 ms | 53.6 / 72.2 ms |
| 写回整篇正文一次 | 0.004 ms | 0.08 ms | 0.013 ms | 0.13 ms |
| 反例：30 张卡片各挂一个编辑器 | 200 ms | 1225 ms | 295 ms | 1632 ms |

200 张的正文是 2.35 万字符、页面上 1800 个节点；1000 张是 11.9 万字符、9000 个节点。

- 卡片里打字不比在整篇里打字慢；卡片越多差得越远（一千张时卡片里 5.8 ms、整篇里 10.5 ms）—— 卡片的编辑器只管这一张的那点字
- 一张卡片一个编辑器不行：30 个就 200 ms，节点从 1800 涨到 2880
- 一千张不剔除，4 倍降速下开白板近 0.9 秒、换一张 73 ms，该剔除了

**没量的。** 写回是直接换字符串，没有经过正文的编辑器状态、协同的绑定、组字期间不写回那一套（表格格子的 `cellEditor.ts` 有，卡片要照着做）；
没量内存；编辑器那一包第一次加载的时间没算（开发服务器上是几百个请求，和生产构建不是一回事）；生产构建没跑。

### 9.3 实验 3：墨迹（不用笔的那一半）

真正要量的是笔尖到屏幕的延迟，要带笔的设备加高速录像，这里没有。量了四样别的。测试页 `ink.html`，驱动 `ink.mjs`、`webview2.mjs`。

**A 笔的事件。** 用调试协议发 240 个 `pointerType: "pen"` 的移动（带压感、倾斜），不等回应一口气发：

| `pointerrawupdate` | 2–7 次 | 45 次 |
| 预测的点 | 一次最多 10 个 | 一次最多 10 个 |

| WebView2 | 3871 | 一笔填一次 | 0.60 ms | 5.6 ms（95% 是 11.2） |
| WebView2 | 10000（缩到 0.25） | 一笔填一次 | 1.30 ms | 22.2 ms |
| 无头 Chrome 1 倍，1440×900 | 2000 | 一笔填一次 | 0.30 ms | 5.5 ms |

### 9.4 实验 4：系统的识别器读算式

`recognize.mjs` 用 `glyphs.mjs` 把 20 个算式（`12+3=`、`1280×0.85=`、`(40+2)÷6=`、`7/8` …）写成笔画，三档潦草程度各写 3 遍共 180 条，
经 `recognize.ps1` 喂给系统的识别器（Tablet PC 的 COM 接口 `msinkaut`），分不限定、限定成 `NUMBER`、限定成 `DIGIT` 三种。
`x`、`*` 算作 `×`。1080 次识别连进程启动一共 17.7 秒，一次约 16 ms。

| 识别器 | 限定 | 完全读对 | 前五个候选里有对的 |
|---|---|---|---|
| 英文 | 不限定 | 56%（三档潦草：60 / 55 / 53） | 84% |
| 英文 | `NUMBER` | 34% | 85% |
| 英文 | `DIGIT` | 0% | 0% |
| 简体中文 | 三种都一样 | 10% | 10% |

- 英文：20 个式子里 10 个九遍全对。错的有规律：丢掉末尾的 `=`（`12+3=` → `12+3`）、`÷` 读成 `=`（`100÷4=` → `100=4`）、`7/8` → `718`。限定成 `NUMBER` 丢 `=` 丢得更多
- 中文：`+` → 十，`=` → 二 或冒号，`1` → `7`，`(` → `1`（`12+3=` → `12十3:`，`(2+3)×4=` → `12十3144:`）
- 喂的是机器写的工整字，真人的字只会更差，所以「读不了算式」这个结论是稳的。「认字可以用」这次没验

**踩到的**（PowerShell 调这套 COM）：墨迹对象的类名是 `msinkaut.InkObject`；`CreateStroke` 要经反射传 `int[]`、第二个参数给 `null`（PowerShell 自己的绑定把数组变成了 `VARIANT[]`，报参数错）；
笔画集合要先放进变量再赋给识别上下文（`@($ink.Strokes)` 会把集合拆开）。正式实现在 Rust 里调，不会有这几条。

### 9.5 实验 5：文件记法

**往返。** `notation.mjs` 是记法的读、写、合并的原型（按行扫；正式实现用编辑器那套解析器）。`notation-check.mjs` 12 条都过：
三种写法写 → 读 → 写一字不差；代码块里长得像标记的一行留在正文里；删掉一个标记，内容并进上一张；位置被删，对象还在、标成自动排；
同一个 id 出现两次，第二份换 id；CRLF 的文件照样读；没有标记的笔记全算正文。

**合并。** 同一张白板（两个分区、六张卡片、两条连线），十一种两边同时改的情形。三种写法：标记紧挨内容、标记后空一行、
内容前只留锚点而位置收在文件末尾的一个注释块里。先用 git 的逐行三方合并（`git merge-file`），再用按对象的合并：

| 情形 | 紧挨 | 空一行 | 收在末尾 | 按对象合 |
|---|---|---|---|---|
| 各挪各的卡片 | 合上 | 合上 | 冲突 | 对 |
| 甲挪卡片，乙改它的第一行字 | 冲突 | 合上 | 合上 | 对 |
| 甲挪卡片，乙改它后面的一行 | 合上 | 合上 | 合上 | 对 |
| 各在不同的地方加一张 | 合上 | 合上 | 冲突 | 对 |
| 都在最后加一张 | 冲突 | 冲突 | 冲突 | 对，两张都在 |
| 都挪同一张 | 冲突 | 冲突 | 冲突 | 对，取本机的位置 |
| 甲删一张，乙挪它 | 冲突 | 冲突 | 冲突 | 对，留着 |
| 同一张卡片里各改一行（隔着别的行） | 合上 | 合上 | 合上 | 对 |
| 各加一条连线 | 冲突 | 冲突 | 冲突 | 对，两条都在 |
| 甲调阅读顺序，乙改被挪的那张的字 | 冲突 | 冲突 | 冲突 | 对，顺序和字都在 |
| 同一行两边改得不一样 | 冲突 | 冲突 | 冲突 | 对，留本机的，对方的另放一张 |
| **合上的** | 4 | 5 | 3 | 11 |

- 「收在末尾」最差：两张卡片的位置在那个块里是挨着的两行，各挪各的都冲突
- 「空一行」比「紧挨」多合上一种，所以定了空一行
- git 按行合，「同一个地方两边都插了东西」一律是冲突 —— 都在末尾加卡片、加连线是最常见的情形，偏偏合不上。所以要按对象合
- 这里的 git 是命令行的 `git merge-file`；同步用的是 libgit2，没单独验，按理是同一套算法

**别的编辑器。** `roundtrip-editors.mjs` 用临时配置目录起 Obsidian 1.15.0（不碰自己的库和设置），走它的调试协议：打开样本、在一张卡片的字前面打几个字、存；
再经 `processFrontMatter`（属性面板走的那条路）加一条 `tags`。两次都是：除了改的那一处，文件一个字节不差，`id`、`board` 两条属性原样留着。
阅读视图里看不见标记，实时预览里每个标记是一行灰色的注释。Typora 1.10.8 不开调试端口，没法自动操作，没测。VS Code 是纯文本编辑，没测。

**Odea 自己的几处**是读代码得出的，没跑：编辑器把块级注释收成「注释」小标记、静态渲染器丢掉注释、摘要跳过注释行（§4.1）。

## 11. 风险、没核实的

**风险**

| 风险 | 说明 |
|---|---|
| 范围 | 审查 §7 说范围是头号风险，§11 两天前才把白板划掉。这一稿把「重做一遍」降成了「加一层视图」，但那一层按「细节到位」做仍然是几个月的量，一个人维护 |
| 没有笔 | 开发机是 2560×1440、100% 缩放的桌面，没有笔。墨迹的手感、延迟、掌压误触在这里验不了；实验 3、4 里的「手写」是机器画的字、「笔」是调试协议发的事件。阶段 4、5 要先有硬件，一块入门的数位板就能验压感、采样、延迟这条管线 |
| 识别会读错 | Apple 做了多年，评测里仍然有读错的。小模型更会。界面必须让读错很便宜：读到什么摆出来、点一下能改 |
| 许可 | 公开的手写算式数据集都是非商用的，拿它训练出来的权重跟着非商用（§6.3） |
| 三层要对得上 | 卡片的字在 DOM 里、描边在 canvas 上，平移缩放时两层要在同一帧里动，差一帧描边就和字错开。实验 1 分别量了两层，没把它们叠在一起量 |
| 缩得很小时的墨迹 | 一屏一万笔每帧重画只有 45 帧（§9.3）。要位图块或者简化的笔画，而位图块缩放时又是「拉伸的位图」那个老问题 |
| macOS / iOS 的 WebKit | 实验全是在 Chromium 上做的。`transform` 不加 `will-change` 时每一步重新光栅化是 Chromium 的行为，WebKit 不一定；`navigator.ink`、`desynchronized`、`pointerrawupdate` 在 Safari 上有没有，没查。苹果平台上可能要用原生的 PencilKit 盖在上面 |
| 文件里的注释 | 被别的工具删掉、用户在源码里改坏（§4.6）。Obsidian 里验过没事；Typora 存盘时会把 Markdown 重写一遍，没验 |

**没核实的**

- 实验里每一节末尾的「没量的」（§9.1–§9.5）
- §5.3 的字形库、§6.4 的会话结构（布局表、只增的笔画列表）还是纸面上的；打字的算式也没有原型
- 实验 2 是开发构建；实验 1、3 主要在无头 Chrome 里，只有关键的几项在真的 WebView2 里复核过
- Typora 里的往返没测（它不开调试端口）；VS Code 没测（纯文本编辑，按理不动别处）
- 同步里按对象的合并只有 JS 的原型（`scripts/perf/board/notation.mjs`），没接进 `sync/repo.rs`，没在 libgit2 上跑过
- 没拿笔画过一笔。`navigator.ink` 的系统合成只在 Windows 11 上有，是按微软 2021 年的文章说的；「延迟改善最多 240%」是它当时预览版的数
- Obsidian 打开带有不认识的节点类型的 `.canvas` 会怎样，没试
- Heptabase、Goodnotes、Nebo、Excalidraw 只看了搜索给的摘要；Heptabase「一张卡片能上好几张白板」、Excalidraw 是 MIT、perfect-freehand 和 rbush 是 MIT，是凭印象写的
- Professor Euler 那几个数是它 README 自己写的，测试表只有 38 条、一个人的字，而且它自己说那张表已经不是盲测；它的仓库只有 1 个星，是个人项目，当「小模型做得动算术这一档」的例证，不当能直接拿来用的依赖
- Texo、PP-FormulaNet 的数来自论文摘要和搜索摘要，没跑过
- iOS 27 的 PencilKit 手写识别只看到搜索摘要里的一句
- Cortex Compute Engine 打包后多大没量；npm 上未压缩是 3.66 MB
- 两百张卡片的白板占多少内存，没量
- MyScript 的价格没有公开数字，「按设备报价」是它论坛和第三方页面上的说法
