## 1. 结论

| 问题 | 方案 | 为什么 |
|---|---|---|
| 「一切皆插件」插到哪一层 | 功能做插件（今日TODO、目标、日历、归档、反链、模板、导入导出、渲染器、同步目标），引擎做模块（CodeMirror、Loro、存储、WebView）。两者不共用一个注册表 | 引擎本来就各是一个模块：CodeMirror 只出现在 `src/editor` 和协作绑定里，Loro 只出现在 `src/collab` 的 4 个文件里。真正写死在核心里的是日程：前端 16 个文件里有 51 处按 day / goal 分支（§3）。VS Code、Obsidian、Zed 也都这么划（§4） |
| 「一切皆文档」落到哪 | 文件格式就是协议：文档类型靠路径规则认，元数据写进属性块，配置写进 `.odea/vault.json` | 团队仓库靠 git 同步，不在文件里的东西传不过去；属性块本来就把不认识的键原样留着 |
| 插件分几档 | L0 纯声明（不跑代码）、L1 沙箱脚本、L2 内置模块 | 官方占位里的「增强 Callout」就是纯声明；到了 iOS 上只有 L1 要受 Apple 4.7 约束 |
| 第三方代码跑在哪 | 跑在 opaque origin 的 sandboxed iframe 里，宿主经 postMessage 只开放 Odea 自己的能力；先不嵌 QuickJS | Tauri 修复 GHSA-57fm-592m-34r7 之后，iframe 调不到 IPC（Windows 上同源的除外）；Joplin 在手机上就是这么跑插件的；Odea 的插件只交编辑意图，本来就是异步的 |
| 插件的界面 | 由宿主照插件交来的声明画；文档类视图就填 `DocumentModel` 的槽位。自由 HTML 面板只作逃生口 | 弹出窗口是用 portal 挂进去的，iframe 一换 document 就会重载；动效、描边那些规矩只有宿主自己画才守得住 |
| 用什么壳 | 继续用 Tauri，按平台选引擎：Windows 用 WebView2，Linux 换成 CEF，macOS 实测以后再定；手机用系统 WebView | Windows 上 WebView2 和 Electron 是同一个引擎，内存也差不多；Tauri 官方在 v3 这条线上做了 CEF 运行时（还是 alpha）；Linux 的 AppImage 现在已经 88 MB。Windows 上实测，同一个前端换成 CEF，启动一样快、内存多 4–5%，动效和组字的结果一样；但安装包从 9.2 MB 涨到 130 MB，而且 Tauri 的 CEF 运行时在 Windows 上不开进程沙箱（§7.6、§7.7） |
| GPUI | 这一轮不上 | 上游的 iOS 后端 2026-10-14 才加进来，没有 Android，接口还没到 1.0；改用它要重写编辑器、公式、图表和 HTML 表格 |
| 正文的权威副本 | 留在 WebView 里，不搬进 Rust | 插件化不需要这一步；组字、表格格子那些规矩都是在这条路径上量出来的 |

## 2. 口号落到哪

「一切皆文档，一切皆插件」落到代码上，是三句话：

- **数据都是文件。** 用户写的内容、插件存的东西、仓库的配置，都落在仓库文件夹里的普通文件上：Markdown 加属性块，以及 `.odea/` 下的 JSON。不认识的内容原样留着；索引和缓存删了能重建。
- **功能都是插件。** 今日TODO、目标、日历、归档……和第三方插件走同一套贡献点接进来，都能关掉。关掉以后，核心里没有它的一行代码，它的文件当普通笔记打开。
- **引擎只是模块。** 编辑器（CodeMirror）、CRDT（Loro）、存储、WebView 都是内部接口后面的实现。要换它们就是改代码加迁数据；它们不进插件注册表，也不让用户在设置里选。

引擎为什么不做成插件：

- 用户不会去挑编辑器内核或 CRDT 库。用户会挑的是功能（要不要日程）、同步目标（GitHub 还是 Gitee）、提示块长什么样。
- 每一个公开接口，每一版都要维护。Zed 的扩展 API 每个版本单独一份 WIT 目录，宿主每一版都得留着对应的绑定（§4）。这份成本只值得花在用户真会去扩展的地方。
- 真要换引擎，数据反正要迁（Codex v2 §1 自己也这么说）。注册表省不掉迁移，只是多出一层天天都要付出代价的抽象。
- 它们本来就已经是模块了（§3）。

这些地方已经在往这个方向走：

- `DocumentModel`（`data/types.ts`）把五个区收成了同一种文档，`data/adapter.ts` 里那个 switch 是唯一的分叉点。插件化就是把这个 switch 换成注册表。
- 日程、归档已经是两个开关（`VaultLayout.journal` / `archive`），记在 `.odea/vault.json` 的 `features` 里，跟着仓库同步。日程关着的时候，日记、目标就是普通文件夹（见 `vault/layout.rs` 的注释）。「插件停用后，它的文件当普通笔记」这条路已经走通了。
- `vault/layout.rs` 会读 Obsidian 的 `.obsidian/core-plugins.json`，看「日记」这个核心插件开没开，再从 `daily-notes.json` 里取文件夹和日期格式。日记在 Obsidian 里本来就是一个能关的核心插件，配置也是一个文件。
- 属性块（`vault/frontmatter.rs`）只认自己那几个键，其余的行原样保留。

## 4. 调研：别家怎么划插件的边界

| 产品 | 哪些是插件 | 哪些不是 | 插件代码跑在哪 |
|---|---|---|---|
| VS Code | 很多核心功能本身就是扩展，用的是同一套 API | 编辑器、工作台。扩展拿不到 DOM，也不能加 CSS，官方理由是不能影响稳定和性能、要给自己留改界面的余地 | 单独的扩展宿主进程 |
| Obsidian | 核心插件：文件列表、搜索、同步、命令面板、日记、模板、反链、大纲…… | 编辑器、库 | 和应用同一个 JS 环境。官方说没法可靠地限制插件的权限 |
| Zed | 语言、主题、代码片段、斜杠命令 | 不能加面板。每个 API 版本单独一份 WIT | Wasm（wasmtime） |
| SilverBullet | 编辑、索引、同步这些核心功能都是 plug | — | 但它主要的扩展方式反而是写在页面里的 Space Lua 和模板库；文档说大多数用户用不着自己写 plug |
| Figma | 插件分成逻辑和界面两半 | — | 逻辑跑在编译成 Wasm 的 QuickJS 里（能碰文档，碰不到浏览器 API），界面跑在 null-origin 的 iframe 里 |
| Raycast | 扩展用 React 写，自定义 reconciler 生成 JSON 渲染树，按 JSON Patch 增量更新，最后由原生组件画出来 | 扩展只能发登记过的那几种消息 | Node 子进程，每个扩展一个 worker |
| Joplin | 桌面、手机都有插件 | iOS 版只允许装推荐插件（App Store 的规则） | 在手机上，插件跑在 WebView 里的 iframe 中 |

Odea 从各家拿什么：

- VS Code、Obsidian：内置功能也走公开的那套贡献点；引擎不做成插件。
- Zed：公开接口要带版本，而且越窄越好。
- SilverBullet：大多数定制靠声明和文档就够，用不着写代码，对应这里的 L0（§5.1）。
- Figma：逻辑和界面分开。QuickJS 是它被逼出来的选择，不是起点（§5.5）。
- Raycast：界面由插件交声明、宿主来画（§5.6）。
- Joplin：手机上用 iframe 做沙箱；iOS 上只开放推荐列表（§8.2）。

## 5. 插件模型

### 5.1 三档

| 档 | 是什么 | 例子 | 谁来写 | 跑在哪 | iOS 上 |
|---|---|---|---|---|---|
| L0 声明 | 清单里的数据，不带代码 | 提示块类型（标签、图标、配色）、模板（Markdown 加占位符）、主题色、命令（打开某篇、插入某个模板）、导航顺序 | 任何人 | 不执行，宿主读了照做 | 能装：它不是可执行软件 |
| L1 脚本 | 清单加一段 JS | 导入导出、批量改写、查询出来的列表视图、围栏代码块的渲染器 | 第三方 | opaque origin 的 sandboxed iframe（§5.5） | 只能从审核过的列表里装（§8.2） |
| L2 内置 | 跟应用一起编译 | 今日TODO、目标、日历、归档、反链、公式、Mermaid、表格、git 同步 | 只有 Odea 自己 | 主 WebView 里，可以带一半 Rust | 跟着应用一起过审 |

L2 的规矩：

- 和 L0、L1 用同一套贡献点注册（文档类型、导航、命令、文档槽位）。这样「关掉日程」走的就是插件停用那条路，内置功能顺带替公开接口试了刀。VS Code 的内置扩展、Obsidian 的核心插件都是这么做的。
- L2 可以做 L1 不许做的事：进编辑器的热路径（CodeMirror 扩展、表格的子编辑器），带一半 Rust（比如按日期扫任务的 `vault/tasks.rs`）。这部分是内部接口，不对外承诺。
- 第三方写不了 L2：应用不会去下载原生代码，iOS 上也不允许这么做（Apple 2.5.2）。

### 5.2 清单

现在的 `ExtensionManifest`（schemaVersion 1）只有名字、版本、分类和一串 `permissions`。升到 2：

- 加上 `api`（需要的插件 API 版本）、`platforms`、`contributes`；L1 再加 `main`、`activation`、`capabilities`。
- `permissions` 换成 `capabilities`，每一项是「一个能力加一个范围」。
- 没有 `main` 的就是 L0。

L0 的例子，加几种中文提示块：

```json
{
  "schemaVersion": 2,
  "id": "someone.callouts-cn",
  "name": "中文提示块",
  "version": "0.1.0",
  "author": "someone",
  "summary": "加几种中文的提示块。",
  "category": "appearance",
  "api": "^1.0",
  "platforms": ["desktop", "mobile"],
  "contributes": {
    "callouts": [
      { "label": "灵感", "kind": "tip", "icon": "lightbulb" },
      { "label": "风险", "kind": "warning" }
    ]
  }
}
```

L1 的例子，从网上导入书单：

```json
{
  "schemaVersion": 2,
  "id": "someone.booklist-import",
  "name": "书单导入",
  "version": "0.1.0",
  "author": "someone",
  "summary": "把网上的书单导成笔记。",
  "category": "integration",
  "api": "^1.0",
  "main": "main.js",
  "platforms": ["desktop"],
  "activation": ["command:booklist.import"],
  "capabilities": [
    { "name": "documents.create", "scope": "folder:读书" },
    { "name": "net.fetch", "hosts": ["book.example.com"] }
  ],
  "contributes": {
    "commands": [{ "id": "booklist.import", "title": "导入书单" }]
  }
}
```

几条规矩：

- `schemaVersion`（清单格式）、`api`（插件 API）、`version`（插件自己）是三个不同的版本号，各管各的。
- `capabilities` 只是申请。授权记在这台设备上，不写进仓库（§6.3）；升级时多要了能力，要重新问用户。
- 某个能力这台设备上没有（比如 iOS 上的系统通知），就只关掉用到它的那部分，不至于整个插件装不上。
- `contributes` 在激活之前就读：宿主不用执行插件代码，就知道它要加哪些命令、哪个导航项。这一套照的是 VS Code 的 contribution points 和 activation events。

### 5.3 贡献点（第一版）

| 贡献点 | 哪几档能用 | 第一个用上的 |
|---|---|---|
| `documentTypes`：类型 id、路径规则、标题、怎么新建 | L2（以后再考虑放给 L1） | 日程：`journal.day`、`journal.goal`（§6.1） |
| `nav`：导航栏的一项 | L2；L0 只能调顺序 | 今日TODO、目标、日历、归档 |
| `documentSlots`：往 `DocumentModel` 里填眉题、分段、横幅、正文后面的一段、状态栏 | L2；L1 用声明式组件填正文后面那一段 | 日历的「当日安排」、目标的周 / 月 / 年分段、归档的横幅 |
| `commands`：命令面板里的一条 | L0（打开某篇、插入某个模板）、L1、L2 | 「打开今天」 |
| `callouts` | L0 | 增强 Callout |
| `templates` | L0（Markdown 文件，加 `{{date}}` 这类占位符）；L2（带逻辑的，日程那几套留在这一档） | — |
| `theme` | L0：只能改 `globals.css` 里已有的颜色 token，值按颜色格式校验 | 主题 |
| `fenceRenderers`：某种语言的围栏代码块画成什么样 | L1（纯函数：进去的是源码，出来的是 SVG 或受限的 HTML）、L2 | Mermaid、公式（L2） |
| `importers` / `exporters` | L1 | — |
| `syncTargets` | L2 | git（GitHub、Gitee） |

第一版不开放这几样：

- L1 的行内装饰和按键处理。每敲一个键都要等沙箱回话，慢，而且会闪：宿主先把字画出来，插件的结果后到，正是 CLAUDE.md 里「先出来、再变样」的那一类问题。
- L1 自己的侧栏面板（自由面板除外，见 §5.6）。
- L1 定义新的文档类型。

围栏渲染器为什么做成纯函数：插件不碰 DOM，宿主按源码内容的哈希缓存结果。源码变了、新结果还没回来之前，接着显示上一次的结果，这和 `adapter.ts` 里 `useShownNote` 的做法一样，「中间不闪一帧」。位置、尺寸、淡入都由宿主管，动效规矩才守得住。

### 5.4 生命周期

照 Codex v2 §14 的顺序：发现 → 校验清单 → 解析依赖 → 授权 → 安装 → 按需激活 → 停用 → 卸载。落到 Odea 上再补几条：

- 每个插件有一个资源作用域。它注册的命令、订阅、视图、计时器、后台任务、能力句柄都记在它名下，停用时一次撤掉。L1 最后把整个 iframe 拆掉，里面剩下的东西也就跟着没了。
- 已经交给宿主的编辑照常存完。插件自己还没交出来的草稿，停用前先问它要；要不到，就在停用提示里说清楚。
- 订阅只发快照。要改文档，必须显式交一笔编辑，来源由宿主填（§5.5）。两个插件互相监听、互相写回会形成死循环，切断的办法是：来源是某个插件的改动，不再发回给它自己。
- 预算：每次调用都有超时（默认 5 秒），每分钟的调用次数和后台任务数都有上限。超了先警告，再超就停用并提示用户。插件出错或者卡死，都不能挡住打开文档。
- 卸载时默认保留 `.odea/plugins/<id>/` 里的设置；选「卸载并删除设置」才删。

### 5.5 第三方代码跑在哪

每个 L1 插件配一个隐藏的 `<iframe sandbox="allow-scripts">`：

- 不给 `allow-same-origin`，iframe 的 origin 就是 opaque 的：碰不到应用的 localStorage / IndexedDB，访问 `parent.document` 会抛错。
- 也不给 `allow-top-navigation`、`allow-popups`、`allow-forms`。
- srcdoc 的第一行是 CSP：`default-src 'none'; script-src 'unsafe-inline'`，网络全部关掉。要联网就走能力代理（`net.fetch`），只能访问清单里写了、用户也同意了的域名。
- iframe 挂在主窗口的 document 上，从不挪动。弹出窗口的做法是把 React 子树 portal 进子窗口（`components/Popouts.tsx`），iframe 一换 document 就会重载，状态全丢。

为什么 iframe 就够用：Tauri 的安全公告 GHSA-57fm-592m-34r7（2.0.0-beta.20 修复）之后，iframe 调不到 IPC。公告里唯一的例外是 Windows 上与窗口同源的 iframe。不加 sandbox 的 srcdoc 会继承父页面的 origin，正好落进这个例外，所以加 sandbox、保证 origin 是 opaque 的，是硬条件。Joplin 在手机上的插件就跑在 WebView 里的 iframe 中。

拒绝测试：三个桌面平台各跑一遍，全部通过之前不发布任何 L1 插件。

- iframe 里没有 `__TAURI_INTERNALS__`；`window.ipc.postMessage` 之类的调用被拒。
- 对外网的 `fetch` 被 CSP 拦下。
- 读不到应用的 localStorage、IndexedDB；用应用的频道名开 BroadcastChannel，收不到应用的消息。
- 访问 `parent.document` 抛错；改不了顶层窗口的地址，也开不了新窗口。

消息协议：

- 请求是 `{ id, method, params }`，回复是 `{ id, result }` 或 `{ id, error: { code, message } }`。`cancel` 带上要取消的请求 id。订阅返回一个句柄，用 `unsubscribe` 释放。消息可以批量发。
- 错误码至少包括：`denied`（没授权）、`unavailable`（这台设备没有这个能力）、`stale`（基线版本已经过时）、`timeout`。
- 改文档分两步：先用 `documents.read` 拿到正文和修订号，再调 `documents.edit({ ref, baseRevision, changes })`。宿主能重定位就重定位，不能就回 `stale`，不让旧结果盖掉新正文。Obsidian 的 `Vault.process` 也是这个用意。
- 「是哪个插件」「这笔改动从哪来」由宿主按 iframe 来填，插件自己写的 origin 不算数。

主线程的问题：WKWebView 里，iframe 和页面跑在同一个线程上，WebView2 里多半也是。插件跑一段长计算，编辑器就会卡。所以：

- 每次调用都有超时；
- 重活在 iframe 里另起一个 Worker 去做（opaque origin 下能不能起 Worker、在 WebKit 上行不行，P14.3 要实测）。P14.3 做的时候干脆把插件的代码全放进了 Worker（§15.3），Chrome、WebView2 上实测起得来、隔得住（§15.8），WebKit 还没测；
- 绝不让插件进输入的热路径（§5.3）。

为什么先不嵌 QuickJS（Codex v2 §10 的方案）：Figma 改用编译成 Wasm 的 QuickJS，有两个前提，Odea 一个都没有。

- Figma 的插件要同步修改一整张巨大的场景图。它第一版用 iframe，光是把大文件序列化给插件就要 14 秒。Odea 的插件只读一篇几十 KB 的 Markdown、交一份编辑意图，本来就是异步的。消息往返一次约 0.1ms（Figma 量的），一次操作只有几条消息。
- Figma 后来的 Realms 方案和宿主共用一个 JS 引擎，被找到过逃逸漏洞。iframe 则是浏览器自己的隔离边界，不是在同一个引擎里靠代理去挡。

QuickJS 留作后备。哪天要给插件提供同步接口，或者 iframe 在哪个 WebView 上隔离不住，再拿出来。

### 5.6 插件的界面

分三种：

- **文档形状的，填槽位。** `DocumentModel` 本身就是一份「文档形状的视图描述」：标题、眉题、横幅、分段、正文、状态栏。它现在有几个只属于某个功能的字段（`dayTasks`，日历和目标用的 `segments`，归档用的 `banner`），把这些换成插件能填的槽位，日历的「当日安排」就成了日程插件挂在正文后面的一段。文档类视图不用另造协议。
- **不是文档的，交声明。** L1 交一棵组件树（第一批：列表、树、表单、空状态、按钮条），宿主用 Odea 自己的 React 组件画出来，更新时按 JSON Patch 增量发送，这是 Raycast 的做法。动效、描边、像素对齐都在宿主的组件里，插件碰不到。L2 可以直接写 React，比如日历的月格子。
- **自由 HTML 面板，作为逃生口。** 一个看得见的 sandboxed iframe，由插件自己画。代价写在明处：不能弹出到别的窗口（会重载）；不保证 CLAUDE.md 里那些动效规矩；主题只提供 CSS 变量。

不做跨框架的视图协议（Codex v2 §9 的 ViewSpec）：宿主只剩 Web 一种（§7），用不着。

## 6. 一切皆文档：文件就是协议

### 6.1 文档类型和定位

`DocumentSaveTarget` 现在是三选一的联合类型：笔记（id）、某一天（日期）、某个周期的目标（周期类型加起点）。改成：

```ts
/** 仓库里的一篇。type 带命名空间，key 的格式由那个类型自己定 */
interface DocumentRef {
  type: string; // "note" | "journal.day" | "journal.goal" | …
  key: string; // 笔记 id | "2026-11-03" | "week:2026-11-02"
}
```

- 核心只认一种类型：`note`，也就是仓库里的一个 Markdown 文件。
- 其余类型由插件声明路径规则，把「路径」和「key」对应起来。日程插件声明的，正是现在 `Layout::day_path` / `goal_path` 里写死的那几条：日记是 `{days}/{YYYY}/{YYYY-MM-DD}.md`（Obsidian 的库是平放的 `{days}/{YYYY-MM-DD}.md`），目标是 `{goals}/{YYYY}/{YYYY}-W{ww}.md`、`{YYYY}-{MM}.md`、`{YYYY}.md`。文件夹的名字从 `.odea/vault.json` 的 `folders` 里取。
- Rust 这边也照这个拆：索引只认文件；「今天还没写过，就延续最近的一天」、按日期扫任务、日历上的记号，都归日程模块（L2 里 Rust 的那一半），放在一个内部的文档类型 trait 后面。`commands.rs` 里那 8 个专用命令也跟着搬过去。
- **只改代码里的类型，落盘的、经网络发给别的设备的字符串一个都不改**（2026-11-04 查过一遍）。新版和老版本会通过 git 同步、团队协作长期共存：
  - 团队协作在设备之间认同一篇，靠的是 `teamIdOf`（`team/store.ts`）：某一天是 `day-2026-11-03`，目标是 `goal-week-2026-11-02`，笔记是 `note-<id>` 或相对路径。访客本机留底的键 `guest:<主持人>:<文档>` 里也带着它。日程插件给出的团队 id 必须和现在一字不差，否则队友还在用老版本时，两边认不出是同一篇。
  - 行为日志（`.odea/activity/*.jsonl`，跟着仓库同步）的 `entity` 写的是 `day`、`goal`，照旧这么写。
  - 索引里某一天、目标的 id 是 `day:2026-11-03`、`goal:week:2026-11-02`（`vault/mod.rs`），冲突副本的 `conflictOf` 就是原文的这个 id；属性块里以 `day:`、`goal:` 开头的 id 不分给笔记（`note_id_for`）。这些都只在本机，可以改，但一改就要升索引版本让它重建，老前缀也得继续保留。最省事的是不改：`DocumentRef` 是 `{ type: "journal.day", key: "2026-11-03" }`，需要拼成字符串的时候，由日程插件给出 `day:2026-11-03`。
  - 本机记的界面状态（localStorage 的 `odea.session`）里存着区名 `today`、`goal`、`calendar`。导航项的 id 照用这几个，或者读取时映射一下；否则升级后第一次打开会退回笔记区。
  - `saveKeyOf` 生成的键只在内存里用（保存失败留下的草稿、外部改动的计数都不落盘），可以随便改。
- 做客时打开的那一篇（`SharedTarget`）不是仓库里的文档，继续留在编辑器目标的联合类型里，不进 `DocumentRef`。

### 6.2 插件不在的时候

- 停用日程：日记、目标回到文件树上，成为普通文件夹里的普通笔记。现在关掉日程就是这个效果（§3）。再打开，原样回来。
- 属性块里不认识的键原样保留（现在已经是这样）。插件写进属性块的键要带命名空间前缀（比如 `journal.mood: 好`），免得和别的工具撞上。
- 插件的设置放在 `.odea/plugins/<id>/`，停用时不删。
- 插件的索引放在应用数据目录里，按插件 id 和版本分开存，删了能重建。不拿数据库表当插件之间的接口。
- 文档里提到了某个插件的类型，不等于就可以去下载、执行那个插件。

### 6.3 Profile 就是 `.odea/vault.json`

现在它长这样（见 `vault/layout.rs`）：

```json
{
  "kind": "logical",
  "features": { "journal": true, "archive": true },
  "folders": { "notes": "笔记", "days": "日记", "goals": "目标", "archive": "归档" }
}
```

加两项：

```json
{
  "plugins": {
    "odea.journal": { "enabled": true },
    "odea.archive": { "enabled": true },
    "someone.callouts-cn": { "enabled": true, "version": "^0.1" }
  },
  "nav": ["notes", "journal.today", "journal.goal", "journal.calendar", "odea.archive"]
}
```

- `features.journal` / `archive` 变成 `plugins` 里的两项。别的设备上可能还装着老版本，老版本只认 `features`。所以新版本读的时候以 `plugins` 为准，写的时候照样也写 `features`，至少保留到老版本退场为止。
- 仓库里记的是「这个仓库要用哪些插件」，也就是一份意图，不是插件的代码，也不是授权。代码装在每台设备的应用数据目录里，授权也记在那里。一台设备授予的文件权限，不会跟着仓库带到另一台。
- 实际生效的插件，是「仓库想要的」和「这台设备装了、授了权、平台也支持的」两者的交集。缺的插件在扩展页列出来，不自动安装。

### 6.4 团队仓库：先信任，再执行

团队仓库（协同编辑 §22）靠 git 同步，`.odea/vault.json` 也跟着一起同步。队友往仓库里加一个 L1 插件，就等于往你的机器上推了一段要执行的代码。VS Code 有现成的先例：仓库里 `.vscode` 下的任务会随 clone 分发出去，所以在不受信任的文件夹里，任务、调试，以及没声明支持受限模式的扩展都不会运行（Workspace Trust）。

Odea 照这个做：同步下来的 `plugins` 里如果有这台设备没装、没授权的 L1 插件，只在扩展页和一条提示里列出来（「这个仓库想用这些插件」），用户点了才安装、才授权。L0 不执行代码，可以直接生效，但主题 token 只接受颜色值，提示块只接受现有的那几种 kind。

## 7. 跨端：按平台选引擎

### 7.1 三种引擎

Tauri 用的是每个系统自带的 WebView：

| 平台 | 引擎 | 版本由谁决定 |
|---|---|---|
| Windows | WebView2（Chromium） | 自动更新；这台机器 2026-11-03 是 151.0.4129.107 |
| macOS、iOS | WKWebView（WebKit） | 跟着系统版本走 |
| Linux | WebKitGTK | 跟着发行版走 |
| Android | 系统 WebView（Chromium） | 随应用商店更新 |

Electron 在三个桌面平台上用的都是同一个 Chromium。论一致性，Tauri 确实不如 Electron。落到 Odea 身上：

- `scripts/perf` 里的五个验证脚本都只驱动 Chrome（`cdp.mjs`）。两个输入法脚本（`table-ime.mjs`、`collab-ime.mjs`）靠 CDP 的 `Input.imeSetComposition` 模拟组字，而这个接口只有 Chromium 有，所以表格格子里、协作当中的组字，在 WebKit 上没法自动测。
- CLAUDE.md 里「先对齐再动」「描边落在整物理像素上」这两套规矩，都是在无头 Chrome 和 WebView2 上量出来的。WebKit 的图层和抗锯齿是不是同样的行为，还没量过。
- 弹出窗口在 macOS、Linux 上都没跑过（标签页与分屏 §17）；「Linux 的 WebKitGTK 动画卡顿」在技术方案 §17 的风险表里记的是「高」。
- 构建目标 `chrome110` / `safari16`（`vite.config.ts`）只管 JS 语法，管不到排版和动效。
- 好的一面是：编辑器里大部分引擎差异，CodeMirror 已经处理掉了。`@codemirror/view` 里按浏览器分支的代码有 59 处（iOS 15、Chrome 12、Android 10、Safari 8……）。而 Odea 自己的代码里，除了 Mac 快捷键的写法（`lib/platform.ts`），没有任何引擎分支。所以风险在于「没测过」，而不是「有已知的坑没处理」。

### 7.2 内存：量过的和没量过的

Windows 上量过（技术方案 §13.2、§13.3；同一台机器，按任务管理器的口径即专用工作集，算整棵进程树）：

| | 刚启动、仓库里几十篇 |
|---|---|
| Odea 0.1.0 | 200–220 MB（Rust 49 + WebView2 底座 73 + 渲染进程 80–97） |
| Odea 去掉 jieba 以后 | 147–154 MB |
| Typora 1.10（Electron） | 约 193 MB |
| Obsidian 1.10（Electron） | 约 397 MB |

WebView2 本身就是 Chromium，它底座的那几个进程和 Electron 的一样重（技术方案 §13.3 记的是 45–50 MB），而 Electron 的主进程里还多一个 Node。

最小化之后：`memory.rs` 把 WebView2 的内存目标设成 Low，30 秒后整棵进程树从 285 MB 降到 88 MB。2026-11-03 量的一个已经最小化了一阵的 Odea 是 46 MB（7 个进程）。这个接口是 WebView2 专有的，换成 CEF 以后要另想办法。

「Tauri 比 Electron 还占内存」这个说法，出处多半是 Tauri 的 issue #5889（2022）。有人把 postman.com、vscode.dev 这样的重网页分别放进两个壳里：macOS 上 Tauri 421 MB、Electron 337 MB；Ubuntu 上 581 MB 对 240 MB；Windows 上 Tauri 也高出 50–80 MB。但那是按每个进程的占用直接加总（共享内存被算了好几遍），维护者的结论是这基本上是在比 WebKit 和 Chromium。同一个帖子里改用 USS / PSS 量默认应用，两边差不多：Tauri 125 / 185 MB，Electron 118 / 207 MB。轻页面则反过来：Better Stack 在 macOS 上量到的空闲内存是 Tauri 109 MB、Electron 128 MB（Electron 那边有没有把辅助进程算进去，文章没说）。

结论：Windows 上 Tauri 和 Electron 持平；2026-11-03 把同一个前端分别放进 WebView2 和 CEF（自带一份 Chromium，和 Electron 是同一类）对照，WebView2 还少 9–16%（§7.6）；11-10 发现那次的配置目录被 MSIX 重定向拖累，挪开以后重量，WebView2 少 4–5%（§7.7）。macOS、Linux 上 Odea 还没量过，WebKit 跑重页面有可能比 Chromium 更占内存。量的口径：

- Windows 用专用工作集；
- macOS 用物理内存占用（phys_footprint），并且把 `com.apple.WebKit.*` 那几个进程算进来，活动监视器不会把它们挂在应用名下；
- Linux 用 PSS。

### 7.3 每个平台用哪个

Tauri 官方在 v3 这条线上做了 CEF 运行时：`tauri-runtime-cef` 从 2026-09-13 的 3.0.0-alpha.0 发到 10-14 的 alpha.6、11-06 的 alpha.7（和 tauri 3.0.0-alpha.6 一起发布，CEF 还是钉在 154），目标平台是 x64 的 Windows、macOS、Linux。Tauri 2 这条线还在继续出补丁（2.12.5，10-21）。也就是说，「用系统 WebView 还是自带 Chromium」正在变成 Tauri 里的一个选项，不用为此换框架。

| 平台 | 用哪个 | 为什么 |
|---|---|---|
| Windows | WebView2 | 本来就是 Chromium，引擎、内存都和 Electron 一样；安装包只有 9.2 MB。换成 CEF 的话安装包 130 MB，而且 Tauri 的 CEF 运行时在 Windows 上不开 Chromium 的进程沙箱（§7.7） |
| Linux | CEF（还要真机对照 WebKitGTK 的动画再定） | WebKitGTK 是已经记下来的最弱一环；AppImage 现在已经 88 MB，再带上 Chromium 体积代价不大。沙箱：deb / rpm 装上 setuid 的 `chrome-sandbox`，照开；AppImage 在 Ubuntu 23.10 以后开不了（AppArmor 限制了非特权的用户命名空间，运行时检测到就关掉沙箱），换 CEF 时 Linux 要以 deb / rpm 为主（§7.7） |
| macOS | 实测以后再定：WKWebView 或 CEF | 动效和输入法的规矩都是在 Chromium 上量的，要在 Mac 上过一遍动效和中文输入法。换 CEF 的话，dmg 从 12 MB 涨到上百 MB（Obsidian 1.15.0 的 dmg 是 222 MB） |
| Android | 系统 WebView | 就是 Chromium |
| iOS | WKWebView | Apple 只允许 WebKit（2.5.6） |

这样一来：

- Windows、Linux、Android 都是 Chromium，macOS 选 CEF 的话也是，一致性和 Electron 一样；
- Rust 核心、169 个命令、插件沙箱都不用动；
- `scripts/perf` 那几个 CDP 脚本在所有 Chromium 平台上都能用。

只有 iOS，以及选了 WKWebView 的 macOS，需要另外测。

技术方案 §13.1 里「安装包 < 20MB」的目标，以后只对 Windows 还成立；Linux、macOS 用 CEF 的话，按新量出来的数改。

CEF 运行时还在 alpha，而且要换到 Tauri 3（2026-11-03 查的，§7.6 的试验用的就是这一套；11-10 又查了一遍，§7.7）：

- Tauri 3 的 `Builder::default()` 是类型擦除的 `DynRuntime`：运行时在启动时用 `.runtime(tauri_runtime_wry::Wry::default())` 或 `.runtime(tauri_runtime_cef::Cef::default())` 选，`AppHandle`、`Window` 不用再带运行时的类型参数。一个二进制里两个运行时可以都带着，按平台、甚至按启动参数选，「按平台选引擎」在 Tauri 3 里就是一行。Odea 的 Rust 里显式写了 31 处 `tauri::Wry`，迁过去改成默认的就行。
- 现在用的六个 Tauri 插件（opener、dialog、window-state、updater、deep-link、single-instance）都有 3.0 的 alpha。
- tauri-specta 没有 3.x（11-10 最新的还是 10-21 的 2.0.0-rc.26，specta 本身 11-05 出了 2.0.0-rc.28）。Odea 的 169 个命令和事件的类型绑定都靠它，迁 Tauri 3 时这是最大的一块。Tauri 3 自己的 `specta` 开关只给 `Channel` 这几个类型加上 `specta::Type`，替代不了它。
- 前端的 `@tauri-apps/api` 也要一起换：Tauri 3 的 CLI 打包前会比对它和 tauri crate 的版本，2.11 对 3.0 直接报错停下（§7.7）。
- 社区里那个对着 Tauri 2 编译的版本（SpikeHD/tauri-runtime-cef），README 写着只在 Linux（X11）上验过，Windows、macOS 是照着改的、没跑过，所以试验用的是官方版本。

所以 Odea 本身先不迁，等 CEF 运行时和 tauri-specta 都有能用的版本；在那之前，Linux 继续用 WebKitGTK。

### 7.4 一致性怎么验

| 平台 | 自动测 | 手动测 |
|---|---|---|
| Chromium（Windows、Android，以及用 CEF 的 Linux / macOS） | `scripts/perf` 的脚本照跑；要对着真正的 WebView 跑，就开远程调试端口（WebView2 和 CEF 都支持） | 用真的系统输入法打中文（CDP 模拟的组字不经过输入法） |
| WebKit（iOS，以及用 WKWebView 的 macOS） | 不涉及输入法的逻辑、排版测试，可以放到 Playwright 的 WebKit 上跑 | 在真机上过一遍：动效逐帧、中文输入法（正文、表格格子、弹出窗口）、1 倍和 2 倍屏 |

内存在每个平台上发版前都量一次，口径照 §7.2。

已经验过（2026-11-03，§7.6）：`fade-frames.mjs`、`table-ime.mjs` 加上环境变量 `CDP_ATTACH=端口` 以后，能接到开着的 CEF、WebView2 外壳上跑，不用自己起无头 Chrome，结果和无头 Chrome 一样。

### 7.5 为什么不是 Electron，也不是 GPUI

**Electron。** 好处是今天就稳定可用，三个桌面平台是同一个 Chromium。代价：

- 169 个命令的 IPC 要改成 napi-rs 原生模块，或者一个单独的辅助进程，tauri-specta 生成的绑定作废；
- 六个 Tauri 插件（更新、深链、单实例、对话框、窗口位置、打开外部链接）都要换掉；
- Windows 安装包从 9.2 MB 涨到 100 MB 以上，主进程还多一个 Node（技术方案 §13.3 估计约 20 MB）；
- 手机端还是得另找一个壳。

只有在 CEF 运行时停滞、而 Linux / macOS 的一致性问题又等不了的时候，才考虑 Electron。

**GPUI**（2026-11-03 查的上游）：

- 桌面已经成熟：Zed 已经发了 1.0；Windows 上的文字支持 ClearType（`gpui_windows/src/direct_write.rs` 会按系统设置在 ClearType 和灰度之间选）。
- 手机才刚起步：`gpui_ios`（UIKit、CoreText、Metal、原生文字输入）2026-10-14 才进 Zed 仓库，到今天 9 个提交；`gpui_web` 在做；上游没有 Android，只有第三方的 gpui-mobile，还很早期。
- 接口不稳：README 写着还没到 1.0，版本之间经常有破坏性改动；crates.io 上的 gpui 停在 2025-10 的 0.2.2，实际上只能跟着 Zed 主干走。
- 一致性并不比 Chromium 好：它的布局在各平台一致，但字形还是交给各个系统去画（DirectWrite、CoreText……），这一点和 Chromium 一样。它真正的好处是没有浏览器那几个进程（WebView2 底座就有 45–50 MB），性能上限也更高。
- 代价是重写。要换掉的有：CodeMirror / Lezer 这套编辑器引擎（打包后约 2.7 万行）、Odea 自己的编辑器（2.1 万行）、KaTeX（1.6 万行）、Mermaid（打包后约 8.3 万行）、HTML 表格。插件的界面也不能再用 Web 技术来写。Codex v1 自己排的 P0–P5 本身就是一次重写。

什么时候再评估 GPUI：`gpui_ios` 能用了、上游有了 Android、接口到了 1.0，同时 Odea 碰上了 Web 解决不了的问题（比如几 MB 长文的输入延迟）。

v1 里有一部分不依赖 GPUI：一篇文档只有一个写入口（DocumentSession）；每个视图有自己的撤销作用域；正文、表格格子、公式源码都是同一篇文档的可编辑投影（EditSurface）；组字统一用一个状态机（CompositionSession）。这些在现在的 Web 栈里一样能做，放到 P14 之后另开一期。

**换 CEF 之前要处理的三件事**（这次新查出来的）：

1. **Windows 上没有进程沙箱。** CEF 的 GPU、渲染、工具进程全带着 `--no-sandbox`（装好的、开发版都是），WebView2 的一个都没有。tauri-runtime-cef 的 `src/sandbox.rs` 写明了原因：Chromium 在 Windows 上的沙箱要由 exe 来当代理，从 M138 起只有 Chromium 自己的工具链编出来的程序能链接这个入口，所以 CEF 带了 `bootstrap.exe` / `bootstrapc.exe`，要把应用编成 DLL 由它们载入。Tauri 应用编出来是 exe，拿不到要传的那个指针，只好不开（安装包里那两个 bootstrap 程序带着，但没用上）。
   - Linux：deb、rpm 装上 setuid 的 `chrome-sandbox`，能开。AppImage 挂载时带 nosuid，只能靠非特权的用户命名空间，Ubuntu 23.10 起 AppArmor 限制了它，运行时检测到就把沙箱关掉。
   - 对 Odea 的影响：P14.3 的插件跑在 sandboxed iframe 里的 Worker 中（§15.3），那是 Blink 里面的隔离；渲染进程的系统沙箱是外面兜底的那一层。没有它，渲染进程一旦被打穿，拿到的就是用户的全部权限。
2. **会装别的软件登记给 Chrome 的扩展。** CEF 154 默认是 Chrome 风格，会读 Chrome 的外部扩展登记（Windows 上是注册表的 `Software\Google\Chrome\Extensions`）。这台机器上登记了三个：迅雷下载支持、电脑管家上网防护（都指向本地的 crx），Adobe Acrobat（只写了 Chrome 应用商店的更新地址）。
   - 用全新的配置目录起一次，三个都装进了 `Default\Extensions`，Adobe 那个是从 Google 的更新服务器下载下来的。
   - 三个的停用原因都是 8192（外部装进来的、等用户确认），没有在页面里跑。CEF 里没有让用户确认的界面，所以会一直停着，但每台机器上装什么取决于别的软件。
   - WebView2 不读这个注册表（它的配置目录里只有微软自带的两个）。加上 `--disable-extensions` 以后一个都不装，只剩 Chromium 自带的 PDF 查看器。
3. **`Intl` 的默认语言变成 en-US。** 运行时没设 `locale` 时，CEF 自己加上 `--lang=en-US`（打包器也只带 en-US 的语言包）。运行时会按系统设置填 `Accept-Language`，所以 `navigator.language` 还是 zh-CN；但不写语言的格式化、排序都按英文。浏览器进程实际的命令行是 `--no-sandbox --lang=en-US --log-file=… --log-severity=warning --disable-features=GlicActorUi,AutofillActorMode,LensOverlay,KillOnInvalidNavigationHeaders --no-first-run`，再加上外壳传的那几个开关。

   | | WebView2 | CEF |
   |---|---|---|
   | `Intl.DateTimeFormat().resolvedOptions().locale` | zh-CN | en-US |
   | `toLocaleDateString()` | 2026/11/10 | 11/10/2026 |
   | `toLocaleDateString(undefined, { dateStyle: "full" })` | 2026年11月10日星期二 | Tuesday, November 10, 2026 |
   | `toLocaleTimeString()` | 15:04:00 | 3:04:00 PM |
   | `new Intl.Collator()` 排「张 阿 李 b A」 | 阿李张Ab | Ab张李阿 |
   | `navigator.languages` | zh-CN, en, en-GB, en-US | zh-CN |

   写明 `zh-Hans-CN` 的两边一样（ICU 数据是全的）。Odea 的文件列表、目录树、文件夹选择、表格排序都写了；没写的只有协作主持人给访客排目录树的 `new Intl.Collator()`（`src/collab/store.ts`）。要改 CEF 的默认语言，得 `Cef::locale("zh-CN")` 加上自己带 zh-CN 的语言包，没试。

**踩到的。**

- tauri-runtime-cef 的 `command_line_arg`：带值的开关名字前面不用写 `--`；不带值的必须自己写 `--`，不然被当成普通参数加进去、什么都不发生（`disable-extensions` 不管用，`--disable-extensions` 才管用）。
- `Browser.getBrowserCommandLine` 要先加上 `--enable-automation` 才会返回。
- 从 Claude 起的进程，`%LOCALAPPDATA%` 被 MSIX 重定向，量启动时间、内存都要把配置目录放到 `%TEMP%`（上面的更正就是这个）。Tauri 3 的 CLI 觉得 NSIS 的版本不对，会在 `%LOCALAPPDATA%\tauri\NSIS` 下重下一份（nsis-3.13），从这里跑的话那一份写进了容器里。

**结论（替换 §7.6 的）。**

- Windows：CEF 和 WebView2 启动一样快，内存多 4–5%，动效、组字的结果一样。真正的差别是安装包 130 MB 对 9.2 MB、没有进程沙箱，还要关扩展、处理默认语言。继续用 WebView2，理由从「慢、占内存」换成「大、没有沙箱」。
- Linux：动画的对照还没做，要真机。真换 CEF 的话：以 deb / rpm 为主（才有沙箱），加 `--disable-extensions`，处理默认语言，打包器的文件清单要等上游修（或者自己补上）。
- 以后要再量，配置目录一律放在不被重定向的地方。

**没做的。** Linux 真机；macOS；把 Odea 整个迁到 Tauri 3；打包器的文件清单、Windows 沙箱这两件事没去上游查有没有人报过；带上 zh-CN 的语言包、设 `locale` 以后 `Intl` 跟不跟着变，没验。

## 8. 手机

### 8.1 先把现在的应用原样编上去

Tauri 从 2.0 起能出 iOS、Android 的包，但官方在 2.0 RC 时就说过，这一版还不是「手机一等公民」，桌面的插件也没有全部移植过去。所以第一步（P14.5）不改架构，先把现在的应用原样编到手机上，逐项记下结论：

| 项 | 要看什么 |
|---|---|
| Rust 编不编得过 | git2 的 https 在 iOS、Android 上需要 OpenSSL（macOS 现在用的是 vendored 的）；iroh、rusqlite、notify；钥匙串（`keyring-core` 在 iOS 上走 Keychain，Android 要另找存储）。`Cargo.toml` 里已经为手机排除了 single-instance |
| 文件 | 默认仓库放在应用自己的目录里（iOS 上再在「文件」App 里露出来）；Android 上用户选的文件夹由 SAF 给出的是 URI，不是普通路径，原子替换、文件监听都要重新确认 |
| 前后台 | 进后台之前，把编辑器里的内容和存盘失败留下的草稿写盘；不指望手机在后台继续主持协作 |
| 输入 | 软键盘挡住的区域、触摸选区、手机上的中文输入法（CodeMirror 里 iOS 的 15 处、Android 的 10 处分支就是管这些的） |
| 局域网 | iOS 上用 mDNS 和本地网络要写权限说明（协作里的「附近」用得到） |
| 窗口 | 手机上一个仓库一个界面，没有弹出窗口；平板再考虑分屏 |
| 更新、深链 | 更新走应用商店，`updater` 只在桌面用；`odea://` 换成通用链接 / App Links |
| 内存 | 按 §7.2 的口径量 |

### 8.2 插件在手机上

- **iOS。** Apple 4.7 允许插件，但有条件：
  - 4.7.2：没有 Apple 的许可，不能把原生平台 API 暴露给下载来的插件；
  - 4.7.3：插件要拿数据、拿隐私权限，必须对每个插件分别取得用户明确同意；
  - 4.7.4：应用里要有插件的索引和通用链接；
  - 4.7.1：要能举报、能屏蔽。

  Joplin 的 iOS 版因此只允许装推荐插件。Odea 照这个做：L0 照常可用；L1 只能从审核过的列表里装，能力表里去掉原生能力（系统通知、剪贴板，Joplin 也提过要关剪贴板），每个插件第一次要数据时单独问用户。
- **Android。** Google Play 的「设备和网络滥用」政策禁止下载可执行代码，但对跑在 WebView 这类解释器里的 JavaScript 有例外。L1 可以和桌面一样，上架前对照官方页面再核一遍。

### 8.3 宿主环境不只是 isMobile

照 Codex v2 §11：宿主提供给插件和界面的环境，至少要包括可用的屏幕空间、输入方式（触摸、笔、鼠标、键盘可能同时存在）、软键盘占了多少地方、安全区、前台还是后台、内存紧不紧、这台设备有哪些能力。平板可能接着键盘和鼠标，桌面也可能有触屏，不能只靠一个 `isMobile` 决定所有行为。

### 13.3 和设计稿不一样的地方

- **贡献点比 §5.3 多几样**，都只给 L2：`toggle`（命令面板、仓库菜单里开关它的那一条）、`Effects`（插件开着时跟着主窗口挂着的副作用组件）、`applyChange` / `reset` / `reindexed`（别处改了文件、开关换了、后台读完文件时，缓存怎么办）、`loadMock`（浏览器预览里它的那一份）。`documentSlots` 落成了 `DocumentModel` 上的几个字段：`segments.onChange`、`afterBody`、`templates`（连同模板选择器的标题、空文档的提示）、`eyebrowAccessory`。`banner` 留在核心，归档在用
- **8 个专用命令没有全搬**：6 个进了日程；`journal_list` 成了核心的 `doc_list`（命令面板按标题搜所有插件的文档），`vault_set_journal` 成了 `vault_set_plugin`。日程切换器的两个命令、一个事件也换成了通用的（§13.1）

### 13.4 踩到的

- **`fitLayout` 把停在「扩展」页的人踢回了「文件」**：一开始写成「不认识的页都回到文件」，开关插件时停在扩展页的也被踢走，0.7.0 不会这样。现在扩展页一直算在，补了测试

### 14.2 清单

照 §5.2 的样子，没有 `main` 的就是 L0。顶层字段：`schemaVersion`（2）、`id`、`name`、`version`（三段）、`author`、`summary`、`category`、`api`（`^1.0` 这样的范围）、`contributes`；选填 `description`、`homepage`（只能 http(s)）、`icon`、`platforms`（`desktop` / `mobile`）、`$schema`。

```json
{
  "schemaVersion": 2,
  "id": "someone.weekly",
  "name": "周会",
  "version": "0.1.0",
  "author": "someone",
  "summary": "周会模板，主色换成青绿，日历放到最前面。",
  "category": "productivity",
  "api": "^1.0",
  "contributes": {
    "callouts": [{ "label": "决定", "aliases": ["decision"], "kind": "important", "icon": "flag" }],
    "templates": [
      { "name": "周会", "description": "议题、决定、待办", "body": "**时间**：{{date:YYYY年M月D日}} {{weekday}}\n\n## 议题\n\n{{cursor}}\n" },
      { "name": "日报", "scope": "day", "body": "## {{date}}\n\n- [ ] " }
    ],
    "theme": { "light": { "accent": "#0a7d5a" }, "dark": { "accent": "#5cc39b" } },
    "navOrder": ["calendar", "today"]
  }
}
```

校验的规矩：

- **写坏了报出是哪个字段**，整句是「清单里 `contributes.callouts[1].kind` 不对：只能是 note、tip、important、warning、caution、generic，写的是 "red"」；缺字段是「清单里缺 `contributes.templates[0].body`」；不是 JSON 的报 JSON 自己的位置。一个都不装，不装一半
- **不认识的字段也报**（§5.2 没说）：同一个 `api` 版本下字段是定死的，拼错了的字段悄悄不起作用比报错难查。以后加字段就升 `api` 的次版本，老版本按 `api` 拒掉
- 设计稿里有、这一版还没做的贡献点（`commands`、`fenceRenderers`、`importers`……）报「这个贡献点这个版本还不支持」；带 `main` / `activation` / `capabilities` 的报「带脚本的插件（L1）这个版本还装不了」；`permissions` 报「这是 schemaVersion 1 的写法」；`schemaVersion: 1` 报「旧格式，没有 contributes」
- `contributes` 空的报「这个插件什么都不加」
- `odea.` 开头的 id 留给官方（内置插件也在这底下）
- 存储里的清单每次读出来都再校验一遍：这个版本的 Odea 不再认它（比如导航项改了名字），就列成坏了的

### 14.3 四个贡献点怎么落的

| 贡献点 | 清单里 | 落到哪 | 停用以后 |
|---|---|---|---|
| 提示块 `callouts` | `label`（写在 `> [!标签]` 里，不能有方括号、换行）、`aliases`、`kind`（只能是已有的六种配色）、`icon`（只能从 `CALLOUT_ICONS` 里挑，不收 SVG） | `editor/callout.ts` 的标签表：插件登记的先查，再查内置的（同一个标签插件说了算，两个插件撞了先装的说了算）。编辑器两层装饰记着版本号，变了整篇重画 | 标签回到中性的样子（`is-generic`），正文一个字不动 |
| 模板 `templates` | `name`、`description`、`scope`（`note`，或者内置插件声明的模板槽位：日程的 day / week / month / year）、`body`（Markdown，≤ 64 KB）。占位符只认 `{{date}}`、`{{date:YYYY年M月D日}}`（YYYY / YY / MM / M / DD / D / ww / w）、`{{time}}`、`{{weekday}}`、`{{title}}`、`{{cursor}}`（至多一个），别的报错 | 换成 `DocTemplate` 交给注册表，排在内置插件的模板后面。笔记现在也有模板槽位：一个都没有时不弹菜单、`/` 菜单里也不列「模板」，和以前一样 | 模板菜单里少了那几个 |
| 主题 `theme` | `light` / `dark` 各一组 token → 颜色；token 只能是 globals.css 里亮、暗两套都有的 21 个颜色；值只收十六进制和 `rgb()` / `hsl()` / `oklch()` 这类颜色函数（括号里不许有括号、分号、引号，塞不进别的 CSS） | `<head>` 最后一个 `<style id="odea-plugin-theme">`：`:root[data-theme="light"] { --color-…: … }`，暗色同理。后开的插件说了算。弹出窗口抄 `<head>` 的样式（`app/popout.ts` 的 `mirrorDocument`），跟着变 | `<style>` 拿掉 |
| 导航顺序 `navOrder` | 导航项的 id（`notes`、`today`、`goal`、`calendar`、`archive`、`extensions`，以后插件的也算） | 列出来的排在前面，没列的照原来的先后跟在后面（`registry.navIds`）。窄栏、切页时内容往哪边挪都按它；窄栏换了顺序照旧是 FLIP 滑过去（`useNavRows`） | 回到原来的先后 |

主题、提示块第一帧就是对的：桌面端在挂上 React 之前就取到了仓库的摆法（`main.tsx` 等 `initialize`），装着的清单是同步读的，`initDeclaredPlugins` 在那之前订阅好，摆法一进 store 就换上。不会先画默认的主色再变（CLAUDE.md「先出来、再变样」那一类）。

### 14.4 装在设备上，开在仓库里

- **装**（这台设备）：清单拷进 localStorage。从扩展页装的同时在当前仓库里开上
- **启用 / 停用**（这个仓库）：`.odea/vault.json` 的 `plugins` 里它那一项，`{ "enabled": true, "version": "^0.1" }`，跟着仓库同步。版本范围在装上、启用时按装着的版本写（`0.x` 写到次版本，否则写到主版本）；对不上只在卡片上提示一句，照样生效（L0 只是声明，版本差一点也不会出事）
- **卸载**（这台设备）：只删本机的清单，仓库里记的不动 —— 团队仓库里别人可能还开着它，卸载不该替整个团队关掉。这时它出现在扩展页最上面「这个仓库想用」：官方的可以点「安装」装回来；都可以点「不用了」在这个仓库里关掉
- 写标记前先把内置开关写实（`marker_written`）：老标记（`plugins`、`features` 都没有）只多出一个 `plugins` 的话，日程、归档就成了「没写 = 关着」
- 标记里的第三方插件只报给前端，不认文档类型、不影响文件怎么认，不进 `fingerprint`，索引不重建。别的设备开关了（同步过来）也算标记变了，照旧问「切换过去」（`check_layout` 比较的样子里加上了它们）；自己开关的，`set_extension` 写完就把 `self.layout.extensions` 换成新的，文件监听再看到不当成别处改的
- §6.4 的「先信任、再执行」：L0 不执行代码，仓库里开着、这台也装着就直接生效；没装的不会自己去装，只列在「这个仓库想用」里

### 14.5 和设计稿不一样的地方

- **清单存在 localStorage，不是应用数据目录里的文件**（§6.3）：L0 只有一份 JSON；localStorage 本来就在应用自己的数据目录里、按设备分，几个窗口之间有 `storage` 事件可以跟着换，Rust 那边也用不着它。L1 带脚本以后（P14.3）再看要不要挪进文件（P14.3：脚本也先放在 localStorage，§15.6）
- **`.odea/vault.json` 的 `nav` 没做**：导航顺序由 L0 插件的 `navOrder` 给，插件本身就按仓库开，效果一样；还没有拖着排窄栏的界面
- **贡献点 `commands`（L0 的「打开某篇」「插入某个模板」）没做**：§10 这一期只列了提示块、模板、主题、导航顺序
- **内置的日程也在扩展页里开关**：和命令面板、仓库菜单里的「启用 / 关闭日程」是同一件事（`setPlugin`）。归档还在核心里，没列
- **扩展页没有搜索、分类筛选了**：插件就这么几个；分类在官方目录的卡片上写着
- **「增强 Callout」加的是九种**：摘要、待办、完成、问题、失败、缺陷、例子、引用、灵感，英文别名和 Obsidian 的提示块类型对得上（`summary`、`todo`、`question`、`bug`……），从 Obsidian 搬过来的笔记不再都是灰的。另带一个「笔记模板」（会议记录、读书笔记、复盘），给模板这个贡献点一个真用得上的例子

### 14.6 踩到的

- **主题要压得过 globals.css 的暗色**：亮色的 token 在 `@theme` 里（Tailwind 放进 `@layer theme`，不分层的规则都压得过它）；暗色是不分层的 `:root[data-theme="dark"]` 和 `@media … :root:not([data-theme="light"])`，权重都是 (0,2,0)。插件的暗色那组得写成同样的 `:root[data-theme="dark"]`、放在 `<head>` 最后，靠先后压住；亮色那组照着写成 `[data-theme="light"]`，免得暗色时也带上。`applyTheme` 总在 `<html>` 上落一个明确的 `data-theme`，所以只写这两条
- **编辑器缓存的状态**：切走的那一篇的 `EditorState` 留在缓存里（`stateCache`），块级装饰在 StateField 里。开关插件时它不在页面上，收不到通知；所以版本号记在 StateField 的值里，切回来那一笔换 session 的事务一到就重建
- **徽章的 `eq` 要比图标**：同一个标签、同一种配色，只是图标换了，不比的话 CodeMirror 沿用旧的 DOM
- **编辑器不依赖数据层**：模板变了一开始想让编辑器订阅 `useDeclared`，那样编辑器分包要带上 `data/store`。改成注册表自己发通知（`onTemplatesChange`），编辑器 `useSyncExternalStore` 订阅
- **笔记一直有模板槽位**：开关带模板的插件时编辑器不用重挂；没有模板时 `/模板` 不弹、`/` 菜单不列，行为和以前一样
- **提示条的文案**：别的设备改了标记时那一条写的是「（日程、目录的样子）」，现在开关第三方插件也会弹它，改成「（开了哪些插件、目录的样子）」（`components/ErrorToast.tsx`）
- **「想用但没装」那张卡**一开始标着「这个仓库没开」，下面「官方插件」里又列了一遍：改成「这台设备没装」，官方目录里不再重复
- **图标尺寸 13 不在档位上**（`styles/uiScale.test.ts`，排版规范的图标档位），改成 12
- **浏览器预览里测提示块**：在 `> [!x]` 那一行回车两次还在引用里（编辑器在空的 `> ` 行上照样续行，原来就这样），接着打的 `> [!y]` 成了嵌套的引用。测试内容改用粘贴

- `main`：同一个文件夹里的一个 `.js` 文件名，不许带路径。有它就是 L1
- `activation`：`startup`、`command:<id>`、`slot:<id>`，id 要在 `contributes` 里声明过。不写就是用到哪个贡献点时（命令、槽位都算）；既没命令也没槽位、又没写 `startup` 的报「什么时候都不会启动」
- `capabilities`：这一版两样。`documents.read` 的范围是 `current`（窗格里开着的那几篇）或 `vault`（仓库里所有的笔记和日程）；`documents.edit` 只有 `current`。`reason` 写在授权对话框里。`net.fetch`、`storage` 这些设计稿里有的报「这个版本的 Odea 还没有」（先于「不认识的字段」报：设计稿里的 `net.fetch` 带 `hosts`）
- `commands`、`documentSlots` 只有带 `main` 的才能写（没有脚本，谁来接）；`documentSlots[].slot` 现在只有 `afterBody`
- L0 的四样（提示块、模板、主题、导航顺序）L1 照样能带，宿主照样只读声明
- 插件 API 1.0 的清单照旧认（1.1 是 1.0 加东西）

### 15.3 沙箱

```
主窗口（应用的 origin）                 iframe（opaque origin）            Worker（继承 iframe 的 origin 和 CSP）
PluginRuntime ── Endpoint ── MessagePort ── relayMain ── postMessage ── workerMain（odea）+ 插件的 main.js
```

- **为什么 iframe 里还要一个 Worker**（§5.5 只写了 iframe）：
  - 死循环。WebView2 里 iframe 和页面多半在同一个线程上，插件在 iframe 主线程上 `while (true)`，整个应用就不动了，宿主的超时也触发不了。跑在 Worker 里，卡住的只是那个线程（实测见 §15.8）
  - 导航。sandbox 拦不住 iframe 导航它自己，CSP 也不管导航：iframe 主线程上的脚本能 `location = "https://…?数据"` 把东西带出去。Worker 碰不到 `location` 和 DOM
  - 所以 iframe 主线程上只有宿主自己的那一段中转（`relay.ts`），插件的代码一行都不在那儿。起不了 Worker 的内核不退回到 iframe 主线程跑，直接报「这台设备上起不了插件的后台线程」
- **iframe 的文档不能是 srcdoc**：srcdoc（还有 blob:、data:）继承父页面的 CSP。桌面端应用的 `script-src` 只有 `'self' 'wasm-unsafe-eval'` 加 Tauri 算的哈希，沙箱里的内联脚本一行都跑不了；要放开就得放开整个应用。所以桌面端由 Rust 的自定义协议 `odea-plugin://localhost/sandbox.html`（Windows 上是 `http://odea-plugin.localhost/sandbox.html`）发一份，响应头带它自己的 CSP：`default-src 'none'; script-src 'unsafe-inline' blob:; worker-src blob:; sandbox allow-scripts`。浏览器预览的页面本来没有 CSP，就用 srcdoc，文档是同一个文件（`sandbox.html`，Rust 那边 `include_str!`），里面的 `<meta>` 带着同样的 CSP
- **IPC**：Tauri 2.11 的初始化脚本（`__TAURI_INTERNALS__`，里面有 invoke key）标着只注入主框架（`manager/webview.rs` 的 `for_main_frame_only: true`），**但 Windows 上 wry 一律注入子框架**（wry 0.55 `webview2/mod.rs`：「scripts are always added to subframes regardless of the `for_main_frame_only` option」）—— 这就是 GHSA-57fm-592m-34r7 说的 Windows 例外。所以 Windows 上 iframe 主线程里看得见 `__TAURI_INTERNALS__`、`window.ipc`、`chrome.webview`。实测调不通：`ipc.localhost` 的 fetch 被沙箱的 CSP（`default-src 'none'`）拦下，Tauri 退回 `postMessage` 也一直没有回应，读、写两个命令都没生效，仓库标记没变（§15.8）。插件的代码不在 iframe 主线程上，Worker 里这些一样都没有 —— 这是把插件放进 Worker 的又一个理由
- **握手**：iframe 起来先给父页面发「ready」；宿主认准 `event.source === iframe.contentWindow`，新开一条 MessageChannel，把中转的源码、Worker 的源码和一头端口交过去。之后两边只走这条端口，window 上的消息一概不认。中转、`odea` 都是 TS 里自成一体的函数，`toString()` 拼成源码，单测能直接测
- 插件的脚本在宿主发来 `activate` 时由 Worker `importScripts` 一个 blob 地址载进来（CSP 的 `script-src blob:`）：脚本写错了是 `activate` 回一个错，不是整个 Worker 起不来，扩展页上报得出「脚本出错了：……」
- iframe 挂在主窗口的 document 上，`display: none`，从不挪动：弹出窗口里的槽位照样画（槽位是宿主的 React 组件，数据从 store 来），iframe 不跟着挪

### 15.4 协议、能力、预算

- 消息：请求 `{ id, method, params }`，回复 `{ id, result }` / `{ id, error: { code, message } }`，通知 `{ method, params }`。一个微任务里攒下的几条合成一个数组发。超时、取消都给对面发 `cancel`，对面把那个请求的 `AbortSignal` 拨掉、回 `cancelled`，晚到的回复丢掉
- 错误码：`denied`、`unavailable`、`stale`、`busy`（输入法正在组字）、`timeout`、`cancelled`、`invalid`、`not_found`、`budget`、`failed`
- 插件 → 宿主：`documents.current`、`documents.read`、`documents.list`、`documents.edit`、`subscribe`（`documents.current` / `documents.changed`）、`unsubscribe`、`slots.update`（整棵或者 JSON Patch）、`ui.notify`。插件只是借 `log` 通知报错
- 宿主 → 插件：`activate`、`deactivate`、`commands.run`、`slots.render`、`slots.action`、`ping`
- 能力按 iframe 认是哪个插件，插件自己说的不算：清单里没申请的回「清单里没申请……」，用户没同意的回「这台设备上没同意它……」。`current` 的范围就是看得见的那几篇（`DocumentView` 登记的），做客的那一篇（别人的文档）不登记，插件看不到
- 预算（`LIMITS`）：宿主问插件每一次 5 秒超时（`activate` 10 秒，`deactivate` 1 秒）；10 秒一次心跳；插件一分钟最多调 1200 次、同时挂着最多 32 个、订阅最多 16 个、提示条一分钟最多 5 条。超时、超了一分钟的次数各算一次犯规：第一次提示条里警告，第二次停下它（`stopped`，不改仓库里的开关，扩展页里「重新启动」）
- 宿主从不在打开文档的路上等插件：槽位异步要，要回来之前接着显示上一棵（切走又切回来的那一篇先显示记着的那一棵），插件出错、卡住只是那一段空着或者是旧的

### 15.5 改正文

- 读：`documents.read` 给正文和修订号。看得见的从编辑器里读实时的（还没存盘的也算）；看不见的（`vault` 范围）读存着的，修订号是 `saved:<指纹>`，改不了
- 改：`documents.edit(ref, baseRevision, changes)`，`changes` 是按那一版算的 `[{ from, to, insert }]`。修订号按编辑器实例记（`editor/pluginEdits.ts`），这个编辑器里每改一笔都算（打字、撤销、另一个窗格转过来的、协作别人的、外部回填的）。那以后改过的：插件要改的地方没被碰过，就把它的改动挪到现在的正文上（`ChangeSet.map`）；碰过了回 `stale`，插件重新读一遍再改。编辑器换了一个（切走又切回来）旧的修订号一律过时
- 改动和打字走同一条路：一笔事务（`userEvent: "plugin.edit"`），进撤销历史（Ctrl+Z 一下撤掉）、转给另一个窗格、经协作发给别人、自动存盘。只读的（协作的旁观者）回 `denied`，输入法正在组字回 `busy`

### 15.6 和设计稿不一样的地方

- **脚本跑在 iframe 里的 Worker 中**，不在 iframe 主线程上（§15.3）。§5.5「重活另起一个 Worker」变成了「插件全在 Worker 里」
- **iframe 的文档从自定义协议发**，不是 srcdoc（§15.3）。§5.5 写的「srcdoc 的第一行是 CSP」在桌面端行不通
- **声明式视图第一批多了几样**：§5.6 列的列表、树、表单、空状态、按钮条之外，加了排版用的 stack、heading、text、stats、divider。没做 Raycast 那样的 reconciler，插件交整棵或者 JSON Patch
- **L1 的槽位只有 `afterBody`**（§5.3 本来就只给 L1 这一个）。L1 自己的侧栏面板、自由 HTML 面板都没做
- **能力只有两样**：`documents.read`（current / vault）、`documents.edit`（current）。`documents.create`、`net.fetch`、`storage`、剪贴板、通知都没做；`.odea/plugins/<id>/` 的插件设置（§5.4、§6.2）也没做
- **脚本存在 localStorage**（§14.5 留的问题）：一份最多 1 MB，用到时才读、不放进状态里。几个插件加起来要是放不下，装的时候报「这台设备的存储放不下了」。以后插件多了、大了再挪进应用数据目录的文件
- **授权可以部分同意**：§5.2「只关掉用到它的那部分」做成了对话框里每一项一个勾。授权记在装着的那一份里，升级只问多要的那几项；卸载一起删
- **团队仓库里同步过来的 L1**（§6.4）：这台没装的照旧只列在「这个仓库想用」；这台装着、但有没问过的权限（升级过、别的仓库里装的时候没问全），停在「等你授权」不启动
- **停下的插件**（犯规）只在这个窗口里停，仓库里的开关不动；关掉窗口再开就是新的一次

### 15.7 踩到的

- **停一个运行时是异步的**（先问它一声，最多等 1 秒）：停完那一下报的「idle」晚到，那时管家已经把它忘了（停用）或者换成了新的一个（升级、改了授权）。晚到的状态把新的那一个的状态冲掉、把它画好的槽位撤掉，停用后还在 `useScripted` 里留下一条。现在只认「现在这一个」运行时报的状态（`scripted.ts` 的 `current()`），单测「停用：运行时拆掉、那一段撤掉、状态也不留」钉着
- **图标白名单用了 `in`**：`"constructor" in CALLOUT_ICONS` 是 true（原型链上的），P14.2 的提示块图标也有这个洞，插件写 `icon: "constructor"` 能过校验、画的时候拿到一个函数。改成 `Object.hasOwn`，两处都补了测试
- **BroadcastChannel 的拒绝测试一开始没过**：iframe 和它的 Worker 是同一个 opaque origin，彼此收得到对方发的（这是对的），测试把 Worker 发的当成了应用发的。改成只认应用那一头发的那句
- **单测里的假端口每条消息隔一个宏任务才到**：一条命令里来回七八趟就过了 80ms，正常的调用给 1 秒，只有测卡死的用例把超时调短
- **在页面里 `import()` CodeMirror 拿到的是另一份**：用它的 `undo(view)` 撤不了（历史字段是另一个对象），验撤销要真的按 Ctrl+Z
- **设计稿（§5.5）和 Tauri 的源码都说 iframe 里没有 `__TAURI_INTERNALS__`，Windows 上有**：wry 在 WebView2 上不分主框架、子框架。拒绝测试里这一项在 iframe 主线程上记成「注：看得见」，真正查的是调不调得通（调不通）；Worker 里照旧必须没有
- **验 CSP 别用 DevTools 里的 `eval`**：DevTools 协议执行的代码不受页面的 CSP 管，`eval("1")` 在正式档里照样能跑，差点得出「没有 CSP」的结论。要往页面里插一段内联 `<script>`，看它跑没跑、有没有 `securitypolicyviolation`。`frame-src`、srcdoc 被不被拦也要用 `tauri build` 出来的验（§15.8），`tauri dev` 的页面里没有 meta CSP
- **bash 的 heredoc、`node -e '…'` 吃反斜杠、碰到中文的引号就断**：改文件一律用脚本文件跑（memory 里记过，这次又踩了两回）

- 协作的访客窗口不加载插件（L0、L1 都是）；弹出窗口里的槽位画得出来（宿主的组件），没在真的弹出窗口里看过
- 插件在 Worker 里起子 Worker（§5.5「重活另起一个 Worker」）：CSP 放了 `worker-src blob:`，没测
